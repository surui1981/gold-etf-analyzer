## §零 摘要：应用现在处在什么位置

用一句话说清现状：

> **界面和功能已经很完整（8 个顶级场景、116 个版本、移动端实测过、门禁体系齐全），
> 但支撑它的数据只有 47 天，且这 47 天里 60% 带着一个伪造的「中性」分数。**

这个判断不是修辞，是六组实测数字：

| 维度 | 实测值 | 用户以为的 |
|---|---|---|
| 历史评估样本 | `scoring_daily_wide` **47 行**（2026-09-07 → 10-23） | roadmap.md:246 自己写的是「~21,900 条评估基线」 |
| 收益率可用天数 | `/backtest/coverage` → `returns_available_days: **1**`，但 `usable: true` | sharpe / 最大回撤 / 年化 |
| 52W 按钮 | **12 周**（2026-07-31 → 10-19） | 1 年 |
| 24M 按钮 | **4 个月**（2026-07-31 → 10-01） | 2 年 |
| 命中分析「上涨日数」 | **恒为 0**（全表没有一行 `direction = 'up'`） | 47 天里的涨跌分布 |
| 白银升贴水表 | 同一张表里白银 = **$7.50/oz** 和 **$54.62/oz**，差 7.3 倍 | 一个升贴水数字 |

**其中 4 条不是独立 bug，是一条链，而链头只有一行代码**：

```
cache.py:35  _key(target, interval, date) —— key 里漏了 days
   │
   ├─► 60D 请求（页面默认先发）霸占缓存槽 → 52W/24M 按钮返回 60 点
   │        └─► 用户以为看了一年和两年图，实际是 12 周和 4 个月
   │        └─► 实测：同一个 URL 9 秒内先返 60 点、后返 730 点（3 年）
   │
   └─► review.backfill(days=…) 走同一条 analyze() 路径
            └─► 价格回填最多落 60 行（gold_price_daily 只有 60-80 行）
                    ├─► 收益率算不出来（returns_available_days=1）→ sharpe/回撤/年化全是空壳
                    └─► 交易日历只剩 ~3 个月 → 命中率样本 n=23~28
                                                   └─► 所有统计结论不成立
                                                          └─► 权重/阈值怎么调都没意义
```

**数据其实一直都在** —— 直连 provider 实测 `days=730` 能拿到
2023-10-18 起的 **730 根日 K**。**不是数据源不行，是缓存把数据挡在门外了。**

**结论**：现在最该做的不是加功能，是**先把已有的功能变成真的**。
加第 9 个场景，不会让命中率的 40.7%（n=27）变成一个可信的数字。

> **§一 A3 是整份路线图的枢纽**：一行 key 的改动，
> 同时解开 A4（收益率算不出）、§二 B1/B3（回填只有 60 行）、
> 以及「52W/24M 骗人」。**它必须第一个做**，
> 因为后面每一层的验证都依赖它 —— 数据补不齐，测什么都不准。

## §一 第 0 层 · 可信度（最高优先，全部已实测复现）

> 这一层的定义：**屏幕上正在显示、但内容是假的或残缺的**。
> 门禁坏了比没门禁更坏 —— 它让人以为有保护；假数据比没数据更坏 —— 它让人以为有结论。

### A1 · 命中分析的「上涨日数」**恒等于 0**，且 40% 的行不参与统计 🔴

**这是本轮最严重的一条，且 100% 静默。**

`scoring_wide.py:294-295`：

```python
up   = sum(1 for r in grp if r.direction == "up")
down = sum(1 for r in grp if r.direction == "down")
```

但 `scoring_daily_wide.direction` 这一列里**根本没有 `up` 这个值**。
`src/app/schemas/common.py:15-20` 的 `DirectionSignal` 枚举只有三个成员：

```python
BULLISH = "bullish"   # 利多黄金
BEARISH = "bearish"   # 利空黄金
NEUTRAL = "neutral"   # 中性
```

**实测的全表取值分布（47 行）**：

| direction | 行数 | 被 `up_days`/`down_days` 统计吗 |
|---|---|---|
| `down` | 24 | ✅ 计入 down |
| `bearish` | 14 | ❌ **完全不计入** |
| `bullish` | 5 | ❌ **完全不计入** |
| `neutral` | 4 | ❌ 不计入（合理） |
| `up` | **0** | — |

两个后果，都是用户直接可见的：

1. **`up_days` 结构上恒为 0。** `scoring.js:369` 直接渲染 `${b.up_days}`，
   页面上命中分析表 47 行**每一行的「上涨日数」都是 0**。
   用户看到的是「这 47 个交易日，黄金一天都没涨过」。
2. **19 行（40%）的 bullish/bearish 数据被整个丢弃。** 2026-10-13 那次回填
   （`created_at=2026-10-13`，18 行）用的是正确词汇 `bullish/bearish/neutral`，
   而更早的 23 行用的是 `down`。两套词汇在**同一列**里共存，
   统计代码只认其中一套。

**按业务日期看，9 月更严重**：

| 月份 | `down`（能统计） | `bullish`/`bearish`（被丢弃） | `neutral` |
|---|---|---|---|
| 2026-09 | 10 | **13** | 1 |
| 2026-10 | 14 | **6** | 3 |

**9 月有一半以上的数据（13/24）压根不进统计。**

**修法**（三步，缺一不可）：

1. **对齐词汇**：`scoring_wide.py:294-295` 改成
   `r.direction in ("bullish", "up")` / `("bearish", "down")`，
   或者（更彻底）加 `up = bullish`、`down = bearish` 的语义映射函数，
   杜绝下次再混。
2. **加迁移**：把已落库的 `direction` 统一成枚举值（`down` → `bearish`），
   否则历史行永远是错的。
3. **加门禁**（见 §五 H1）：枚举列的取值集合必须与代码里的字面量比对通过。
   今天这条能溜过去，纯粹是因为没有任何一处检查过它。

### A2 · 60% 的历史评分行带着**伪造的中性消息面 50 分** 🔴

`macro.py` / `settings.py:51` 的默认合成权重：

```
tech 0.30  ·  macro 0.40  ·  news 0.30
```

**消息面占 30%** —— 与技术面持平，低于宏观面的 40%，但它是**三大面里唯一一个
经常没有数据的面**（消息面要用户手工打分，见 §一 A2）。

而 `scoring_daily_wide.news_index` 的实测分布：

| 月份 | 行数 | 其中 `news_index = 50.0` | 占比 |
|---|---|---|---|
| 2026-09 | 24 | 11 | **46%** |
| 2026-10 | 23 | 17 | **74%** |
| **合计** | **47** | **28** | **60%** |

`50.0` 就是「中性」—— 而这正是 **V0.100.0 已经修掉的那个 bug**：
「消息面未打分 → 用 50 兜底」改成了「`score=None` → 剔整面 → 按剩余权重归一化」。
**但 V0.100.0 之前的行已经落库了，从没重算过。**

**这个 50 到底吃掉了多少信号？**

关键在于：**要估的量只依赖 news 的权重，不依赖技术面怎么算。**
按 `settings.py:51` 的 `news = 0.30`，把真实的 news 值 `x` 换成占位的 50，
综合指数就凭空偏移 `(x − 50) × 0.30`。

非 50 的行里 news 实测跨度是 **20 ~ 90**（取自 47 行中news ≠ 50 的 19 行），
所以偏移量级：

| 真实 news 若为 | 相对占位 50 的偏移 |
|---|---|
| 90（强利多） | **(90−50)×0.3 = 少 12.0 分** |
| 20（利空） | (20−50)×0.3 = **多 9.0 分** |
| 30（弱利空） | (30−50)×0.3 = 多 6.0 分 |

**这不是小扰动。** 综合指数的历史波动范围大概在 26~50 之间（实测 47 行），
**光是这个占位符就能注入 6~12 分的假摆幅 —— 相当于整个历史波幅的 1/4 到 1/2。**

> ⚠️ **一个诚实的边界**：我**没有**从落库的 `tech_index / macro_index / news_index`
> 三列反解出精确权重。对 47 行做最小二乘，最优解是
> `tech=0.26 / macro=0.64 / news=0.10`，**RMSE 高达 2.795**，
> 拟合不上 —— 说明落库的 `tech_index` 列**不是**参与合成的那个技术面分
> （V0.79.0 的 `group_combine` 在组内先做平均）。
> **所以本文只给「只依赖 news 权重」的上下界，不编精确数字。**

**而所有命中率（t0 35.7% / t1 40.7% / t3 40.0% / t5 39.1%）、
所有 verdict card、所有回测，全都建立在这批被压平的数据上。**

**修法**：

1. 加一个**重算脚本**，用 V0.100.0 之后的逻辑重跑 2026-09-07 → 至今，
   把 `news_index` 从 50 改成 NULL 并重算 `trend_index`；
2. 重算后**所有命中率会变**（大概率），命中分析页要打上「数据已重算」的说明；
3. **在消息面数据真正积累起来之前**，综合指数页必须显示
   「消息面覆盖 x/47 天」——让覆盖不足可见，而不是让 50 冒充真实。

### A3 · `days` 参数完全失效 ⇒ 52W / 24M 按钮画的是 **12 周 / 4 个月** 🔴⭐

> **这是整份路线图上投入产出比最高的一个改动：一行。**

`trend.html:399-401`：

```html
<button data-days="60"  data-interval="D">60D</button>
<button data-days="365" data-interval="W">52W</button>
<button data-days="730" data-interval="M">24M</button>
```

**实测：`days` 传 60 / 365 / 730，返回的点集完全一样。**

| interval | days=60 | days=365 | days=730 |
|---|---|---|---|
| D | 60 点 · 07-31→10-22 | **完全相同** | **完全相同** |
| W | 13 点 · 07-31→10-19 | **完全相同** | **完全相同** |
| M | 4 点 · 07-31→10-01 | **完全相同** | **完全相同** |

用户点「52W」，看到的是**12 周**的图；点「24M」，看到的是**4 个月**的图。

#### 根因：`served_cache` 的 key 漏了 `days`

**先排除掉「数据源没有历史」这个可能** —— 直连 provider 实测：

```
provider days=60   → n=60   2026-07-23 → 2026-10-22
provider days=365  → n=365  2025-04-21 → 2026-10-22
provider days=730  → n=730  2023-10-18 → 2026-10-22   ✅ 3 年历史完好
```

**数据一直都在。** 问题出在 `src/app/services/cache.py:30-36`：

```python
# V0.64.0：key 由 (target, date) 扩展为 (target, interval, date)
_CACHE: dict[tuple[str, str, date], tuple[GoldTrendOut, datetime]] = {}

def _key(target: str, interval: str, on_date: date) -> tuple[str, str, date]:
    """统一构造缓存 key，interval 归一化为大写单字母（D/W/M）。"""
    return (target, (interval or "D").upper()[:1], on_date)
```

**key 是 `(target, interval, date)` —— `days` 不在里面。**

V0.64.0 加 `interval` 是对的（interval 只改聚合粒度，底层数据相同）；
但 `days` 改的是**响应里到底装了多少条数据**，
把它漏掉意味着**两个长度不同的结果共用一个缓存槽**。

**触发顺序**（这是最恶劣的部分）：

1. `trend.html:399` 的 `60D` 按钮带 `class="active"` ⇒ **页面默认先发 `days=60`**
2. 这次调用把 60 点结果写进 `key=(ny, D, today)`
3. 接下来 600 秒（`served_cache_ttl_seconds`，`config.py:91`）内，
   任何 `days=365` / `days=730` 的请求都命中这个槽，**拿到 60 点**
4. 谁先发谁定调

#### ✅ 实测证明：同一个 URL，9 秒内返回两种完全不同的数据

后台轮询 `GET /trend?days=730&interval=D`（每 2 秒一次，等 TTL 到期）：

```
05:13:30  points=60
05:13:39  points=730        ← TTL 到期，同一个 URL
```

**同一个 URL，`days=730`，先返回 60 点，9 秒后返回 730 点
（覆盖 2023-12-26 → 2026-10-22，3 年）。**

更妙的是**命中之后**（730 点已占据那个共享槽）：

```
days=60   → n=730   2023-12-26 → 2026-10-22
days=365  → n=730   2023-12-26 → 2026-10-22
days=730  → n=730   2023-12-26 → 2026-10-22
```

**现在点「60D」会拿到 3 年的日 K。**

⇒ 这不是「按钮标签写错了」，是**同一个接口在不同时刻返回长度差 12 倍的数据**，
而前端三种标签共用同一份数据去画图。
**任何基于这个接口的统计、图表、导出，都会跟着这次抽签结果变。**

**连带影响**：`review.py:132` 的 `backfill(days=…)` 走同一条 `analyze()` 路径，
所以**价格回填也最多只能落 60 行** —— 这就是 §二 B1 里 `gold_price_daily`
只有 60-80 行的直接原因。**它不是「没做回填」，是「回填了也只有 60 行」。**

#### 修法

```python
# cache.py：把 days 纳入 key
def _key(target: str, interval: str, on_date: date, days: int | None = None):
    return (target, (interval or "D").upper()[:1], on_date, days or 60)
```

连带要改 `get_served` / `set_served` 的签名与 `trend.py:396/402` 两处调用。

⚠️ **注意缓存容量**：加了 `days` 之后 key 空间从 3×3 变成 3×3×N。
`served_cache_ttl_seconds=600` 会自然淘汰，但如果 key 用裸 `days` 值，
`days=37/58/60/365/730` 各占一格。**建议归一化到档位**
（`60 / 250 / 500 / 750`），避免缓存碎片。

⚠️ **两层缓存**（记忆 `served-cache-two-layer`）：改完之后，
历史序列会变长，**必须同时清 `TrendService.invalidate_cached_results()`
和 `market_data.py:585` 的 `("etf", days)` 仓储缓存**，
否则会看到「保存成功但数值不变」。

**验证判据**（改完必须为真）：

```
curl "…/trend?days=730&interval=D"   → 730 点，起始 ≈ 2023-12（今天实测已是这个值）
curl "…/trend?days=60&interval=D"    → 60 点（今天实测是 730，因为撞上了共享缓存槽）
curl "…/trend?days=365&interval=W"  → ≈ 52 个周点
curl "…/trend?days=730&interval=M"  → ≈ 24 个月点
```

**四个数必须互不相同，且各自符合标签。** 今天它们全是同一个数 —— 这就是判据。

再加一条门禁（§五 H3）：**每个 `data-days` 按钮的返回点数必须与标签一致**。

**顺带修文档**：`market.py:178` / `:209` / `:329` / `:356` 四处 description
写着「上限 750 ≈ 3 个交易年，支持 24M 月 K 聚合」——
修完之后这句话**才第一次成立**。修之前它是错的。

### A4 · 回测的 sharpe / 最大回撤 / 年化，建立在 **1 个观测**上 🔴

`/api/v1/backtest/coverage` 实测返回：

```json
{"available_days": 14, "available_window_trading_days": 14,
 "price_calendar_days": 2, "returns_available_days": 1, "returns_missing_days": 13,
 "usable": true,
 "note": "覆盖期 2026-10-07 ~ 2026-10-23（14 个有效样本）；已排除 3 天来源不可信
          （mock 或未标记）的快照；历史快照均无来源标记，故从今日起才逐步可用；
          其中 13 天因缺后继交易日价格而未参与指标计算"}
```

**14 个快照里只有 1 天能算出收益率**，但 `usable: true`，
所以页面照常显示 `0.00` 的 Sharpe、`0.00%` 的最大回撤、`0.0%` 的命中率。

#### 关键：披露机制是**存在**的，只是从来没被触发

`static/backtest-chart.js:113-120` 有一套做得很完整的保护：

```js
var notMeasured = (s.usable === false || cov.usable === false);
var suffix = notMeasured ? "（填充值）" : "";
…
'<div class="label">最佳 Sharpe' + suffix + '</div>…' +
'<div class="extra">' + (notMeasured ? "缺少价格数据，未计算" : "越高越好") + '</div>'
```

**问题出在触发条件上。** `src/app/services/backtest.py:279`：

```python
usable = returns_ok > 0          # ← 1 > 0 ⇒ True
```

`returns_ok` 是 **1**。`1 > 0` 成立 ⇒ `usable = True` ⇒
`notMeasured = false` ⇒ **「（填充值）」后缀不出现、「缺少价格数据，未计算」不出现**、
数值照常渲染成 `0.00`。

同一条链上还有第二道门也差一点没拦下：

```python
MIN_SAMPLES_OVERALL = 10                      # backtest.py:47
sample_warning = available < MIN_SAMPLES_OVERALL or not usable    # :308
```

`available = 14`，`14 < 10` 为假；`not usable` 也为假 ⇒ **`sample_warning` 也是 False**，
所以 `backtest-chart.js:295` 的告警横幅同样不触发。

> **所以这不是「没有披露」，是「披露的阈值差了 10 倍」。**
> 系统知道该说，只是判据写成 `returns_ok > 0`，
> 于是 1 天和 200 天被当成同一回事 —— 而且 `available = 14` 刚好从
> `MIN_SAMPLES_OVERALL = 10` 上面过去，两道门一起放行。

**修法**（一行）：

```python
usable = returns_ok >= MIN_SAMPLES_RETURNS      # 而不是 > 0
```

配套：`MIN_SAMPLES_RETURNS` 建议取 20（收益率指标的最低可信样本），
并在 `sample_warning` 里用 `returns_available_days` 而不是 `available_days`
（两者差 14 倍，用错了就等于没有）。

**验证判据**：修完之后 `/backtest/coverage` 应返回 `usable: false`，
回测页应出现「（填充值）」后缀 +「缺少价格数据，未计算」+ 告警横幅。

> **顺带**：A3 修好 + B3 回填之后 `returns_ok` 会自然上去，
> 这条就自动消解。**但阈值仍要修** ——
> 否则下一个「采集又断了」的场景会以完全相同的方式静默复发。

### A5 · 3-market 升贴水表：同一张表里白银有两个价格，差 7 倍 🔴

`/api/v1/market/health` 实测：

```json
{"etf": "live", "ny": "live", "sge": "live",
 "silver_etf": "stale", "silver_ny": "stale", "silver_gram": "stale",
 "sge_silver": "mock",
 "xau": "stale"}
```

**白银侧 4 个源一个 `live` 都没有** —— 沪银 `sge_silver` 是 **mock**（演示数据）。

#### 先说做对的部分

`/silver` 顶部的数据源条**做得很好**（`silver.js:390-397`），
实跑显示：

```
⚠️ 部分数据源降级为演示数据（1 mock / 3 live）：sge_silver
   · ⚠ 时效滞后: SGE 上海银 Ag99.99 数据至 2026-10-20（滞后 3 天）
```

这一条比很多项目都强。

#### 问题在表里

`/silver` 的「多市场升贴水表」（V0.99.0 C5 交付，以 SGE 为锚）实跑渲染：

| 指标 | 562800 ETF | NY SI 折算 | SGE Ag99.99 |
|---|---|---|---|
| 折算口径 | 元/份 × 1000 | USD/oz × 31.1035 × 7.1 | 现货基准 |
| 最新价 | 1656 | 12062 | 13854 |
| 升贴水（以 SGE 为锚） | **−88.05%** | −12.93% | +0.00% |

**算式本身没问题** —— 我用页面写的口径逐项复算，
−88.05% 和 −12.93% **都能一位不差地重现**（`silver.js:237-240`）。

**但同一张表在暗示白银有两个价格，差 7.3 倍**：

```
ETF 列：1656 元/kg ÷ 7.1 ÷ 31.1035 = $7.50/oz
NY  列：12062 元/kg ÷ 7.1 ÷ 31.1035 = $54.62/oz   ← 与 NY 报价端点完全一致
```

白银不可能同时是 $7.50/oz 和 $54.62/oz。
**所以 −88.05% 不是「ETF 折价」，是某一列的口径错了** ——
而且表格把它当作真实升贴水，用颜色标成绿色（`col()` 把 < −0.5 判为 `down`）。

**加重问题**：
- 三个列的值全部来自 stale/mock 源，**表内没有任何标注**，
  只有页面顶部那条通用横幅；
- ETF 报价接口自己带着 `"data_source_note": "lof_proxy"`（代理值），
  页面没透出这个字段；
- SGE 锚是 **mock**（`silver.js:375` 的 key 写对了，
  但 `help.js:214` 仍写 `silver_mock` —— 文档漂移）。

#### 修法

1. **锚是 mock 时拒绝渲染**：`renderPremiumTable` 拿到 `sge_silver.status !== "live"`
   就显示「基准价为演示数据，不计算升贴水」，而不是给一个 −88.05%；
2. **表格内逐列标源状态**（live/stale/mock），不依赖页面顶部横幅；
3. **核对 `ETF_G_PER_SHARE = 1000` 这个假设**（`silver.js:236`）——
   7.3 倍的差要么在这一项，要么在 `lof_proxy` 的口径上。
   **在核对清楚之前，这一列的升贴水不应该展示。**
4. 顺带修 `help.js:214` 的 `silver_mock` → `sge_silver`。

## §八 方法论：这一轮是怎么查出这些的

### 8.1 最有价值的两个发现，都不是「读代码读出来的」

**A1（上涨日数恒为 0）** 是从**渲染出来的页面**里看出来的 ——
puppeteer 切到命中分析 Tab、把每张表 dump 出来，发现 47 行全部「上涨 0」，
才回头去查 `scoring_wide.py:294`。只读代码不会发现它：
`sum(1 for r in grp if r.direction == "up")` 这行本身看不出任何问题。

**A3（`days` 失效）** 是被一个**反直觉的观察**逼出来的：
「为什么 `days=60` 和 `days=730` 返回一样？」
第一反应是「数据源只有 60 天」，于是去 `roadmap.md` 找佐证 —— 找到了「730 天」。
**两处文档互相印证，反而没人怀疑文档。**
真正定位靠的是**绕过所有缓存直连 provider**：

```
provider days=730 → n=730，2023-10-18 起    ← 数据一直都在
```

一行这个调用，把「数据源不行」和「缓存挡路」彻底分开了。

> **教训**：当两个独立来源给出同一个可疑数字时，
> **它们更可能是同源的错误，而不是相互印证。**
> `roadmap.md:246` 的「21,900 条」和端点实际返回的 60 点，
> 就是这么互相「印证」了好几版的。

### 8.2 这一类问题的共同特征

它们**不产生错误**，只产生「看起来正常的数字」：

- `up_days` 永远算成 0 —— 没有异常、没有日志、页面照常渲染
- `news_index = 50.0` —— 中性分在 schema 上完全合法
- `days=730` 返回 60 点 —— 返回 200，JSON 结构完整，字段一个不少
- `returns_ok = 1` 却 `usable: true` —— 布尔值本身就是「可用」
- `mock` 源 —— 值的形状和真实数据一模一样

有意思的是：**A4 和 A5 都不是「缺少披露」，而是「披露机制的判据错了或不够」**。
回测页早就写好了「（填充值）」后缀和「缺少价格数据，未计算」，
只是 `usable = returns_ok > 0` 让它永远不触发；
白银页顶部的降级横幅也做得很好，只是**表里那三个数字自己不会说话**。

> 所以 §一 不是「加提示」，而是**「修判据」** ——
> 让已经存在的诚实机制真的能被触发。
> 这比新写一套提示文案更省事，也更不容易做漏。

对应到工程上就是 §五 那 7 条横向纪律。
它们看起来都不产生用户可见价值，但**没有它们，第 0 层修完还会再烂回去** ——
`check_v084` 就是因为「没人看」而烂掉的样板。

### 8.3 一条可以复用的排查手法

**「绕过缓存直接打 provider」应该成为默认动作，而不是最后手段。**

本轮两次关键定位都靠它：

- **A3**：直连 provider 才知道数据是全的 ⇒ 问题在缓存层。
  随后再补一次「等 TTL 到期后重打」才拿到**同一个 URL 两种结果**的铁证。
- **A2**：`news_index` 分布 + `settings.py:51` 的 `news=0.30`
  才估得出「假 50 每行注入 6~12 分」。

记忆里那条 **served_cache 两层缓存陷阱** 已经记了
「写入后必须清两层缓存」，本轮补上了它的另一半：
**排查时也要绕过两层缓存，否则你会对着缓存里的假象下结论。**

### 8.4 两次「差点写错」的记录

留在这里是因为它们比结论更值得复用：

1. **差点断言「升贴水表的数字无法用页面自己的口径复现」。**
   实际是我把「折算后」的价（1656 / 12062）又过了一遍折算公式。
   页面那行标题就是「**最新价**」但显示的是折算值 —— 逐项复算后 −88.05% / −12.93%
   **一位不差**。算法没问题，问题在输入和口径。
   ⇒ **断言一个数字算不出来之前，先确认自己手里的操作数是不是同一层的。**
2. **差点在文档里写「`trend = tech×0.3 + macro×0.4 + news×0.3` 完全吻合」。**
   实际四行里有三行差 0.2~6.0 分，最小二乘最优解 RMSE 高达 2.795 ——
   落库的 `tech_index` 根本不是参与合成的那个技术面分（V0.79.0 `group_combine` 先做组内平均）。
   最后改成只给**只依赖 news 权重**的上下界，不编精确数字。
   ⇒ **拟合不上就说明模型错了，不要硬调参数去凑。**
