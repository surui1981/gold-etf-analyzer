## 〇 一页结论

### 排序依据（先说清「主次」是怎么定的）

不按「价值 ÷ 成本」排，而按 **①不做的后果是否不可逆 × ②是否有前置依赖** 排。理由：

- 会**丢数据**的问题 → 每次使用都在损失，且客户不知道自己在损失 → 无止损点
- 会**串数据**的问题 → 一旦开放多人使用就泄露，事后无法撤回 → 不可逆
- 会**误判**的问题 → A 包已修完（失败态不再伪装正常）
- 会**不便**的问题 → 可交换、可延后

### 主次总表

| 层 | 主题 | 核心条目 | 触发条件 | 成本 | 不做的后果 |
|---|---|---|---|---|---|
| **第 0 层** | **开放多用户的前置门槛** | V0.75.2 数据隔离（9 张表加 `user_id` + 仓储注入 + 存量归 `LEGACY_USER_ID=1` + 404 不泄露 + 迁移先备份） | **只要打算让第二个人的数据独立，就必须先做** | ~2 人天（P4-b 共 6 人天，第①步已落地） | 客户 A 看到客户 B 的交易流水与研判；项目自评「半成品，不宜对外」 |

| **第 3 层** | **视客户构成** | D1 `country.*` 33 死键 · D2 4 个 fallback 键 · D3 后端中文标签 · D7 门禁升级（机制组）；D4/D5/D6（体力组） | **有没有繁中/英文客户** | 机制组 ~1 天；体力组 ~3 天 | 无外文客户 → **影响为 0，整包暂缓** |

### 推荐路线（若近期要交付给团队/客户）

**丙 · 先补丁、后门槛**：

1. **半天**做 V0.77.2（第 1 层四条）—— 成本极低，但不能拖：客户每次打分都在丢依据
2. **~2 天**做 V0.75.2 数据隔离 —— 打开「多人各自用」的门
3. 之后按第 2 层 → 第 4 层推进

### 定位已确认（2026-10-03 追加）

> **答复：应用作为 C 端客户应用使用**；同时我们自己用它做**「第二个交易日」（T+1）的趋势判断**。

**这个变量已消除，路线收敛为「路线丙」**：

- 面向多个客户 ⇒ **第 0 层数据隔离是硬门槛，不可跳过**（路线甲出局）
- 「先补丁 → 再门槛」的顺序不变，理由见 §六 6.1（现在是迁移成本最低的时刻：需归户的真实客户数据合计**仅 8 条**）

同时新增一项待决事项（第 2 层），详见 §六：

> **每日打分次数要不要从「固定 3 次」改为「用户自选」？**

> 实测：该上限**从未被触及**（全库仅 1 条打分）；且在现有线性权重下，**次数越多「最新判断」越被稀释**（N=10 时从 50% 掉到 18%），与「越晚权重越高」的设计意图相反。

## 二 主次分层详解

### 第 0 层 · 开放多用户的前置门槛（V0.75.2 数据隔离）

**性质**：不是「改进」，是「发布前提」。它不提升任何体验，但**不做的代价不可逆**。

**工作内容**（据 `improvement-path.md:310`）：
- 9 张表加 `user_id`：`positions` / `accounts` / 交易流水 / `news_scores` / `daily_snapshots` / `gold_price_daily` / `push_subscriptions` / `app_settings` / `telemetry_events`
- 存量数据归入 `LEGACY_USER_ID = 1`
- 仓储层统一注入用户上下文（现在硬编码 `= 1`）
- 跨用户访问返回 **404 而非 403**（不泄露资源存在性）
- 登录后路由与导航按角色裁剪
- 迁移**先备份 + 幂等补列**（沿用 `ensure_sqlite_columns` 兜底）

**风险（高）**：涉及 9 张表 + 所有仓储查询路径 + 存量数据归属。本项目有明确教训 —— **`create_all` 不给已有表加列**，必须 Alembic `upgrade head` + `db_migrate.py` 幂等补列；且**迁移前不可 `create_all`**（双写者争锁 → 启动 hang）。

**验证方式**：建两个测试用户 → 各自建仓/录入交易/打分 → 断言 A 的查询结果里**看不到** B 的任何记录（含计数一致）；跨用户直接按 id 访问返回 **404**；`authz_violation` 审计事件计数为 0。

### 第 1 层 · 每次使用都在发生的损失（建议无论如何先做）

| 条目 | 证据 | 成本 | 为什么不能等 |
|---|---|---|---|
| **B1** 打分保存补 `basis` / `review_note` | `news.html:525` 的 payload 仅含 `score/direction/notes/slot`；后端契约 `schemas/news.py:30-33` 两字段默认空 → **缺省即覆盖为空**（仓储层对这两项是硬覆盖） | **1 行** | 客户认真勾的 12 个研判依据全部静默丢弃 → 复盘页「依据胜率」表**永久为空**，而客户会以为是自己没勾 |
| **B2** 修掉轮询清空输入 | `portfolio.html:751` `document.getElementById("price").value = d.trend_index ? "" : "";` —— 两分支同值，**空操作三元**；由 `:551-558` 的 30s 定时器触发 | **1 行** | 注释写「预填开仓价格」，代码实际在**清空**。填好价格准备开仓，最长 30 秒后被静默清空 |
| **B5** 修正复盘页空态指引 | `review.html:369` 写「可在该页填写并指定日期」，而 news 页编辑器**无任何日期控件** | 1 行 | 客户按指引跳过去找不到入口，路径断死 |
| **C2** 权重「恢复默认」加确认 + `try/catch` + `else` | `weights.html:315-319`：无二次确认、无 `try/catch`（网络失败即未捕获异常）、`if (r.ok)` **无 `else`**（服务端拒绝时界面毫无反应） | 小 | 一次误点即**不可撤销地**覆盖自定义权重，并**立即改变综合指数与购买决策** |

**为什么这一层必须优先于第 2–4 层**：这四条都不是「不好用」，而是**用一次损失一次**。B1 尤其 —— 它是 V0.76.0 引入首页打分器时新旧双实现不一致造成的**回归**（`news-score-widget.js` 已正确回填 `notes`/`basis`，而 `/news` 页没有），意味着**同一件事在两个入口一个有损、一个无损**。

**建议合成 V0.77.2 补丁版**（纯前端、接口零新增、用例数不变），半天内可完成并发布。

### 第 2 层 · 让复盘闭环真正成立（B3 / B4 日期能力）

**性质**：这不是修 bug，是补**能力缺口** —— 后端早已支持，前端没有入口。

| 条目 | 现状证据 |
|---|---|
| B3 持仓补「成交日期」 | `portfolio.html` **无** `type="date"`（grep 零命中）；而后端 `schemas/position.py:119` 已支持；站内已有范式 `trades.html:151/155` |
| B4 打分补「日期」 | `news.html` **无** `type="date"`；但同页 L571 的表格**已在展示 `score_date`** —— 字段存在、只缺输入入口 |

**风险（必须验证）**：补录的日期会参与**收益曲线回放**与 **T+N 命中统计**，需确认 `_replay()` 的归属规则 —— 本项目既定口径是「按**首个 ≥ 成交日的交易日**归属；**成交日晚于行情序列末日时归入最后一个可得交易日，绝不丢弃**」（ETF 源 T-1 滞后 / 盘中 / 周末录入都会触发）。这是上一轮踩过的地方，本次必须复核。

**验证方式**：用**历史日期**补录一笔 → 核对收益曲线回放位置、平均持仓天数、T+N 命中判定三者是否符合上述口径；再补录一个**周末/未来日**日期 → 确认归入最后一个可得交易日而非丢失。

### 第 3 层 · 视客户构成（D 多语言包）

**判断依据只有一个：有没有繁中/英文客户。没有 → 影响为 0，整包暂缓。**

若要做，**内部也要分主次**：

- **机制组（先做，~1 天）**：D1 `country.*` 33 键死键（**真 bug**：字典键是英文国名 `"country.China"`，代码拼 ISO-3 `CHN` → 命中 0，央行页翻译投入归零；这也是我上轮「图例改走 i18n」空转的根因）· D2 补 4 个连 zh-CN 都缺的 fallback 键（时效条在英文/繁中环境显示中文）· D3 后端 `market_clock` 中文标签改返回 key · **D7 门禁升级**（i18n 门禁现在只扫 HTML 属性、**完全不覆盖 JS 调用**，且不查 zh-TW）
- **体力组（押后，~3 天）**：D4 zh-TW 缺 141 个在用键 · D5 4 个模块接 i18n · D6 语言切换重渲染模板内容

**理由**：先把「能永远拦住问题的门禁」建起来，剩下的缺口会自己暴露；D4/D5 是纯体力活，投入产出比在确认有外文客户前无法评估。

**风险**：D1 是**字典键改名**，需全仓 grep 确认无其他引用方式后再动。

### 第 4 层 · 可延后（但有两条便宜可捡）

- **E1（回测芯片键盘不可用）便宜可捡**：芯片在 `backtest.html:266-282` 的 `renderChips()` 里**动态生成**为 `<span class="chip">`，容器绑 `click` 委托 → 键盘客户完全无法使用该页核心功能。**改成 `<button>` 后，现有 click 委托自动获得键盘支持**（Enter/Space 会派发 `click`），几乎零逻辑改动，只需适配 `.chip` 的 CSS。这是全站「投入产出比最高的一条无障碍修复」。
- **F 包的「请求量」类问题在本地单机场景价值大幅降低**：`#40/#41`（首页 7 请求/分、持仓页 30s 轮询）在 `127.0.0.1` 上无带宽与服务端压力，**但 F1「结论卡被推到第 214 行」仍然值得做** —— 首屏看不到结论是真实的体验损失，与部署形态无关。
- **C 包（一致性）价值中等但风险最低**：C6（`settings.html` 补 `responsive.css`，实测引用数为 **0**）成本极低；C4（`backtest.html` 成孤岛页）需先确认「它与独立布局是否冲突」—— 该项目文档未记录原因，**可能是有意为之，动前先确认**。

## 三 三条候选路线

| | 路线甲 · 信任收尾线 | 路线乙 · 产品化门槛线 | **路线丙 · 先补丁后门槛（推荐）** |
|---|---|---|---|
| **适用** | 只有你/团队看同一份数据 | 多个客户各自记录 | 近期先给团队试用、之后开放 |
| **顺序** | V0.77.2（半天）→ B3/B4（1.5 天）→ C 一致性 → E → F | V0.75.2 数据隔离（~2 天）→ V0.75.3 找回密码+用户管理（~2 天）→ 回到路线甲 | **V0.77.2（半天）→ V0.75.2 数据隔离（~2 天）→ B3/B4 → C/E → 视客户 D → F** |
| **收益** | 单机场景下达到可信、可复盘、少踩坑 | 打开「多客户独立使用」的门 | 先堵住持续失血，再开门 |
| **代价** | 不解决数据隔离，不能开放给多人 | 半天内不做 V0.77.2 → 期间客户继续丢依据 | 半天 + 2 天，稍长 |
| **风险** | 若之后要开放，仍需补第 0 层 | 数据迁移风险（高），需先备份 | 同乙 |

**推荐丙的理由**：V0.77.2 的半天投入是「顺手」，但**不做会持续伤害信任**（客户每次打分都在丢依据、每次填价格可能被清空），而它恰好是**零依赖、零接口变更**的纯前端补丁 —— 没有任何理由让这半天排在数据隔离之后。

### 6.2 「当前页面每天只统计 3 次数据」的定位与实测

**定位（源码级）**：**消息面打分的每日槽位上限**（全仓 grep「3 次」唯一匹配）。

| 位置 | 内容 |
|---|---|
| `src/app/models/news.py:29` | `MAX_DAILY_SLOTS = 3` ← **单源常量** |
| `src/app/services/news.py:38` | `SLOT_WEIGHTS = {n: n for n in 1..MAX}` → 权重 **1:2:3** |
| `src/app/models/news.py:36` | 唯一约束 `(score_date, slot)` |
| `src/app/schemas/news.py:37` | `slot: le=MAX_DAILY_SLOTS` ← **导入期求值**，改配置时的硬骨头 |
| `static/news-score-widget.js:59` | `var MAX_SLOTS = 3;` ← **前端独立硬编码**，未读 API 的 `max_slots` |

**设计语义（易被误解）**：槽位**不绑定时段**（`models/news.py` 注释原文：「序号制，不绑定具体时段」）—— 它是纯**计数上限**，不是「早/中/晚」三个固定时点。

**实测（这个数字改变了优先级）**：

```
news_scores 全库记录数 = 1     （2026-08-30，slot 1，分值 68.0）
```

**该上限从未被触及。** 连带推论：

- 消息面打分占「综合趋势指数」30% 权重 → 仅 1 天有数据，其余各天 `news_index` 恒为中性参考 **50**
- 你的 T+1 复盘校准（`services/review.py`：对比 **T+1/T+3/T+5** 金价涨跌）**同样只有 1 个样本** → 校准功能实际处于**空转**状态

**所以真正的问题不是「3 次够不够」，而是「为什么几乎没打」。**（可参照 A 包的发现方向：入口在首页、`/news` 页曾有取数失败静默、依据标签会被丢弃 —— 即「打了也白打」。）

### 6.3 关键洞察：放开次数会给「次日判断」帮倒忙

若保留现有**线性**权重（1:2:…:N）而把次数放开：

| 每日次数 N | 最新一次权重占比 | 倒数第二次 | 说明 |
|---|---|---|---|
| 1 | 100% | — | |
| 3（**现状**） | **50.0%** | 33.3% | 最新一次恰占一半 |
| 5 | 33.3% | 26.7% | |
| 7 | 25.0% | 21.4% | |
| 10 | **18.2%** | 16.4% | 最新判断几乎被淹没 |

公式：最新一次占比 = N ÷ (1+…+N) = **2/(N+1)** —— **N 越大，最新（信息最全、最接近收盘、对次日判断最有价值）的一次越被稀释**，与「越晚权重越高」的设计意图**方向相反**。

**还有一个更根本的问题**：同一天内的多次打分**高度自相关**（面对同一个信息环境、同一批投行观点），**增加日内次数并不增加独立样本量** —— 对 T+1 校准没有实质帮助。真正能增加独立样本的是：

1. **更多天数**（坚持每天打）
2. **补录历史**（`backfilled` 机制已存在，且正确地排除于统计之外，避免前视偏差）

### 6.4 三个方案与推荐

| 方案 | 做法 | 依赖 | 成本 | 代价 |
|---|---|---|---|---|
| **甲 · 保持 3 次固定**（推荐） | 不改 | 无 | **0** | 无；且保住历史口径与 `2/3` 测试断言 |
| **乙 · 全局可配** | 设置页配 `news_slot_limit`（默认 3），权重仍线性 1..N | 无 | 0.5–1 天 | 改了次数的那天与历史**不可比**，校准统计会跨口径混合 |
| **丙 · 每用户自选** | 每用户在设置页自选 1–10 次 | **依赖数据隔离先行** | 乙 + 0.5 天 | 跨用户口径不统一；群体排行/校准若要做则失真 |

> **若要选乙/丙且允许 >3 次，必须同时改权重公式**：从线性 `1..N` 改为几何 `w_i = 2^(i-1)`，让最新一次稳定在 **~50%**（N≥3 时：57.1% / 53.3% / 51.6% / 50.4% / 50.0%），倒数第二稳定 ~25%。这样增加次数只增加「历史采样」，不改变「最新判断的决定性」。
> **代价**：历史分值口径断裂 —— 需引入公式版本号（旧数据按 v1 线性冻结、新数据按 v2 几何），否则历史 `effective` 分值会被重算而不可复现。

**推荐甲**，理由不是「省事」，而是：**这个上限从未被触及（1 条记录），而真正缺的是样本天数与「打了不丢」**。若你的诉求是「为 T+1 判断积累样本」，正确的动作是补 B1（打分丢依据）+ B3/B4（补日期能力，让历史补录可行），而不是放开每日次数。

### 6.5 隔离范围需要修正（实测反驳了原规划）

`docs/improvement-path.md:310` 的 P4-b 写「9 张表**全部**按用户隔离」。按数据性质实测后有 4 处需要修正：

| 表 | 原规划 | 实测性质 | 建议 |
|---|---|---|---|
| `gold_price_daily` | 加 `user_id` | **市场公共行情**（0 条） | **不加** —— 否则同一份行情复制 N 份，浪费且易不一致 |
| `analysis_records` | 未列 | **市场公共宏观**（dxy/us10y/real_rate…） | **不加** |
| `central_bank_purchases` | 未列 | **市场公共**（96 条） | **不加** |
| `daily_snapshots` | 加 `user_id` | ⚪ **混合体**：`close`/`ma20`/`tech_index`/`macro_index` 是市场公共；但 **`news_index` 由该用户的打分合成**，`trend_index` 随之也是用户相关 | **不能简单加** —— 加则行情重复 N 份；不加则客户 A 的趋势指数里混了客户 B 的消息面。需**拆解**：市场部分留公共表，用户部分（`news_index`/`trend_index`）按用户另存 |

**真正需要归户的只有 4 张**：`trade_records` / `news_scores` / `app_settings` / `push_subscriptions`（`positions`/`accounts`/`telemetry_events` 已有 `user_id`，只需把硬编码的 `= 1` 换成真实用户）。

> 这条修正的价值：照原规划直接给 9 张表加 `user_id`，会把**市场公共数据错误地按用户复制**，并给 `daily_snapshots` 留下「同一份行情存 N 份、且用户维度不自洽」的长期隐患。
