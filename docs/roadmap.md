## 一、可信度层（最高优先 · 用户会被误导的地方）

### A1 · 命中分析的「上涨日数」恒等于 0 ✅（V0.121.1 已修）

**现象**：命中分析页每个时间桶的「上涨天数」永远是 0。

**实测（2026-11-05）**：`scoring_daily_wide.direction` 的取值分布 ——

| direction | 行数 |
|---|---|
| `down` | 30 |
| `bearish` | 14 |
| `neutral` | 8 |
| `bullish` | 7 |
| **`up`** | **0（不存在）** |

而代码 `src/app/services/scoring_wide.py:293` 算的是
`up = sum(1 for r in grp if r.direction == "up")` ⇒ **永远加不上**。

**根因（2026-11-06 复核：是三层叠在一起，不是一个词写错了）**：

| 层 | 实测事实 |
|---|---|
| ① 口径根本不是「当日涨跌」 | `daily_snapshots.direction` = `_detect_direction(closes, ma20)` ⇒ 语义是「收盘价 vs MA20 + MA20 斜率」的 **60 日趋势方向**。生产库 60 行：`down` 56 / `sideways` 4 / **`up` 0** |
| ② `change_pct` 也不是当日涨跌 | `snapshot.py` 调的是 `trend.analyze(days=60)` ⇒ `change_pct` 是 **60 日区间涨跌幅**（实测 `-12.68` / `-11.83` / `-10.64`） |
| ③ 宽表列被**消息面方向**覆写 | `scoring_wide.py` 里 `row.direction = direction_of(effective).value` 把**消息面**方向（bullish/bearish/neutral）写进了**价格**方向列 ⇒ **一个列两套词表** |

⇒ 三层任意一层单独修都不够，**必须治本**。

**唯一可信的「当日涨跌」源**：`gold_price_daily.change_pct` ——
模型注释明写「**相对前一交易日的涨跌幅 %**」（ny 目标 80 行：40 up / 39 down / 1 flat，
**但只到 2026-10-14** ⇒ 见 B1）。

**修法（V0.121.1，用户已拍板「一并治本：加列 + 迁移」）**：
新增 `scoring_daily_wide.price_direction` 列（可空）+ **停掉消息面方向覆写** +
`price_direction` **只从 `gold_price_daily.change_pct` 的符号取**，**该日无价格行 ⇒ NULL（未知），不兜底**。

> ⚠️ **已排除的兜底方案**：不能拿 `daily_snapshots.close` 顶替 ——
> 实测两源同时有数的 **27 天里方向只有 12 天一致（44%）**，
> 且快照 close 多数等于 `gold.close(d−1)` ⇒ **系统性错位一天，比留空更坏**。

**✅ V0.121.1 落地结果**：迁移 `t2u3v4w5x6y` 加列 + ETL 只从 `gold_price_daily.change_pct` 取符号
+ 停消息面方向覆写 + 聚合加 `known_days`。生产库实测：`price_direction` 分布
**down 17 / up 11 / NULL 33** ⇒ **上涨天数不再是 0**；宽表 `direction` 取值
从 `bullish 7 / bearish 14 / neutral 8` 变成 **`down 55 / sideways 6`**（两套词表混用已消除）。

**⚠️ V0.121.3 收尾（发版后的线上复测发现「没修干净」）**：
桶聚合被**抄了三份**（`summary()` / `hit_stats()` / `hit_stats_all_horizons()` 共用同一个
`ScoringSummaryBucket` schema），V0.121.1 **只改了 `summary()` 那一份** ⇒
`/scoring/hit-stats` 与 `/scoring/hit-stats-all` 仍返回 **`up_days=0`**。
⚠ **0 与 null 语义不同**：前端只对 `null` 兜底「—」，`0` 会被如实渲染成「上涨 0 · 下跌 0」。
⇒ 抽出 `_bucket_direction_stats()` 让三处共用一份口径；
同时按**补齐后**的价格日历重算宽表 —— `price_direction` 覆盖 **28 → 45** 行，`hit_t1` **13 → 22** 行。
**教训**：共用 schema ≠ 共用口径；**验收要遍历所有返回该 schema 的端点**，不能只挑一个看。

### A2 · 64% 的历史评分行带着伪造的中性消息面 50 分 ✅（V0.121.1 已修）

**实测（2026-11-05）**：`scoring_daily_wide` 59 行里 **`news_index = 50` 的有 38 行（64%）**，
`news_index IS NULL` 的 **0 行**。

**为什么 50 是假的**：50 = 「中性」= **「没打分」**的占位值。
V0.100.0 已经把「未打分」改成 `score=None` + 综合指数挂 pending chip，
但**历史宽表里的旧行没被回填**，于是：
- 命中分析里这些行**参与了消息面均值**（把 50 当成真实打分）；
- 而同一个综合指数在实时接口里是 **pending** ⇒ **同一个日子两个结论**。

**污染链（2026-11-06 复核，已打通到源头）**：

```
trend.news.score = None（今天没打分）
  └─ services/snapshot.py → news_index = 50.0            ← 源头伪造
       └─ models/snapshot.py → news_index NOT NULL DEFAULT 50  ← 源头锁死
            └─ 宽表 ETL 继承 ⇒ 31 行假 50
                 └─ direction_of(50.0) = NEUTRAL（**不是 None**）
                      └─ judge_hit(NEUTRAL, chg) → 按 ±0.3% 横盘判定
                           ⇒ **伪造出 14 个 hit_t1 / 12 个 hit_t5**
```

**修法（V0.121.1，治源头 + 连带清假命中）**：
① `daily_snapshots.news_index` 改 **nullable** + `snapshot.py` 不再兜底 50（None 就是 None）；
② 宽表 ETL：当天无 `news_records` ⇒ `news_index = None`（`news_slot_count = 0`）；
③ **一次性幂等回填**：`news_slot_count = 0` 的行 ⇒ `news_index = NULL` + `hit_t0/t1/t3/t5 = NULL`
（判定需要方向，没方向就没有判定）；`news_slot_count >= 1` 的行**一律不动**；
④ 消费侧 null-safe（`backtest.py` 的 `float(snap.news_index)` ⇒ 改成跳过该日）。

> ⚠️ **回填判据必须是「当天有没有 `news_scores` 记录」，不是「值是不是 50」** ——
> 实测 `news_slot_count = 1` 的 28 行里有 **8 行 `news_index` 恰好是 50**，
> 那是**真实的 50 分**，按「值 == 50」一刀切会误伤。
>
> ⚠️ **已排除的方案**：把宽表里 `news_index = 50` 的行**一律置 NULL** ⇒ 同上，误伤 8 行真实分。

**✅ V0.121.1 落地结果**：源头改可空（模型 / schema / ETL / 补列 SQL 四处一致）+
宽表 ETL 不再继承快照的 `news_index` + `_set_outcome` 拆分（事实照写、判定缺方向不写）
+ 消费侧 `news_w > 0` 且 NULL 时跳过该日 + **幂等回填**（`scripts/backfill_news_truth.py`）。
生产库实测前后对比：快照 `news_index = 50` **57 → 8**（那 8 行是真实分，**全部保留**）、
`= NULL` **0 → 32**；宽表 slot=0 组 `news_index` 非 NULL **32 → 0**、
**hit_t0 / t1 / t5 非 NULL 14 / 14 / 12 → 0 / 0 / 0**（26 个伪造命中清零）；
二次规划 **0 行**（幂等）。

### A3 · `days` 参数完全失效 ⇒ 52W / 24M 按钮画的是 12 周 ✅（V0.121.1 已修）

**这是本清单最严重的一条**（一个字符的错误，解释了三个假象）。

**实测（2026-11-05，线上 `192.168.0.204:8888`）**：

```
/api/v1/market/gold/trend?days=30   → metrics.start_date=2026-09-24  points=30  index=39.5
/api/v1/market/gold/trend?days=60   → metrics.start_date=2026-09-24  points=30  index=39.5
/api/v1/market/gold/trend?days=120  → metrics.start_date=2026-09-24  points=30  index=39.5
```

**三个不同的请求返回完全相同的结果** —— `days` 根本没进计算。

**根因**：`src/app/services/cache.py:35` 的缓存 key 是
`(target, interval, on_date)` —— **没有 `days`**。
⇒ `?days=30` 先算完进缓存，后面 `?days=60` / `?days=120` **直接命中同一份缓存**。

**连带影响**：趋势页的「52W / 24M」按钮画的是 12 周 / 4 个月；
回测算不出收益率（价格日历取到的永远是 30 天）；价格回填只有 60 行。

**修法建议**：`days` 加进缓存 key（如 `(target, interval, on_date, days)`）。
⚠ 注意 `invalidate_cached_results()` 的失效逻辑要一起改，否则改完 key 会留下旧 key 的孤儿缓存。

> **落在 V0.121.1（批次 1）** —— 本清单第 1 优先级。
> **反向验证**：把 `days` 从 key 里去掉 ⇒ 必须复现「三个 days 返回相同结果」。

**✅ V0.121.1 落地结果**：`served_cache._key()` 加 `days` 维度
（`get_served` / `set_served` / `_entry_set_at` 同步），`invalidate` 仍按
`(target, interval)` 匹配 ⇒ 覆盖该 target 的**所有** days 变体（不留孤儿缓存）。
反向验证：monkeypatch 把 `_key` 换回 3 元组 ⇒ **3/3 变红** ⇒ 恢复 ⇒ 3/3 绿。

### A6 · AI 助手的 token 统计失真，页面上渲染成 `↓ 0` ✅（V0.121.2 已修）

**实测（2026-11-05）**：
- 客户端 `static/ask.js:860` 初始化 `inputTokens: 0`，**全文件没有任何一处给它赋值**

**语义混淆**：0 的意思是「**未知**（没拿到 usage）」，不是「用了 0 个 token」，
但落库和渲染都当成 0。

**修法建议**：① 客户端接 `message_stop` 的 `usage` 填进 `currentRound`；
② 服务端 `input_tokens` 改 `NULL` 表示未知；③ 前端把 0 一并视为「未取到」。

> **落在 V0.121.2（批次 2）**。补充实测（2026-11-06）：
> 服务端**确实在 `message_stop` 里发了 usage**（`service.py`），客户端**全文没有
> `message_start` 处理器**、`case 'message_stop'` **完全没读 `payload.usage`**
> ⇒ 修客户端即可让 **输出 token（实测 312，是真值）** 显示出来；
> 输入 token 仍是未知（miniMax 不发 `StreamMessageStart`）⇒ 语义上必须是 `NULL` 而不是 0。

**✅ V0.121.2 落地结果**（批次 2）—— 修的是**三层**，不是一层：

| 层 | 落地内容 |
|---|---|
| 客户端 | `message_stop` **先读 usage 再 commit**（顺序反了就挂不上）；初值改 `null`；`\|\| null` 改 `?? null`（0 是合法值，`\|\|` 会把它也吞掉） |

请求必带 system prompt + tools + 历史 ⇒ 真实输入 token **不可能为 0**
⇒ 代理的 0 其实是「**没数**」⇒ 判据定成「**字段缺失 或 值为 0 ⇒ 未知**」，

```
落库               = (input_tokens=NULL, output_tokens=1874)      ← 修复前是 0
```

### C7 · 新增：「共识度」要不要独立成一个可展示的维度 ⚪（待用户拍板）

用户在 V0.122.0 这一轮的框架里，把「资金的共识」提到了**投资价值**的高度。
现在它只体现为「资金流面」里的 6 个因子（COT 净多、ETF 申赎、美元流动性…），
**没有一个统一的「共识度」读数**。

**候选做法**：把「拥挤度」（COT 净多占 OI 的分位）+「一致性」
（各资金流因子方向是否同号）合成一个 **0~100 的共识分**，
在首页/趋势页单独展示（而不是藏在面分数里）。

**⚠ V0.123.0 已按 C4 的管线把候选读数全部测完**（5 个候选 × 2 个标的）：

| 候选读数 | GLD | 518880 |
|---|---|---|
| 方向共识（`consensus_dir`） | ❌ 不过② | ❌❌❌ |
| 一致程度（`consensus_agree`） | ❌❌❌ | ❌ 不过② |
| **面内离散度（`dispersion`）** | ❌❌❌ | ❌❌❌ |
| 拥挤度分位（`crowding_pctile`） | ❌❌❌ | ❌❌❌ |
| 拥挤度水平（`crowding_wmax`） | ❌❌❌ | ❌ 不过③ |

⇒ **没有一个候选读数在两个标的上同时过三问** ⇒ **「共识度」目前没有实测依据**。

**建议（不再是「待拍板」，而是「有依据的暂缓」）**：**先不新增维度**。
理由有三：① 候选读数全部不过线，做出来是**没有证据的展示位**；
② 唯一机械上过线的「拥挤度水平」本质是 `cot_gold_net` 的**水平代理**（同一个因子换个读法），
进表就是**重复计权**；③ 它的判决**随口径摆动**（口径调整前 ✅✅✅、调整后 ❌❌❌，n 仅 34~46）。

⚠ 若将来要重开这条，**判据不变**：先落观测 → 按 C4 的三问管线测 → **两个标的都过线**才进规则表；
「产品上想展示」不能替代「数据上站得住」。

## 七、本文件怎么用

1. **新问题写进来之前先实测复现** —— 没有复现判据的判断不写。
2. **状态字段只有三种**：`🔴 仍存在` / `🟡 部分` / `✅ 已修`（已修的挪进 §六，不要留在待办里）。
3. **每条带一条可复现命令**（本文件里的都是实测输出，可直接复制重跑）。
4. **修完一条就更新状态 + 挪进 §六** —— 免得半年后又出现「已修的还在待办里」。
5. **复核时重跑命令，不要相信上一轮写下的结论** —— §五 的 G3/G4 就是「写下时就已经不成立」的实例。
