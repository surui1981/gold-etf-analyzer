# V0.80.1 · prod 写端点自动附加 X-Admin-Token（hotfix）

**发布日期**：2026-10-08
**commit**：`56c040e`
**与上一版本对比**：V0.80.0（2026-10-07，`b13c7fa`）—— 间隔 1 天

## 〇 一页结论

**症状**：prod 部署下 news.html 保存打分直接 401 `admin token required`。
**根因**：V0.72.0 P3-b 上线的 `Depends(require_admin)` 守卫从未在客户端接上 —— 前端
几十处裸 fetch 都没传 `X-Admin-Token` 头，dev 模式 `ADMIN_TOKEN` 未设所以从来没暴露。
**修法**：复用 V0.75.0 已有的 CSRF 自动注入模式 —— auth.js 全局 fetch 打补丁，同源写请求
未带 `X-Admin-Token` 时自动从 localStorage 读 `pm_admin_token` 附加。

**单文件 / 单 commit / 51+/17-**，无 schema、无 i18n、无后端变动。

## 一、问题

### 现象

prod 部署（`APP_ENV=prod` + `.env.prod` 含 `ADMIN_TOKEN`）下，用户打开
`/static/news.html` 保存打分立即报：

```
POST /api/v1/news-score → 401 {"detail":"admin token required"}
```

dev 模式 `ADMIN_TOKEN` 不设 ⇒ `admin_auth.require_admin` 第 49 行直接 return
⇒ dev 永远看不到这个问题。**生产才暴露。**

### 涉及范围

`src/app/middleware/admin_auth.py` + `dependencies.get_admin_token`：env 有
`ADMIN_TOKEN` 时所有 `dependencies=[Depends(require_admin)]` 的写端点都拒绝 401。

排查全仓 grep，挂了守卫的路由：

| 路由 | 来源 |
|------|------|
| `PUT /api/v1/news-score` | V0.72.0 P3-b 同期 |
| `DELETE /api/v1/news-score/{slot}` | 同上 |
| `POST /api/v1/portfolio/*` | 多处（positions / accounts / transactions） |
| `PUT /api/v1/settings/*` | weights / cache / push |
| `POST /api/v1/backtest/*` | 异步回测 |
| `POST /api/v1/push/*` | 推送订阅 / 验证 |

⚠ 涉及**所有写端点**。不只是 news-score。但症状只在 news-score 上暴露，是因为
news.html 的 Save 是 prod 用户**每天都会点的**一个写操作。

---

## 二、根因

### V0.72.0 P3-b 上线时的设计遗漏

`require_admin` 设计意图清晰（`src/app/middleware/admin_auth.py:32-57`）：

- dev 模式无 `ADMIN_TOKEN` → 跳过校验（不打断本地开发）
- prod 模式有 `ADMIN_TOKEN` → 严格校验 `X-Admin-Token` 头

但**前端那头没接**：V0.72.0 当年只有**设置页 + auth 页**两个前端页面有显式写
调用，其余页面（news / portfolio / weights）当时还没有写操作 ⇒ 守卫落到了
**服务端后端无人调用**的位置。

V0.75.0 上线 news / portfolio 等十几个页面，且加了几十处裸 `fetch(...)` 调用，**没人
复查"是否带 admin 头"**。V0.80.0 把 `app_settings`（含 admin token）混合表列入了
遗留项，但**客户端自动附加头这个空缺没人接**。

### 为什么 CI 没拦住

`tests/conftest.py` 走的是 `:memory:` SQLite + `ADMIN_TOKEN` env **不设**
（dev 默认路径）⇒ `require_admin` 走 49 行 `return` 分支，**根本不会触发**
401 分支。**CI 永远不会验**这条 prod 路径。

## 三、修法

### 复用 V0.75.0 已有的 CSRF 自动注入模式

`static/auth.js:113-160 patchedFetch()` 已有结构：

```js
if (WRITE_METHODS[method] && sameOrigin(input)) {
  if (!hasHeader(init, CSRF_HEADER)) {
    var csrf = csrfToken();   // 从 pm_csrf cookie 读
    if (csrf) { init.headers[X-CSRF-Token] = csrf; }
  }
  // 👇 V0.80.1 加这段
  if (!hasHeader(init, ADMIN_TOKEN_HEADER)) {
    var adm = adminToken();   // 从 localStorage pm_admin_token 读
    if (adm) { init.headers[X-Admin-Token] = adm; }
  }
}
```

+ 新增 `adminToken()` helper（`static/auth.js:76-83`）：

```js
function adminToken() {
  try {
    var v = localStorage.getItem(ADMIN_TOKEN_KEY);   // "pm_admin_token"
    return v && String(v).trim() ? String(v).trim() : "";
  } catch (e) { return ""; }   // Safari 隐私模式 / cookie 禁用 → 视为未设
}
```

### 设计取舍

- **auth.js 而非 settings.js**：auth.js 是全站基座（每个页面都加载），
  settings.js 仅设置页加载。基座自治 ⇒ 无反向依赖。
- **不覆盖显式传入**：与 CSRF 一致，调用方自己 set 了 `X-Admin-Token` 就跳过。
- **dev 模式零干扰**：localStorage 读不到就不加头，dev 后端不强制要求。
- **三语 UI 不变**：纯 fetch 打补丁，零可见 UI 变化。
- **零后端变动**：服务端依赖、契约、数据库 schema 全不变。

### 用户操作

无需重新输。**前提条件**（已经在 V0.80.0 之前的设置页配过的）：用户在
`/static/settings.html` 已经把 admin token 填进「管理员令牌」输入框并保存过
（settings.js:24-34 LS_ADMIN 写入 localStorage）。

如从未填过：admin token / 不填（dev 不需要）或填后保存。

## 四、验证

### 静态门禁

| 门禁 | 结果 |
|------|------|
| `node -c static/auth.js` | syntax OK ✓ |
| `check_static_js.py` | 13 页 + 23 脚本全过 ✓ |

### 后端契约

`src/app/middleware/admin_auth.py:32-57` 的 `require_admin` 路径：
- `admin_token is None`（dev）→ return → 不强制
- `admin_token` 存在 + header 缺失/不匹配 → 401

修法**只动前端**：服务端逻辑零变动。

### 浏览器手测（puppeteer 实跑 —— **MEMORY 规则强制**）

1. 用 prod 配置启动 uvicorn（`APP_ENV=prod` + `.env.prod` 含 `ADMIN_TOKEN`）
2. 打开 `/static/settings.html` → 填 admin token → 保存 → 确认 localStorage 有 `pm_admin_token`
3. 打开 `/static/news.html` → 编辑打分 → 保存 → **不再 401**
4. DevTools Network 面板：PUT 请求 Headers 应含 `X-Admin-Token: <base64>`
5. 关闭设置（清除 localStorage `pm_admin_token`）→ 再保存打分 → 应回到 401
   （说明 token 来自 localStorage，不是写死）

⚠ step 3-5 是**唯一**能确认整条链路的手段（dev 模式 CI 拿不到这条路径）。
