# V0.116.3 · 命令面板自动聚焦被 V0.113.0 的无障碍修复顺手打没了

> 2026-10-25 · fix · 维护性发版 · 一个「无障碍修复 → 回归」的跨版本因果链

## 起因

V0.116.2 修的是「3 处静默失效的前端缺陷」。本轮继续往下挖，
在**移动端门禁** `scripts/_verify_mobile.mjs` 身上挖出一条线索：

> 那条「打开时搜索框自动聚焦」的断言，有时绿有时红 —— 同一个代码、同一个服务，
> 跑三次得到 33/0、32/1、33/0。

按门禁的常识，红了就是实现坏了。但这里**红不红和实现对不对无关**，
它红是因为**等待时间是个运气阈值**。把这条断言的时间轴摊开，
牵出了本轮的缺陷：一个**三个月前的无障碍修复，悄悄废掉了更早的一个功能**。

## 一、缺陷：命令面板打开了，但光标不在搜索框里

### 症状

按 `⌘K` / `Ctrl+K`（手机上点顶栏「⌘ 搜索」）打开命令面板 ——

- 面板**弹出来了**（可见、有内容、样式正常）
- 但**光标不在搜索框里**
- ⇒ **直接打字没反应**，必须先用鼠标点一下搜索框

### 根因：一条跨版本的因果链

| 版本 | 提交 | 做了什么 |
|---|---|---|
| V0.68.0 | `5d0d81c` | 命令面板打开后**自动聚焦**搜索框：`setTimeout(() => input.focus(), 30)` |
| V0.113.0 | `8f75b16` | 移动端无障碍整改：给 `.pm-cmd` 加 `visibility: hidden`，让**关闭态的面板真正退出 tab 序列**（WCAG 2.4.3 焦点顺序） |

V0.113.0 那次改动是对的 —— 它修掉了一个真实的无障碍缺陷
（`opacity: 0` 的元素**仍在 tab 序列里**，键盘用户一进页面 Tab 到的第一个东西
就是这个看不见的搜索框，还落在 sticky 顶栏底下，看着像「点不动」）。

但它给 `.pm-cmd` 加了 `visibility` **过渡**：

```css
.pm-cmd {
  visibility: hidden;
  transition: opacity .14s ease, transform .14s ease, visibility .14s ease;
}
body.pm-cmd-open .pm-cmd { ... visibility: visible; }
```

于是出现了三个事实叠在一起：

1. **`visibility: hidden` 的元素不能接收焦点** —— 浏览器会**静默丢弃** `focus()`
   （不抛异常、不打 console 警告）。
2. `visibility` 参与过渡 ⇒ 面板从 `hidden` 翻到 `visible` 需要**一帧**。
3. 旧实现写死 `setTimeout(..., 30)` ⇒ 这 30ms 和上面那一帧**赛跑**。

赛跑的结果是**看运气**的 ⇒ 面板偶尔开着但没焦点。

### 实测（`scripts/_diag_cmd_focus.mjs`，12 次 open/close）

| 实现 | 焦点落上去 | 落焦耗时 |
|---|---|---|
| 旧实现（固定 30ms） | **8/12** | 16–34ms |
| 本轮修复 | **12/12** | 16–77ms |

### 为什么「新建 DOM 的首次 open 100% 丢」

顺带纠正一个中间结论：`init()` 里已经调了 `buildDom()`
（`static/command-palette.js:481`）⇒ **面板 DOM 在页面加载时就建好了**，
不是 open 时才建。所以每一次 open 走的都是「已有元素 + visibility 过渡」这条路径，
**不存在**「首次 open 一定丢焦点」这回事。首帧时序一变，就丢；变不了，就不丢。

> 这条纠正很重要：正是「首次 open 必丢」这个错误前提，
> 让我一开始把判据建在了错误的方向上（见第二节）。

### 修法：等到**真的可见了**再聚焦

```js
function focusWhenVisible(panel) {
  if (!panel || !panel._input) return;
  var deadline = performance.now() + 2500;   // 时间截止，不是帧数
  function attempt() {
    if (!document.body.classList.contains('pm-cmd-open')) return;  // 已关就别抢
    if (getComputedStyle(panel).visibility === 'visible') {
      try { panel._input.focus(); } catch (e) { /* 静默 */ }
      if (document.activeElement === panel._input) return;         // 落上了
    }
    if (performance.now() < deadline) requestAnimationFrame(attempt);
  }
  requestAnimationFrame(attempt);
}
```

三个要点：

- **判据是计算样式，不是「等多少毫秒」** ⇒ 过渡快慢都正确。
- **重试到 `activeElement` 真的落上去**为止 ⇒ 不止试一次。
- **用时间截止（2.5s）而不是帧数（60 帧）** ⇒ 低帧率机器上 60 帧可能只有 300ms，
  遇上被人为拉长的过渡就会假红（实现没坏）。

## 二、门禁为什么是绿的 —— 以及我**第一版判据也是假绿**

这一节是本轮真正的收获：**判据本身也会骗人。**

### 2.1 原来的断言：固定 350ms 等待（flaky）

```js
await page.evaluate(async () => {
  window.PM_CmdPalette.open();
  await new Promise((r) => setTimeout(r, 350));   // ← 运气阈值
  const focused = document.activeElement === input;
});
```

350ms 是「.14s 过渡 + 一点余量」拍出来的数。**过渡慢一点就假红**，
过渡快一点就假绿 —— 它测的是**机器快慢**，不是**实现对错**。

### 2.2 第一版修法：改成 2000ms 轮询 —— **还是假绿**

把固定等待换成「轮询到有明确截止时间」：

```js
const deadline = performance.now() + 2000;
while (performance.now() < deadline) {
  if (document.activeElement === input) { focusable = true; break; }
  await new Promise((r) => setTimeout(r, 25));
}
```

这一版**逻辑上是对的**（实现坏了就实打实红到截止），但**实际不区分**：

> 旧实现那 30ms 的 `focus()` 是**看运气**的 —— 有一半以上的概率，
> 那一帧的 visibility 早就翻成 `visible` 了，`focus()` ** succeeds**，
> 于是轮询立刻抓到焦点 ⇒ 门禁绿。

**反向验证直接暴露了这点**：回退实现后，门禁连报两次「34 passed, 0 failed」。

### 2.3 第二版判据：`transition-duration` 拉长过渡 —— **方向就是错的**

我最初的思路是「把过渡拉长，让 30ms 必输」：

```js
await page.addStyleTag({ content: ".pm-cmd { transition-duration: 1500ms !important; }" });
```

**这个杠杆根本不起作用。** `visibility` 是**离散插值**：
过渡一旦开始，**第一帧**（progress > 0）就翻成 `visible` ——
加长 `duration` 只影响 opacity 淡入，**不影响「可见时刻」**。

实测（`scripts/_diag_cmd_focus3.mjs`）：

```
transition-duration = 1.5s
t=16ms  vis=hidden
t=29ms  vis=visible   ← 过渡才过了 1.3% 就已经翻成可见了
```

⇒ 「30ms 聚焦会不会被丢」这件事**根本没被改变** ⇒ 门禁还是绿的（假绿）。

### 2.4 第三版判据（落地版）：`transition-delay` —— **这才是对的杠杆**

`transition-delay` 期间，属性保持**起始值**（`hidden`），
于是「可见时刻」可以被推到**确定的** 400ms 之后：

```js
await page.addStyleTag({
  content: ".pm-cmd { transition: opacity .14s ease, transform .14s ease, visibility 0s ease 400ms !important; }",
});
```

于是：

| 实现 | 面板变可见 | `focus()` 发生在 | 结果 |
|---|---|---|---|
| 旧实现（固定 30ms） | t=413ms | t=30ms（此时还 hidden）⇒ **被静默丢弃** | **焦点永远落不上去 ⇒ 必红** |
| 本轮修复（等 visible） | t≈400ms | 可见后第一帧 ⇒ t=477ms | **必绿** |

**反向验证（真跑，不是推断）**：

```
### B. 回退实现（固定 30ms focus）⇒ 必须红
  ✗ 延迟可见时搜索框仍然自动聚焦（V0.113.0 引入的回归） {"focusedAt":null,"visibleAt":413}
  ✓ 判据自检：面板确实是延迟可见的（否则这条断言等于没测）
  结果：34 passed, 1 failed        ← 第 1 次
  结果：34 passed, 1 failed        ← 第 2 次（确定性）
### C. 恢复修复版
  ✓ 延迟可见时搜索框仍然自动聚焦（V0.113.0 引入的回归）
  结果：35 passed, 0 failed
```

> 注意还多了一条**自检断言**「判据自检：面板确实是延迟可见的」——
> 它保证「延迟」这个前提真的生效了（`visibleAt > 300ms`），
> 免得哪天 CSS 改了导致判据退化成「什么都没测」而门禁还是绿的。

`static/settings.js:341` 有形状一样的代码：

但它**不受影响**，理由两条（都查过，不是猜的）：

| 隐藏机制 | `visibility: hidden` + **过渡** | `hidden` 属性 ⇒ `display: none`（`theme.css:507`） |

## 六、教训

1. **`visibility: hidden` 的元素不能接收焦点，`focus()` 会被浏览器静默丢弃** ——
   不抛异常、不打日志。任何「先隐藏、后显示、再聚焦」的组合都要重新审视。

2. **无障碍修复不是「纯加法」**。V0.113.0 修的是真问题，但它改变了元素的
   **可见时刻**，而 V0.68.0 的自动聚焦**依赖**旧的可见时刻。
   跨版本的因果链只有把两边都翻出来才看得见。

3. **「等固定时间」和「轮询到截止」都可能是假绿** ——
   前者测机器快慢，后者若目标行为本身是概率性的就照样绿。
   **判据必须让目标行为变成确定性的**（这里是把「可见时刻」用 delay 钉死）。

4. **拉长 `duration` ≠ 推迟「可见时刻」**。`visibility` 是离散插值，
   第一帧就翻。**要推迟的是 delay，不是 duration** ——
   我在这个坑里绕了一轮，是靠逐毫秒采样才发现的。

5. **反向验证必须真的红**。第一版判据（duration）连跑两次都是
   「34 passed, 0 failed」——**门禁是绿的，但它什么都没保护**。
   这和 V0.116.2 修的那两处「绿着但什么都没保护」是同一个病根：
   **断言没被证伪过，就不算数**。
