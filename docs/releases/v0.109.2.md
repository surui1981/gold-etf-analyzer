# V0.109.2 · 白银页面数据时效透明化（SGE akshare 数据滞后 2 天暴露）

> 发版日期：2026-10-20
> 前置：V0.109.1（白银 3-market 页面重构）
> 性质：故障透明化 hotfix

## 一句话

白银 SGE akshare 接口 `spot_silver_benchmark_sge()` 在生产中常见滞后 2-3 个工作日，
原 `/silver/sge-quote` 接口只用历史 K 线末根日期当 `updated_at`，前端看不出来 stale，
用户连续刷新 cache（5 分钟过期）还是拿到同一日数据 → 误以为「缓存 2 天」。

实测 2026-10-20（周二）下午 20:22 BJT：

| 端点 | last_date | 距今 | 通路 |
|---|---|---|---|
| `/silver/quote` (NY SI) | 10-20 | 0 天 | sina_si 实时 |
| `/silver/etf-quote` (562800) | 10-19 | 1 天 | eastmoney 挂 → 降级 sina sz161226 lof_proxy |
| `/silver/sge-quote` (Ag99.99) | **10-18** | **2 天** | ak.spot_silver_benchmark_sge() 真源就是 10-18 |

---

## 核心漏洞

1. **`get_silver_sge_quote()` 用历史 K 线最后一行当「最新报价」**，但没把这个日期告诉前端，UI 只显示「13976 元/kg」数字，**用户看不见数据是哪天的**。
2. **没有任何 staleness 检测**：akshare 数据如果 3 天前 / 1 周前，系统照样当 live 显示，「数据源健康条」一直显示 ✅ 全 green。
3. **`renderSourceBar()`** 只统计 `data_sources` 里的 live/mock 计数（SGE 数据源 `sge_silver_history` 不在数据源统计里），所以问题源在 source-bar 完全不可见。

**不是 cache TTL 问题**（默认 `QUOTE_CACHE_TTL=300` = 5 分钟是合理的）。

---

## 改法

### `data_as_of` 字段：让前端知道数据是哪天的

```diff
 class SilverQuoteOut(BaseModel):
     symbol: str
     price_usd: float
     change_pct: float
     updated_at: datetime
+    data_as_of: date | None = Field(None, description="V0.109.2：数据真实所属交易日")
```

同样的字段加到 SilverEtfQuoteOut / SilverGramQuoteOut / SilverSgeQuoteOut。

**3 个效果**：
- 报价卡片下方显示「数据日期 2026-10-18」+ 滞告 chip
- 三市场报价统一携带语义位（不再是混用 `updated_at`）
- 客户端向后兼容（`None` 默认，老 JS 不会报错）

### 后端 staleness 检测

```python
@staticmethod
def _is_data_stale(last_date: date | None, *, max_lag_days: int = 1) -> bool:
    from app.utils.market_clock import trading_days_between
    return trading_days_between(last_date, date.today()) > max_lag_days
```

阈值 1 工作日的直觉：
- Sun(18) → Mon(19) = 1 trading day（跨周末挡路）→ **不**算 stale（正常）
- Sun(18) → Tue(20) = 2 trading days → **算** stale ← 本次故障的真实状态
- 工作日定义：周一至周五 5×24h（不区分 A 股节假日；SGE 与 A 股同日休市，对齐即可）

Stale 数据走 `_mark(ok=False)`，source-bar 看到 `mock` 状态 → 用户从主条就知道有问题。

### 前端 chip + source-bar 增强

`static/silver.js` 3 个卡片下方显示「数据日期 YYYY-MM-DD」+ 滞后 chip：

```
SGE 上海银 Ag99.99
13976.00 元/千克
+0.23%
数据日期 2026-10-18 ⚠ 数据滞后 2 天
```

`renderSourceBar()` 健康条尾部追加：

```
⚠️ 部分数据源时效滞后: SGE 上海银 Ag99.99 数据至 2026-10-18（滞后 2 天）
```

复用 freshness.js 的 `fsh-chip fsh-warn fsh-stale-chip` 样式 + 与 idxPendingChip 同模式。

## 不引入新数据源

`ak.spot_silver_benchmark_sge()` 滞后是上游 akshare 的问题（数据爬虫慢 / SGE 基准价发布节奏），加代理源风险大、收益小。透明化 + staleness fallback 报警 即足够。

akshare 数据源恢复后（典型场景：下周一前 SGE 周末基准价补齐），下次刷新页面 chip 自动消失，无需代码改动。

## 设计取舍

| 决策 | 理由 |
|---|---|
| **不引入新数据源** | akshare 滞后是上游问题；加代理源风险大 |
| **不调 cache TTL** | 300s 5min 是合理的；问题在 data-as-of 不透明 |
| **stale 阈值用 1 工作日**（非日历日）| 周末挡路算正常（Sun→Mon）；周二还没数据算 stale（直觉） |
| **前端 lag chip 用日历日** | 简化 UX；与后端 trading_days 略宽，但展示够用户理解 |
| **stale 时仍走真数据路径**（不切 mock）| 让用户看到真实价 + 滞告提示，假数据会误导决策 |
