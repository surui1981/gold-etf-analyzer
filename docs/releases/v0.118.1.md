# V0.118.1 · 宏观因子「末次落库」兜底层 + 手动校准页降级可见

> **发版日期**：2026-10-26 ｜ **类型**：bugfix ｜ **上一版**：[V0.118.0](v0.118.0.md)
>
> **一句话**：V0.118.0 给 8 个宏观因子都接上了实时源，但**兜底层没跟着换** ——
> 上游源一挂，宏观面就静默退回 2026-08-28 的内置常量，而历史表里明明存着前几轮
> 抓到的真值。用户在权重页「宏观因子手动校准」的「当前生效」列看到的是两个半月前的
> 数字，且**没有任何降级提示**。

---

## 一、问题

### 1.1 现象

线上权重页「宏观因子手动校准」卡的「当前生效」列显示：

| 因子 | 显示值 | 数据日期 | 源标识 |
|------|--------|----------|--------|
| 美元指数 | 96.5 点位 | **2026-08-28** | 静态参考值 |
| VIX 恐慌指数 | 18.5 点位 | **2026-08-28** | 静态参考值 |
| 美债 10Y 收益率 | 4.40 % | **2026-08-28** | 静态参考值 |
| …（其余 4 个市场因子同样） | | | |

而**同一时刻**应用自己抓到的真值是（`daily_macro_factors` 表，2026-10-25 23:00 落库）：

| 因子 | 真值 | 数据日期 | 源 |
|------|------|----------|-----|
| 美元指数 | **101.81** | 2026-10-23 | Yahoo `DX-Y.NYB` |
| VIX | **19.03** | 2026-10-22 | FRED `VIXCLS` |
| 美债 2Y / 10Y / 30Y | 4.65 / 4.96 / 5.29 | 2026-10-22 | 美联储 H.15 |
| 10Y 实际利率 | 2.64 | 2026-10-22 | FRED `DFII10` |

**美元指数差了 5.3 个点**（96.5 vs 101.81），且落在 `dxy` 的 best/worst 区间
（94 / 107）内 —— 足以改变因子的黄金友好度评分，进而改变综合指数。

### 1.2 触发条件

上游源不可用。V0.118.0 发版当天实测到的具体故障是**本机 DNS 解析不了境外域名**：

```
$ dig @192.168.0.1 fred.stlouisfed.org
;; communications error to 192.168.0.1#53: timed out

$ getent hosts query1.finance.yahoo.com   → 空
$ getent hosts hq.sinajs.cn                → 2400:89c0:1053:4::21:147   （国内域名正常）
```

路由器只能解析国内域名，境外域名（Yahoo / FRED / 美联储）一律超时；
直连 8.8.8.8 / 1.1.1.1 / 223.5.5.5 的 53 端口也全被拦。**这是间歇性的** ——
同日 09:27 服务重启时源仍不可用，09:27 源恢复，宏观指数在两次请求间从
「末次落库」切回「实时」。

3 个宏观自动源**全部**是境外域名 ⇒ 一次 DNS 抖动就让 7 个市场因子同时失去实时源。

### 1.3 为什么是 bug 而不是「本来就这样」

V0.110.0 专门为这件事做过设计：当时 `dxy` / `vix` 没有自动源，长期停在
`STATIC_REF` 的常量上，**综合指数的 16% 建立在两个半月前的常量上** ——
「宏观因子手动校准」这个功能就是为了让用户能手工顶替掉那两个常量而生的。

V0.118.0 把 8 个因子都接上了实时源，**但兜底层仍然是同一批常量**。
于是任何一次上游抖动都会把系统原样打回 V0.110.0 要解决的问题 ——
而且这次是**静默**的：页面上不显示任何降级标记，用户无从判断那个 96.5
是「今天的读数」还是「两个半月前的化石」。

### 1.4 顺带发现：滞后提示只对手动值生效

`static/weights.html` 的滞后 chip 条件是 `cur.source === "手动输入"` ——
**只有手动录入的值**才会提示滞后。自动源退回常量（滞后 59 天）时，
页面上一个警告都没有。

## 二、修法

### 2.1 后端：在自动源与常量之间插入「末次落库」层

新的优先级链：

```
用户手动覆盖 > 自动数据源 > 【末次落库的真实读数】> STATIC_REF 内置常量
```

「末次落库」= `daily_macro_factors` 表里每个因子**最近一条**落库记录
（新增 `MacroFactorHistoryRepository.get_latest_per_factor()`）。
它是**真实市场读数**，只是属于过去某一刻。

| 场景 | 修前 | 修后 |
|------|------|------|
| 源正常 | 实时值 | 实时值（不变） |
| 源不可用 | 96.5（2026-08-28 内置常量） | **101.81（2026-10-23 末次落库）** |
| 全新部署（历史表空） | 96.5 | 96.5（不变，无历史可退） |
| 手动覆盖 | 手动值 | 手动值（不变，优先级最高） |

### 2.2 降级必须**可辨认**（否则等于没修）

- **source 前缀**：降级值的 source 变成 `末次落库·<原源>`
  （如 `末次落库·FRED VIXCLS`），前端据此挂琥珀色 chip；
- **API 新增 `tier` 字段**：`MacroFactorOut.tier` ∈ `live` / `lkg` / `static`。
  前端**不靠匹配中文前缀**判断降级 —— 那种做法一改文案就失效；
- **降级值不再落表**：`is_persistable_source()` 排除 `末次落库` 前缀。
  旧读数写进今天的 `snapshot_date` 等于谎报观测时间，会把滚动分位窗口压平
  （这正是 V0.79.0 静态值不落表要防的事）。

**三处消费降级信号的地方，一处都不能漏**（本次补上了第 3 处）：

| 消费方 | 表现 | 本次 |
|--------|------|------|
| 权重页「当前生效」列 | 挂「降级·末次读数」/「内置常量」chip | V0.118.1 新增 |
| 综合卡「数据质量」提示 | 报出降级因子的数量 / 名称 / 最新数据日 | V0.118.1 新增（原先只认 `静态参考值` 一档） |
| 落表策略 | 降级值不写进 `daily_macro_factors` | V0.118.1 新增 |

> 综合卡那处原先判据是 `source.indexOf('静态参考值')`，**新增的 `lkg` 档完全
> 不会触发它** —— 用了旧真值这种降级对用户不可见，正好违背该卡「不夸大可信度」
> 的立意。现在判据优先用 `tier` 字段（tier 缺失时才退回匹配 source 字面量）。

### 2.3 派生因子 `curve_10y2y` 的规则

利差 = 生效后的 10Y − 2Y。两个输入的**层级取更弱的一档**：

| 两个输入 | 利差 source | 可落表 |
|----------|-------------|--------|
| 都 live | `派生 10Y-2Y` | ✅ |
| 掺了末次落库 | `末次落库·派生 10Y-2Y` | ❌（混了不同日期的读数） |
| 掺了静态常量 | `静态参考值` | ❌（不是市场读数） |

另外：历史表里若已有末次落库的利差，而 10Y/2Y 退化成常量，**不会**用更弱的
静态派生值把它盖掉（降级方向不能反着来）。

### 2.4 前端：滞后提示对**所有**源生效 + 降级 chip

- 滞后 chip 不再只给手动值：自动源读数滞后 > 4 个日历日即提示
  （4 天 = 跨一个长周末仍不提示）；
- 手动值维持 > 1 天即提示（那是用户自己抄的数，该提醒刷新）；
- `tier=lkg` → 挂「降级·末次读数」chip；`tier=static` → 挂「内置常量」chip。

## 三、顺带修掉的一个真 bug：`/ask` 的 `get_market_overview` 工具**每次调用都失败**

`src/app/main.py` 构造 `TrendService` 时，第 2 个位置参数（`macro`）误传了
第二个 `MarketDataRepository`：

```python
trend_svc = TrendService(
    MarketDataRepository(tool_sess), MarketDataRepository(tool_sess)   # ← 第 2 个是 macro
)
```

`TrendService.analyze()` 会 `await self._macro.evaluate()` ⇒
`AttributeError: 'MarketDataRepository' object has no attribute 'evaluate'`。
异常被 tool 层兜住并回成一条 error 结果 ⇒ 页面上表现为「工具没给出数据」，
**没有日志告警、没有 500**。

`/api/v1/ai/health` 显示 5 个工具已启用（`enabled=true`），所以这是**线上活跃路径**。

修法：注入真正的 `MacroFactorService`（含央行购金 + 滚动分位 + 末次落库兜底），
与另外两处构造点口径一致。

## 六、遗留（不属于本次范围）

**本机 DNS 解析不了境外域名**（路由器 192.168.0.1 只解析国内域名，
直连 8.8.8.8 / 1.1.1.1 / 223.5.5.5 的 53 端口全被拦），且**间歇性发生**。
这不是应用缺陷，但会让 3 个宏观自动源 + 若干外部源同时不可用。

本次的兜底层正是为这种「源会挂」的现实准备的；DNS 本身要动路由器或
换 DNS 服务器，属于环境配置，不在应用内解决。

## 七、教训

1. **「加了实时源」不等于「实时源是唯一口径」** —— 兜底层才是决定「源挂掉时
   系统说什么」的那一层。V0.118.0 换了 4 个源，却把兜底留在 2.5 个月前的常量上。
2. **降级必须可辨认** —— 一个「看起来是当前读数」的陈旧值，比一个明显的
   错误值更危险。source 前缀 + API `tier` 字段 + 前端 chip，三件套缺一不可。
   而且**每一处消费降级信号的地方都要一起改** —— 本次就漏了综合卡的
   「数据质量」提示（它只认 `静态参考值` 一档），新加的 `lkg` 档对它完全隐形。
3. **提示的触发条件要覆盖所有路径** —— 滞后 chip 只对手动值生效，
   自动源的 59 天陈旧读数反而一个警告都没有。
4. **位置参数是最容易错的一处** —— `TrendService(repo, macro, ...)` 的第 2 位
   传成了 `MarketDataRepository`，异常被 tool 层兜住 ⇒ 线上工具每次都失败
   却没有任何告警。构造点少用位置参数。
5. **新门禁要反向验证** —— `_verify_synthesis_quality.mjs` 写完后撤掉被测
   改动跑一遍，确认它真的变红（本次：5 passed / 2 failed / exit 1）。
   「一直绿的断言」和「有效的断言」不是一回事。
