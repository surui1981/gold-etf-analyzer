### 2. 优质源因摘要为空被误杀

readhub 上财经垂直源经常给空摘要。这类条目正文关键词命中不了，V0.107.1
的 classify 判「其他」→ 被 fetcher 弃入。**站名本身**就是最可靠的类目信号，
但 V0.107.1 之前只有 8 个站名进了词典。

## 方案 B 的落地形态

用户说的「方案 B = 站点白名单」，实际拆成**两条腿**，因为纯白名单会误杀
readhub 新增的优质源（readhub 来源在轮换，31 个源里不少是新面孔）：

### 正向腿 —— 白名单站名写入关键词词典（C2）

复用现有 classify 通路，**零新增逻辑**：把 33 个优质源的站名直接写进对应
的关键词元组。站名即信号，摘要为空也能稳定归类。

```
财经 +9   第一财经 金融界 同花顺财经 界面新闻 中国证券报
          上海证券报 证券时报 经济观察报 每日经济新闻
科技 +16  IT 之家 IT之家 快科技 C114 钛媒体 品玩 爱范儿 机器之心
          雷峰网 techradar zdnet 9to5Mac theblockbeats
          techflowpost 蓝点网 infoq
创投 +7   36Kr 创业邦 投资界 铅笔道 IT桔子 IT 桔子
```

「IT 之家 / IT之家」「IT桔子 / IT 桔子」两种写法都收 —— readhub 的
`siteName` 空格不统一。

### 负向腿 —— 聚合噪声源硬删（C1）

```python
SITE_BLOCKLIST = frozenset({"新浪科技", "maomu.com"})
```

**收录纪律**（三条全满足才进黑名单，写进代码注释防止以后凭印象扩大）：
1. 30 天窗口样本量 ≥ 10 条（样本少的交给 classify 兜底）
2. 抽样 ≥5 条里与 4 类无关的比例 ≥ 60%
3. 不是任何优质垂直媒体的转载源

`_normalize` 在 `classify()` **之前**拦 —— 新浪科技这类聚合源即使单条内容
碰巧能分类（ETF 题材）也不进 4 类流。

### 刻意**不**拉黑的

初版名单里我一度把澎湃新闻也列进黑名单，拉数据时**实测推翻了**：

```
澎湃新闻 (3 条)
  [财经] 首批 136 项标志性重大应用场景项目清单发布，涉及新技术 1700 余项
  [科技] 研究实现量子网络跨节点、散粒噪声极限相位锁定
  [科技] 当创新踩下油门，社会如何减震？
```

3 条全优质，已从名单撤除，并写成断言钉住（防止以后有人凭印象加回去）。
techradar / 9to5Mac 同理保留 —— 有广告促销内容，但主体是有效科技新闻。

## 防御层

V0.107.1 已有的两层 gate 保留，V0.108.0 在两层上各加一个条件：

```
L1  fetcher._normalize   category ∈ {财经,科技,创投,商业}
                          AND site_name ∉ SITE_BLOCKLIST
L2  service.refresh()    同上（复用同一段 tuple 过滤，不新增分支）
L3  news_feed_daily      按日聚合表（不动）
```

L2 的存在意义：模拟「fetcher 的黑名单检查被漏改」，service 仍能拦住
（已有单测覆盖）。

## 已知问题（本次不修，留 V0.109）

### 1. `_BIZ_KW` 的「发布」过泛

「俄罗斯称袭击乌克兰敖德萨地区四艘货船」被判**商业** —— 因为摘要里出现了
「发布」。这是关键词精度问题不是站点问题（新浪科技已进黑名单，但同题材可能
从其他源进来）。

修法方向：给 `_BIZ_KW` 加**负向黑名单**（战争 / 冲突 / 事故 / 灾害 等
灾害类词出现时不判商业），或把「发布」限定为「发布会 / 发布新品」。

### 2. `tests/test_api/test_news_feed.py::test_list_items_filter_days` 已失败

**与本次改动无关** —— 该用例硬编码 10-17 / 10-18 / 10-19 三个 seed 日期，
今天是 10-20，`days=1` 的 cutoff 已把它们全排除。在干净的 HEAD 上
（`git stash` 验证）同样失败。属日期轮转导致的 pre-existing 失败。
