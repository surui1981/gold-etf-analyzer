## 〇 一页结论

**症状**：在 `/ask` 智能分析页使用对话功能，打开一个**用过工具的对话** ⇒ 前端弹
「加载对话失败：Internal Server Error」。**整个对话打不开**，不是只坏一条消息。

**根因**：`ai_messages.tool_input` 列存的是 **JSON 字符串**（`json.dumps(...)`），
而 `AIMessageOut.tool_input` 对外声明是 **dict**。`from_attributes=True` 会把 ORM
的**原始字符串属性**直接喂给 dict 校验 ⇒ Pydantic `ValidationError` ⇒ **整个响应 500**。

**修法**：在 schema 边界加一个 `mode="before"` 的解码器（**落库侧是对的，错的是接口边界没解码**），
与 `SnapshotOut.macro_detail` 完全同类，照抄它的做法。

**为什么 2007 条测试全绿**：mock LLM 的 tool_use 入参是**空 dict `{}`** ⇒
`repositories/ai_chat.py` 的 `if tool_input else None` 把它判成 falsy ⇒ 落库 NULL ⇒
校验通过。**真实 LLM 传的是非空入参**（实测 `get_scoring_summary({"from": ..., "to": ...})`）
⇒ 才炸。**空入参把真缺陷藏住了。**

## 一、问题

### 现象（用户报）

```
加载对话失败：Internal Server Error
```

出现在 `/ask` 页加载历史对话时。前端只拿到一句 500，看不出是哪条消息、哪个字段出的问题。

### 服务端日志（真相在这一行）

```
pydantic_core._pydantic_core.ValidationError: 1 validation error for AIMessageOut
tool_input
  Input should be a valid dictionary [type=dict_type,
  input_value='{"from": "2025-09-01", "to": "2026-03-29"}', input_type=str]
```

### 缺陷链（3 处代码，2 个方向不一致）

| # | 位置 | 事实 |
|---|---|---|
| 1 | `src/app/repositories/ai_chat.py:172` | 落库：`tool_input=json.dumps(tool_input, ensure_ascii=False) if tool_input else None` ⇒ 存的是**字符串** |
| 2 | `src/app/models/ai_chat.py:148` | 列定义：`Mapped[str \| None] = mapped_column(Text, ...)` ⇒ 存储层**自洽**（JSON 字符串） |
| 3 | `src/app/schemas/ai_chat.py:65` | 对外契约：`tool_input: dict[str, Any] \| None = None` ⇒ 与存储层**不一致** |
| 4 | `src/app/api/v1/endpoints/ai.py:144` | `AIMessageOut.model_validate(m)`（`from_attributes=True`）⇒ 原始字符串进 dict 校验 ⇒ **ValidationError ⇒ 500** |

**落库侧是对的，错的是接口边界没解码。** 这与 `SnapshotOut.macro_detail`
（同样是 Text JSON 列、同样对外声明 dict）完全同类，而**那个 schema 早就有解码器** ——
说明「Text JSON 列」在本项目里是**已知模式**，只是这次漏了一处。

### 为什么是「整个对话打不开」，而不是「一条消息坏掉」

`GET /conversations/{id}` 一次性返回该对话的**全部**消息（`ai.py:144`），
其中**任意一条** `tool_use` 消息的 `tool_input` 是字符串 ⇒ 整个列表序列化失败 ⇒ 500。
⇒ **一个坏字段 = 整个对话不可用**。这也解释了为什么用户感觉「AI 功能整个坏了」，
而实际上只有含工具调用的对话受影响。

### 受影响的两条路径（不止一条）

| 端点 | 位置 | 是否受影响 |
|---|---|---|
| `GET /api/v1/ai/conversations/{id}` | `ai.py:144` | ❌ **500** ← 用户报的就是这条 |
| `POST /api/v1/ai/conversations/{id}/messages`（同步回退） | `ai.py:221-222` | ❌ **500** ← 前端 SSE 降级时的回退路径 |
| `POST .../messages/stream`（SSE） | — | ✅ 不受影响（SSE 走 `tool_input` 事件流，不经 `AIMessageOut`） |

### 为什么测试没抓到

```python
# tests/test_api/test_ai_chat_endpoints.py::mock_llm_tool_use
tool_call = ToolCall(id="tc-001", name="get_market_overview", input={})   # ← 空 dict
```

```python
# src/app/repositories/ai_chat.py:172
tool_input=json.dumps(tool_input, ensure_ascii=False) if tool_input else None
#                                                              ↑ 空 dict 是 falsy ⇒ 落库 NULL
```

⇒ **空 dict → 落库 NULL → 校验通过 → 用例绿。** 而真实 LLM 传非空入参
（实测 `get_scoring_summary({"from": "2025-09-01", "to": "2026-03-29"})`）
⇒ 存成 JSON 字符串 ⇒ 才炸。

⚠ `grep -rn "tool_input" tests/` 修复前返回 **0 行** —— 该字段**零覆盖**。

## 二、修法

### 改哪一层：schema 边界（不是落库层，不是数据库迁移）

| 备选 | 判断 |
|---|---|
| **schema 边界加解码器** | ✅ **采纳**。列设计本身是对的（Text + JSON 字符串，SQLite 无 JSON 列类型）；一处解码器覆盖 `AIMessageOut` 的**全部 3 个调用点**；历史行与脏数据自动降级 |
| 改落库层存 dict | ❌ Text 列存 dict 只能存 `str(dict)`（Python repr，**不是合法 JSON**）⇒ 反而更坏 |
| 加数据库迁移改列类型 | ❌ 收益为零（SQLite 无 JSON 类型）、风险高（要重写历史行）、且**接口边界该做的事不该推给存储** |

### 代码

```python
# src/app/schemas/ai_chat.py
@field_validator("tool_input", mode="before")
@classmethod
def _parse_tool_input(cls, v: Any) -> dict[str, Any] | None:
    if v is None:
        return None
    if isinstance(v, dict):
        return v
    if isinstance(v, str):
        try:
            parsed = json.loads(v)
            if isinstance(parsed, dict):
                return parsed
            logger.warning("AIMessageOut.tool_input 顶层非 dict（%s）→ 置 None", type(parsed).__name__)
            return None
        except (json.JSONDecodeError, ValueError):
            logger.warning("AIMessageOut.tool_input JSON 反序列化失败 → 置 None")
            return None
    logger.warning("AIMessageOut.tool_input 收到非预期类型 %s → 置 None", type(v).__name__)
    return None
```

### 三条设计纪律（与 `snapshot.py::_parse_macro_detail` 对齐）

1. **坏 JSON → 置 `None` + log warning，不抛异常**
   ⇒ 一个坏字段不该让整个对话打不开。
2. **不兜底为 `{}`**
   ⇒ 数据不足 ≠ 中性。空对象会被前端 `summarizeInput` 当成「工具没带参数」渲染，
   是**另一种假数据**（与 `fallback-masks-missing-data` 同源）。
3. **顶层不是 dict（JSON 数组/数字）也置 `None`**
   ⇒ 契约是 `dict[str, Any]`，不是「能解析就行的 JSON」。

### 前端契约确认（修完为什么能用）

`static/ask.js::summarizeInput(tool, input)` 按 **`input.from` / `input.to` / `input.days`** 取值：

```js
if (tool === 'get_scoring_summary') return (input.from || '?') + ' → ' + (input.to || '?');
if (tool === 'get_etf_recent_flows') return '近 ' + (input.days || 30) + ' 天';
```

⇒ **对外必须是对象**。此前 SSE 流式路径已经是对象（`currentRound.toolInput = JSON.parse(...)`），
**只有 GET 路径是字符串** ⇒ 修完两条路径形状一致，前端无需改动。

### 同类缺陷排查（全库扫描）

本项目共有 4 个 Text 列，其中：

| 列 | schema 声明 | 是否有解码器 |
|---|---|---|
| `ai_messages.tool_input` | `dict[str, Any] \| None` | ✅ **本次补上** |
| `daily_snapshots.macro_detail` | `dict[str, Any] \| None` | ✅ 早就有（V0.79.0 起） |

## 四、迁移与回滚

### 无需迁移

- **零数据库变更**（不新增表/列/索引，不改历史行）
- **零接口契约变更**：响应体形状**本来就是前端期待的**（对象）；修的是「后端一直没兑现契约」
- **零配置变更**
- ⚠ **唯一的行为变化**：`tool_input` 从「请求体字符串」变成「请求体对象」 ——
  但这是**修回契约**，不是改契约（前端从 V0.97.0 起就按对象写）

### 回滚

```bash
git revert <v0.120.2 修复 commit>
```

回滚后回到 V0.120.1 行为：**含工具调用的对话重新打不开**（500）。

## 五、遗留

| 项 | 说明 |
|---|---|
| **历史脏数据仍是 `None`** | 若库里存在 `tool_input` 不是合法 JSON 的行，修复后该字段显示为空（前端不显示入参摘要），**但对话能打开**。实测生产库 175 条 `ai_messages` 中**仅 1 条**含非空入参（即触发 500 的那条），无其它脏数据 |
| **`ai_messages.tool_input` 零历史覆盖** | 本次补的 2 条用例覆盖「非空入参」与「脏 JSON」两条路径；`tool_input` 的其余分支（顶层非 dict、NULL）走的是同一段代码，未单独开用例 |
| **前端未改动** | 修完后 `/ask` 页的「工具入参摘要」终于能显示（此前因 500 从未渲染过）；SSE 与 GET 两条路径形状现已一致 |
| **`repositories/ai_chat.py` 的 `if tool_input else None` 未改** | 空 dict 落库成 NULL 是**既有语义**（无入参 ⇒ 不存），改动它会波及历史行为；schema 侧已能同时处理 NULL 与字符串两种情况，故不动 |
