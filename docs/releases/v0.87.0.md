## 三类改动

### 1. 修 broken link test（方案 A · 文档侧最小侵入）

**`docs/releases/v0.83.2.md`** line 53 的 inline code
`` `r'i18n:\s*["\']([A-Za-z0-9_.\-]+)["\']'` `` 在 `scripts/check_links.py` 的
`LINK_RE` 下被误识别为 markdown 链接（`["\']([A-Za-z0-9_.\-]+)` 这串字符
凑出 `[…](…)` 模式），触发 `test_repo_docs_have_no_broken_links`
「链接目标不存在」。

修复：把 inline code 换成 fenced code block + 去掉 capture group 括号，
LINK_RE 不再匹配，断言恢复绿。

**为什么选方案 A 不选方案 B**：
- 方案 B（改 `check_links.py` 在 `_link_targets` 里先剥离 inline code）会改
  基础设施，引入跨测试的回归风险；
- 方案 A 改动局限在 release notes 文本里，零代码层风险；
- 同时释放了一段对未来有指导价值的注释（原 V0.83.2 link-true-positive
  在 V0.86.1 hotfix 时的勘误）。

**`tests/test_dependencies/test_main_app.py`**（新建）

**测试矩阵（27 用例 · 6 个 group）**：

|---|---|---|

`Task was destroyed but it is pending!` 与 `ValueError: I/O operation on closed file`。
这是 V0.79.0 Step G 已记录的副作用（task 在 loop 关闭时被丢弃），不在本次修复。

## 教训

1. **覆盖率 baseline 必须每次升级前重跑**：V0.86.1 误以为「前次跑过就行」，
   实际新增 `main.py` alias 后覆盖率会回退；本次 baseline 是 V0.86.1 真实状态
   的 84%（不是 V0.85 的 87%），重新测量后才能识别低洼。
2. **inline code 含 regex 字面量是高风险**：markdown 链接 regex 看似只匹配
   `[text](url)`，但 `["\']([A-Za-z0-9_.\-]+)` 这种字符串里的字符类配合
   半角 `()` 就会触发误报。**写 release notes 时含 regex 字面量必须用 fenced
   code block，不能 inline code**——已写进 commit 注释作为经验。
3. **新增 alias 必须同步更新 3 处**：main.py `@app.get` + 测试断言 +
   docs/roadmap §4 别名清单；任何一处遗漏都会导致「页面存在但 404」或
   「测试通过但路由不存在」的诡异状态。V0.85 漏注册 `/data-health` 教训
   必须固化为测试断言（已在 `test_root_alias_count_matches` 实现）。
