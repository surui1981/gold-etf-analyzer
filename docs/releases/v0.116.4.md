# V0.116.4 · 命令面板「输入决策」落到趋势追踪 —— 场景落地页被第一个子页顶掉了

> 2026-10-25 · fix · 维护性发版 · 一处「同一个入口四种落点」的不一致

## 起因

用户反馈：**「点击决策的时候看到的页面是趋势追踪」**。

第一反应是「顶栏的决策点错了」—— 但实测不是。逐个入口查过去，
**顶栏、首页场景卡、手机抽屉三处「决策」一直都指向 `/scoring`（打分汇总）**，
只有**命令面板**这一处会落到趋势页。

于是先做了件事：**别信代码，去实测每个入口**。
`scripts/_diag_decision_nav.mjs` 扫了 17 个页面上所有文案含「决策」的
链接/按钮（共 60+ 个），逐个记 href：

```
/static/scoring.html    <a data-scene="decision"> "📊 决策"  href="/scoring"
/static/portfolio.html  <a data-subtab="nav.portfolio"> "💼 持仓与决策"  href="/portfolio"
...
```

全部指向 `/scoring`。**全站没有任何一个「决策」链接指向 trend。**

那用户点到的是哪？往下查了一层 —— 命令面板。

---

## 一、缺陷：面板里输入「决策」，第一条命中的是「趋势追踪」

### 实测（`scripts/_diag_palette_decision.mjs`）

面板输入「决策」后列出的 5 条：

```
0. ▶选中 📈 趋势追踪   /static/trend.html     ← 默认选中
1.        🎯 打分汇总   /scoring
2.        🧪 参数回测   /static/backtest.html
3.        🔍 研判复盘   /review
4.        💼 持仓与决策 /portfolio

回车后 URL = http://192.168.0.204:8888/static/trend.html   ← 落到趋势追踪
```

面板的默认选中项是**第一条命中**的行（`filter()` 里 `panel._active = 0`），
所以「输入决策 → 回车」= 趋势追踪。

### 根因：组内排序把「场景落地页」顶掉了

命令面板的清单是**从 `topnav.js` 导出的 `SCENES` 惰性派生**的
（V0.112.0 起，命令面板与顶栏同源）。派生时组内先铺子页：

```js
for (var j = 0; j < subs.length; j++) { rows.push({...子页}); }

// 场景自身入口：仅当没有被任何子页覆盖时才单独成条
var covered = false;
for (var k = 0; k < subs.length; k++) {
  if (subs[k].path === sc.path) { covered = true; break; }
}
if (!covered) { rows.push({...场景自身}); }
```

「决策」场景的 `path` 是 `/scoring`，而它的 4 个子页是：

| 子页 | path | 与场景 path 同？ |
|---|---|---|
| 趋势追踪 | `/static/trend.html` | 否 |
| **打分汇总** | **`/scoring`** | **是** |
| 参数回测 | `/static/backtest.html` | 否 |
| 研判复盘 | `/review` | 否 |

⇒ 场景自身那条被**去重逻辑吃掉了**（`covered = true`），
组内剩下的是「趋势追踪 / 打分汇总 / 参数回测 / 研判复盘」——
**落地页（打分汇总）排在第 2 位**，第 1 位是趋势追踪。

而面板的过滤是 `label + hint + section` 匹配，**组内 4 条全都命中「决策」**
（`section` 就是场景名）⇒ 第一条命中 = 趋势追踪 ⇒ 回车落到趋势页。

> 去重逻辑本身是对的（V0.111.1 起 4 个带子页的场景 path 都恰好等于某个子页 path，
> 不去重就会出现两条一模一样的 /scoring）。**错的是排序**：去重之后，
> 落地页应该被**提到组首**，而不是留在原来的第 2 位。

### 修法：场景落地页排组首

```js
var landingIdx = -1;
for (var k = 0; k < subs.length; k++) {
  if (subs[k].path === sc.path) { landingIdx = k; break; }
}
if (landingIdx >= 0) {
  rows.unshift(rows.splice(landingIdx, 1)[0]);   // 落地页提到组首
} else {
  rows.unshift({ ...场景自身 });                  // 没有同 path 子页 ⇒ 场景自身排组首
}
```

效果：**「输入场景名 → 回车」与「点顶栏场景入口 / 首页场景卡 / 手机抽屉」落到同一个页面。**

| 入口 | 修复前 | 修复后 |
|---|---|---|
| 顶栏「决策」 | `/scoring` | `/scoring`（一直是对的） |
| 首页场景卡「决策」 | `/scoring` | `/scoring`（一直是对的） |
| 手机抽屉「决策」 | `/scoring` | `/scoring`（一直是对的） |
| **命令面板输入「决策」** | **`/static/trend.html`** | **`/scoring`** ✅ |

## 二、门禁加固：一条**通用**断言，8 个场景全受约束

新增 `scripts/_verify_cmd_palette.mjs` 的【2b】段：

```js
for (const sc of SCENES) {
  // 检索词用**面板里实际渲染出来的组名**，不用 SCENES[i].fb
  const kw = secs[i];
  // 输入场景名 → 第一条命中的 hint 必须 === 场景的落地页 path
  ok(`输入「${kw}」第一条 = 落地页 ${sc.path}`, res.hint === sc.path, ...);
}
```

**为什么写成通用循环而不是给「决策」单写一条**：
新增场景时自动受约束 —— 否则下一次加场景又会有人把子页铺在落地页前面。

> ⚠ 检索词用**渲染出来的组名**（`secs[i]`）而不是 `SCENES[i].fb`：
> `fb` 只是 i18n 缺失时的兜底文案，与真实标签可能不同 ——
> AI 场景 `fb = "AI 智能分析"`，而 zh-CN 的 `nav.ask = "智能分析"`
> ⇒ 用 `fb` 检索**一条都匹配不到**（实测 0 条），断言会以「null」的形式假红。
> 这条坑是门禁写完后第一次跑就撞上的，改用渲染组名后 8/8 通过。

**反向验证**（回退实现，不是改期望值）：

```
### 回退「落地页提组首」⇒ 必须红
  ✗ 输入「决策」第一条 = 落地页 /scoring  实际「📈 趋势追踪」→ /static/trend.html
  ✓ 其余 7 个场景仍绿（它们的落地页本来就在第 1 位）
  结果：38 passed, 1 failed

### 恢复修复版
  结果：39 passed, 0 failed
```

只有「决策」这一条变红 —— 判据精确，不是一刀切。

## 三、顺带修的 2 处（都是这轮撞出来的）

### 3.1 `scoring.js` 命中分析 Tab 在接口异常时整块崩掉

跑门禁时撞见一条真错误：

```
✗ 无其它 pageerror / console.error
  ["data.by_direction is not iterable\nrenderHitStats (scoring.js:417)\nloadHitStats (scoring.js:106)"]
```

**根因**：`fetchJson` 在任何失败（429 限流 / 网络抖动 / 500）时返回**通用空壳**：

```js
// static/scoring.js:318
return { rows: [], buckets: [], tags: [] };   // ← 这个壳没有 sample_size / by_direction
```

而 `renderHitStats` 的守卫写的是 `data.sample_size === 0` ——
兜底场景下 `sample_size` 是 `undefined`，`undefined !== 0` ⇒ **守卫不生效**
⇒ 落进 `for (const d of data.by_direction)` ⇒ `undefined is not iterable`
⇒ TypeError ⇒ **整个「命中分析」Tab 渲染不出来**，
描述行还会露出 `sample=undefined` 字面量。

同文件的 `renderSummaryTable` / `renderTagTable` / `renderCalendar`
**都是**用「字段缺失或数组为空」做守卫的，只有这里漏了。

修法（与同文件其它 renderer 一致）：

```js
if (!data || !data.sample_size || !Array.isArray(data.by_direction)) { ...空态... }
```

**新门禁** `scripts/_verify_scoring_robust.mjs`（8 条断言）：
用**真实请求拦截**造出两种响应，不靠「等它恰好撞上限流」——
A. 兜底空壳 ⇒ 必须显示空态、零 JS 错误、无 `undefined` 泄漏；
B. 正常 payload ⇒ **必须真的渲染出方向卡**（防「修成永远空态」）。

**反向验证**：回退守卫 ⇒ `6 passed, 2 failed`（含 `sample=undefined` 泄漏那条）；恢复 ⇒ `8 passed, 0 failed`。

### 3.2 两道浏览器门禁把「服务端 429 限流」误判成「页面 JS 错误」

`_verify_cmd_palette.mjs` / `_verify_mobile.mjs` 的收尾都有一条
「无其它 pageerror / console.error」。而服务端有 **600 req/min per IP** 的限流
（`src/app/middleware/rate_limit.py`），浏览器把被拒的请求记成 console error：

```
fetch failed: /api/v1/scoring/verdict?date=2026-10-25 Error: HTTP 429: Too Many Requests
```

⇒ 门禁**连续跑几次就 flap**（同一份代码、同一台服务，39/0 与 38/1 交替）——
**429 是服务端拒绝，不是页面缺陷**。

修法：加一条**窄口径**豁免（只匹配 `HTTP 429: Too Many Requests`），
并**显式打印条数与条件**（限流被关掉或行为变了，这行豁免自然失效）：

```
⚠ 服务端限流（429）导致 5 次请求被拒 —— 不是页面缺陷（连续跑本门禁会撞 600 req/min；等 60s 窗口滑过再跑）
```

> 豁免必须写明失效条件，否则就成了永久放行（见记忆「豁免清单会自我腐化」）。

## 六、教训

1. **同一个入口可以有四种落点，而其中三处是对的** ——
   「点顶栏」「点场景卡」「点抽屉」「在面板里输入」这 4 个动作，
   在用户心里是**同一件事**，实现上却是 4 条独立路径。
   顶栏/场景卡/抽屉共用 `SCENES` 的 `path`，面板是**另外派生**的 ⇒ 漂移就发生在派生那一层。
   **教训：同源派生的东西要连「顺序」一起同源**，不只是「集合」同源。

2. **去重会改变顺序，顺序也是行为** ——
   去重逻辑本身没错（不去重就会出现两条一样的 /scoring），
   但它把落地页从第 1 位挤到了第 2 位，**而「第一条命中」在面板里是有语义的**（默认选中 + 回车）。
   凡是「第一条有特殊含义」的地方，去重/排序都要重新审视。

3. **门禁要断言「同一个动作的多个入口落点一致」，而不是逐个入口断言** ——
   本轮的断言写成「输入场景名 → 第一条 == 场景 path」，
   一条断言同时管住 8 个场景，且**新增场景自动受约束**。

4. **豁免必须写明失效条件** ——
   429 的豁免窄到只匹配 `HTTP 429: Too Many Requests`，且会打印条数与原因。
   限流真被关掉时这行豁免自然失效，不会变成永久放行。

5. **门禁的「绿色」要经得起连续跑** ——
   flap 的门禁比红的门禁更坏：它让人不再相信它。
   本轮 3 次连跑才暴露出 429 误分类和 scoring 崩溃两个问题。
