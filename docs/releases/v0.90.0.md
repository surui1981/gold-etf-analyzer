## 五类改动

### 1. Schema bug fix · `SnapshotOut` 暴露 `macro_detail`（C1）

**`src/app/schemas/snapshot.py`**：加 `macro_detail: dict[str, Any] | None = None` + `field_validator` 反序列化 JSON。

**V0.79.0 同类陷阱复盘**：
- V0.79.0 任务 #162 加 `tech_detail` 列 + schema 暴露 + 数据落库 ✓
- V0.79.0 **同期**加 `macro_detail` 列 + 数据落库 ✓，但 **schema 漏配** ❌
- Pydantic `from_attributes=True` 按白名单丢弃未声明字段 ⇒ 前端快照响应永远没有 `macro_detail`
- 修了 `tech_detail` 漏 `macro_detail`，**两者本应是同类修改**

**反序列化策略**（V0.78.0 Step D 纪律：数据不足 ≠ 中性）：
- `str` JSON → `dict`（主流路径）
- `dict` 入参 → 透传
- `None` → 透传（与 `tech_detail` 历史 NULL 同语义）
- 损坏 JSON / 顶层非 dict → log warning + 置 None（**不兜底为 `{}`**）

**为什么此前漏掉**：V0.79.0 任务 #162 关注点是「**落库** + **回测可用**」，schema 字段暴露是次要关注；当时 V0.79.0 回测只直接读 DB（不经过 schema），所以 schema 漏配无即时症状。V0.90.0 timeline 端到端走 schema ⇒ 暴露。

**防回归**：tests/test_schemas/ 新建目录（与 test_models / test_services 平级），14 例覆盖 8 类入参 + 既有字段不变回归 + SnapshotListOut 容器包装。

### 2. 仓储层 · `SnapshotRepository.list_in_range`（C2）

**`src/app/repositories/snapshot.py`**：新增 `list_in_range(start, end) -> list[DailySnapshot]`，按日期升序。

**用途**：
- timeline 聚合批量取 trades 时间窗内快照内存对齐（避免 N+1 调用 `get_previous`）
- snapshots/in-range 端点

**边界**：
- `start == end` → 1 行
- `start > end` → 空 list（**仓储层零业务规则**，参数校验放端点）
- 稀疏数据 → 只返回已存在行（中间不补全）
- 倒序插入 → 输出仍升序

**`tests/test_repositories/test_snapshot.py` 10 例**：8 例 `list_in_range` 全分支 + 2 例既有方法（`get_by_date` / `upsert`）回归。

### 3. 服务层 · `DailySnapshotService.get_by_date` + `get_in_range`（C3）

**`src/app/services/snapshot.py`**：
- 新增 `get_by_date(snapshot_date)` —— 薄包装到 `repo.get_by_date`，返回 `SnapshotOut`（含 macro_detail 反序列化）
- 新增 `get_in_range(start, end)` —— 薄包装到 `repo.list_in_range`

**`tests/test_services/test_snapshot_service.py` 新增 `TestGetInRange` 6 例**：空 DB / 含端点升序 / macro_detail 反序列化端到端 / start>end 返空 / 稀疏数据保留空洞 / 返回类型 `SnapshotOut`。

修复 `_insert` fixture：`macro_detail` 是 NOT NULL 列（V0.79.0 设计：snapshot 必带宏观因子；缺失时不写快照而不是写 NULL）。

### 4. Snapshot 端点 · `by-date/{date}` + `in-range`（C4）

**`src/app/api/v1/endpoints/snapshot.py`**：复用既有文件（V0.79.0 创建），加 2 个端点：

#### `GET /api/v1/snapshots/by-date/{snapshot_date}`
- 200：返回 `SnapshotOut`（含 `macro_detail` dict 反序列化）
- 404 `snapshot_not_found`：当日无快照（节假日 / 数据缺失）

#### `GET /api/v1/snapshots/in-range?start=&end=`
- 200：`SnapshotListOut`（含 `macro_detail`）
- 400 `invalid_date_range`：`start > end`
- 400 `date_range_too_wide`：范围 > 730 天（2 年上限）

**`tests/test_api/test_snapshot.py` 新增 10 例**：
- `TestByDateEndpoint` 4 例（端到端 macro_detail dict 验证 / 404 / 200 / 422）
- `TestInRangeEndpoint` 6 例（升序 / 倒序 400 / 范围过大 400 / 单日 200 / 空 list 200 / 缺参数 422）

既有 6 例 V0.63.0 回归全过。

### 5. Timeline 服务 + 端点（V0.90.0 核心新增）（C5）

#### `src/app/services/timeline.py`（新）
- `TimelineService.build(*, account_id, from_date, to_date, compress_threshold_days=7)`
- 聚合 `TradeRecord` + `DailySnapshot` 按日期对齐
- **对齐策略**：trade 当日优先 → 缺则回退最近前一日（**上限 30 天**防历史空洞误拿远古快照）
- **空闲段折叠**：跨度 > `compress_threshold_days` 时折叠为 1 个 `compressed=True` 段

#### `src/app/schemas/timeline.py`（新）
- `TimelineOut`：from_date / to_date / span_days / active_days / decision_count / segments
- `TimelineSegment`：type="decision"|"idle" + 日期范围 + decision 段附 `trade`/`snapshot` / idle 段附 `idle_days`/`compressed`

#### `GET /api/v1/trades/timeline`
**Query 参数**：
- `account_id: int | None` —— 账本筛选（不传=全部）
- `from_date: date` —— 默认 90 天前
- `to_date: date` —— 默认今日
- `compress_threshold_days: int` —— 默认 7（0=不折叠；最大 365）

**错误**：
- 400 `invalid_date_range`：`from_date > to_date`
- 400 `date_range_too_wide`：范围 > 730 天
- 422：`compress_threshold_days < 0` / 日期格式非法

**`tests/test_api/test_trades_timeline.py` 16 例**：
- 空 / 单 trade + 同日快照 / 回退前一日 / 完全无快照 → null / 折叠 / 不折叠 / 默认 90 天窗口 / 400×2 / 422×2 / account_id 过滤 / 同日多 trade / active_days 去重 / 交替排列 / 当日优先于回退

## 风险与缓解

| # | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|
| R1 | `macro_detail` 反序列化失败（旧数据格式异常） | 低 | 中 | `field_validator` 捕获 `JSONDecodeError` → log warning + 置 None |
| R2 | `get_previous` 找不到前一日（账户无任何历史快照） | 中 | 低 | `snapshot=None` 透传，前端决策点展示「无数据」badge |
| R3 | timeline 聚合 N+1 查询（每个 trade 一次 get_previous） | 中 | 中 | 服务层先批量 `list_in_range` 再内存对齐；O(1) DB 往返 |
| R4 | 范围 > 2 年导致前端渲染卡 | 中 | 中 | 服务层强制 `date_range_too_wide` 400；前端默认 90 天窗口 |
| R5 | V0.90.0 改 schema 字段会让现有 `/api/v1/snapshots/list` 响应字段变化（macro_detail 突然现身） | 中 | 低 | 是 fix；前端 V0.86 决策可解释已接 snapshot 但只用 `trend_index` / `tech_index`；`macro_detail` 新增不影响 |
| R6 | trades 跨日（如 23:59 下单算次日）边界 | 低 | 低 | 沿用 `datetime.combine(date, time.min)` 边界 |
| R7 | `compress_threshold_days=0` 时 idle 段全部不折叠，性能骤降 | 低 | 低 | 服务层做 ≤ 365 段保护（> 365 idle 段 → 强制折叠 30 天） |
| R8 | V0.88.0 sw.js VERSION hotfix 教训在 V0.90.0 重演 | 中 | 中 | **本版预防**：C6 同时改 `static/sw.js:16` 的 `const VERSION`；末步必跑 `pytest tests/test_scripts_check_pwa_assets.py` |

## 教训

1. **同类 schema 漏配要配对查找**：V0.79.0 任务 #162 加了 `tech_detail` 列 + schema 暴露 + 数据落库三件套；**同期** `macro_detail` 做了前两件但漏第三件。V0.79.0 没有「同表所有 JSON 列 schema 暴露」的回归测试 ⇒ 漏了 6 个版本。**对策**：未来加 JSON 列到任何 schema 时，写测试断言「同表所有 JSON 列 schema 都暴露」（V0.90.1 候选）。
2. **「薄包装」是有意义的**：服务层 `get_by_date` / `get_in_range` 看似只是转发到仓储，但它们是「schema 边界」——把 ORM 转 `SnapshotOut`，触发 macro_detail 反序列化。直接端点调仓储会**绕过** schema 验证。**对策**：未来「薄包装」写测试验证它确实「不只是转发」（断言返回类型是 schema 而非 ORM）。
3. **「同日多 trade」边界要测**：V0.90.0 timeline 聚合容易漏「同一日 N 个 trade → N 个 decision 段」的边界（语义上是「单点多次操作」而非「单点单操作」）。测试矩阵里 `test_multiple_trades_same_day_each_get_segment` 固化为回归用例。
4. **「无 trade 但区间非空」要单测**：`_build_segments` 早期版本有 elif 处理这种边界但写错（idle 从 `from_date + 1` 开始而非 `from_date`）。**对策**：服务层每个分支都对应至少 1 个测试用例（不依赖组合 case 顺带覆盖）。
5. **V0.88.0 sw.js VERSION 教训生效**：本版发版 checklist 第一项就是改 sw.js VERSION（V0.88.0 同期推送的 `sw-version-sync-gate` MEMORY 已固化清单）。
6. **决策点对齐的「30 天上限」要明确写进代码注释**：避免后续被误改成「无上限」→ 回退到远古快照，与决策点语义脱节。
