## 核心发现：整条链的链头只有一行代码

`src/app/services/cache.py:35`：

```python
def _key(target: str, interval: str, on_date: date) -> tuple[str, str, date]:
    """统一构造缓存 key，interval 归一化为大写单字母（D/W/M）。"""
    return (target, (interval or "D").upper()[:1], on_date)
```

**key 里没有 `days`。** V0.60.0 给它加过时间戳、V0.64.0 给它加过 `interval`，
唯独漏了 `days` —— 而 `days` 是唯一决定**响应里装多少条数据**的参数
（`interval` 只改聚合粒度，底层数据不变）。

于是：

```
60D 按钮带 class="active"（trend.html:399，页面默认先发）
   └─► 60 点结果写进 key=(ny, D, today)
         ├─► 52W 按钮（:400）显示 12 周   · 用户以为是 1 年
         ├─► 24M 按钮（:401）显示 4 个月   · 用户以为是 2 年
         └─► review.backfill(days=…) 走同一路径 ⇒ gold_price_daily 只有 60-80 行
               └─► /backtest/coverage 的 returns_available_days 恒为 1
                     └─► sharpe / 最大回撤 / 年化 全是空壳
```

### 铁证：同一个 URL，9 秒内返回两种长度

后台每 2 秒轮询 `GET /trend?days=730&interval=D`：

```
05:13:30  points=60
05:13:39  points=730      ← TTL(600s) 到期，同一个 URL，覆盖 2023-12-26 → 2026-10-22
```

**命中之后**（730 点已占据那个共享槽）：

```
days=60   → n=730    days=365  → n=730    days=730  → n=730
```

**现在点「60D」会拿到 3 年的日 K。** 同一个接口在不同时刻返回长度差 12 倍的数据，
而前端三种标签共用这一份数据画图。

### 数据源是好的

直连 `AkshareGoldHistoryProvider.get_history(days=730)`：

```
days=60   → n=60    2026-07-23 → 2026-10-22
days=365  → n=365   2025-04-21 → 2026-10-22
days=730  → n=730   2023-10-18 → 2026-10-22      ← 3 年历史完好
```

**一行绕过缓存的调用，把「数据源不行」和「缓存挡路」彻底分开。**
