# V0.114.2 · 修「点上传并存档没有文件对话框」

> 日期：2026-10-22 ｜ 类型：hotfix ｜ 1 处 CSS + 1 段注释
>
> 一句话：上传区的 file input 被设成 `display: none`，而容器上**只挂了拖拽事件、
> 没有任何 click 处理器** —— 点「上传并存档」后**点哪里都不弹对话框**，所有浏览器
> 都一样。

## Context

用户报「点击报告上传，浏览器中没有文件上传的对话框」，用的是 Firefox。

初判是 Firefox 特有问题。实跑 Chrome 后**推翻了**：

```
点 .drop 后 filechooser 触发: 否 ← 对话框没弹（Chrome）
fileInput 计算样式: display=none  offsetParent=null
```

根因是**通用 bug**，Firefox 只是先被撞见的那个。

## 根因

```html
<!-- report-archive.html:246 -->
<div class="drop" id="dropZone">
  <span class="ico">📄</span>
  <span data-i18n="reports.drop_hint">点击选择，或把 HTML 文件拖到这里</span>
  <input type="file" id="fileInput" accept=".html,.htm,text/html">
</div>
```

```css
/* report-archive.html:151 —— 原先 */
.upload-card .drop input[type="file"] { display: none; }
```

```js
// report-archive.js:426 —— 只有 dragenter/dragover/dragleave/drop，**没有 click**
```

三处叠起来：

1. input 是 `display: none` ⇒ 用户点不到它
2. `.drop` 上没有 click 处理器 ⇒ 提示文案承诺的「点击选择」没有任何实现
3. 于是**唯一可用的路径是把文件拖进来**，而提示文案完全没提这点

所以这不是「某个浏览器拦了对话框」，而是**根本没有对话框可弹**。

## 修法：让 input 本身当覆盖层，点击路径上不经过任何 JS

把 `display: none` 换成铺满 `.drop` 的透明覆盖层：

```css
.upload-card .drop { position: relative; }
.upload-card .drop input[type="file"] {
  position: absolute; inset: 0;
  width: 100%; height: 100%;
  opacity: 0; cursor: pointer;
  z-index: 2;   /* 盖住前面的 .ico 与提示文案，抢到命中测试 */
}
.upload-card .drop:focus-within { outline: 2px solid var(--accent); outline-offset: 2px; }
```

真实点击落在**原生 file input** 上 ⇒ 浏览器自己的默认行为就是弹对话框。
没有 JS 参与，也就没有「用户手势」「是否在事件回调里」这类浏览器差异。

### 为什么**不**用「`display:none` + JS 调 `input.click()`」

那是最容易想到的写法，也正是最容易只在一个浏览器坏的写法：

- Chrome：**放行**
- Firefox：**拒绝** —— 元素未渲染（unrendered）时不允许唤起文件选择器

也就是说不加注释的话，这条路会在 Chrome 上测得「通过」，上线后只在 Firefox
静默失效。覆盖层写法绕开了整个差异面。

### 为什么用 `opacity: 0` 而不是 `visibility: hidden`

`visibility: hidden` 在部分浏览器里会让控件**不可聚焦**，键盘用户就彻底够不着
了。`opacity: 0` 保留可聚焦性，配合 `:focus-within` 给 `.drop` 一圈可见焦点环
（沿用 V0.113.0「焦点不能不可见」的口径）。

### 拖拽不受影响

drag 事件从覆盖层**冒泡**到 `.drop`，原有的 `dragenter` / `dragover` /
`dragleave` / `drop` 监听器照旧命中（已在验证脚本里断言）。

## 验证

新增 `scripts/_verify_upload_dialog.mjs`，**10 条断言**。

### 踩到的坑：判据选错了

第一版用 `page.on("filechooser")` 当「对话框真的弹了」的判据，跑出来是红的。
但基线测试证明**这个 headless Chrome 连裸 `<input type="file">` 的真实点击都不发
`filechooser`**：

```
A. JS 调 input.click() → filechooser: 未触发
B. 真实点击 input      → filechooser: 未触发
```

那条断言测的是 puppeteer 的能力，不是被测代码 —— **比没有断言更坏**（假绿）。
换成真正的判据：

> **`document.elementFromPoint(drop 区中心)` 是不是那个 fileInput。**

因为浏览器对**已渲染**的 file input 的默认行为就是弹对话框，落点对了对话框就会弹，
路径上没有 JS。修复前这里命中的是无处理器的 `<SPAN>`。

### 反向验证

把 CSS 退回 `display: none` 后 **6 条变红**，含决定性的那条：

```
[FAIL] drop 区中心命中的是 fileInput :: {"tag":"SPAN","id":"","type":null}
[FAIL] fileInput 不是 display:none     :: {"display":"none","opacity":"1","w":0,"h":0}
[FAIL] fileInput 有实际尺寸（能接到点击） :: 0×0
[FAIL] fileInput 视觉上透明            :: opacity=1
[FAIL] 点击落点仍是 fileInput
[FAIL] fileInput 可键盘聚焦
```

修复后 **10 passed / 0 failed**。
