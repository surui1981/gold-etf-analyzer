# V0.116.2 · 3 处静默失效的前端缺陷 + 2 处「绿着但什么都没保护」的门禁缺陷

> 2026-10-25 · fix · 维护性发版 · 从「CI 修绿」转向「深挖前端静默失效」

## 起因

V0.116.1 把 CI 修绿之后，「CI 绿」这件事本身已经不再是瓶颈了。
于是继续往下挖前端，结果挖出 **3 处「不报错、不红屏、就是少一块东西」** 的缺陷。

它们的共同点比缺陷本身更值得记：**没有任何机制会告诉你坏了** ——
没有异常、没有 console 报错、没有测试失败、门禁全绿。
页面只是少了一块、或者整页显示成别的东西。

更值得注意的是**门禁为什么没拦住** —— 因为门禁自己的扫描口径有洞。
本轮把这 2 处门禁缺陷也一并修了（这才是「这类问题以后不再复现」的部分）。

---

## 一、缺陷 1：「用户管理」页整页渲染成 i18n 键字面量

### 症状

`/static/admin/users.html` 显示的是：

```
admin.h_title
admin.sub
admin.denied
reset.btn_back_login
```

而不是「用户管理」/「仅所有者可访问此页面。」/「返回登录页」。

### 根因

该页的 `<head>` 里只引了 `i18n.js` + `auth.js`，**漏引 `/static/i18n/zh-CN.js`**。

### 为什么「只有默认语言中招」—— 这是最反直觉的一处

`static/i18n.js` 的加载逻辑是分叉的：

| 语言 | 取字典的方式 | 漏引字典文件的后果 |
|---|---|---|
| 非默认语言（en-US / zh-TW） | **动态插 `<script>`** 去加载对应字典 | ✅ 照样能取到字典 ⇒ 页面正常 |
| **默认语言 zh-CN** | 走 `syncLoadDefault()`，**只读 `window.PM_I18N_ZH_CN`** | ❌ 字典没引 ⇒ `window.PM_I18N_ZH_CN` 是 `undefined` ⇒ **全页回落成键字面量** |

所以现象是「**中文坏了，英文和繁体中文好好的**」——
一个很容易被误判成「翻译没做完」或「某几个 key 漏了」的现象，
真实原因却是「一个 `<script>` 标签漏了」。

### 修法

```html
<script src="/static/i18n/zh-CN.js"></script>
<script src="/static/i18n.js" defer></script>
```

### 门禁为什么没拦住（缺陷 1 的真正成因）

`scripts/check_i18n_keys.py` 里有一条**专门防这个**的检查：

```python
def check_dict_loaded() -> int:
    """有 data-i18n 的页必须引字典文件，否则整页渲染成 key 字面量。"""
    for name in sorted(os.listdir(STATIC_DIR)):   # ← 只看顶层！
        if not name.endswith(".html"):
            continue
```

`os.listdir(STATIC_DIR)` **只列顶层目录** ⇒ `static/admin/users.html`
（在 `static/admin/` 子目录里）**永远扫不到** ⇒ 门禁一路绿灯。

而**同一个脚本**里的 `extract_html_keys()` 用的就是递归 glob ——
**两处口径不一致**，这正是这类漏扫的温床。
（同类问题本仓库已踩过两次：`check_docs_claims.py` 漏扫 `docs/releases/`、
`check_i18n_keys.py` 漏扫 `static/admin/`。）

改成递归后：

```python
for path in sorted(glob.glob(os.path.join(STATIC_DIR, "**", "*.html"), recursive=True)):
```

扫描面 **20 → 21 页**。

**反向验证**（把字典行去掉，门禁必须红）：

```
[FAIL] admin/users.html 用了 data-i18n 但没引字典文件 → 整页会渲染成 key 字面量
```

## 二、缺陷 2：`/ask` 的数据时效条 + 投资警示 pill 永久不可见

### 症状

`/ask` 页顶部**没有**「数据时效 / 警示计数」那一行；
而 `trend` / `portfolio` / `silver` / `scoring` … 都有。

### 根因

```html
<details id="statusPanel" class="status-panel" hidden>   <!-- ← 这个 hidden -->
```

全站 **12 个**带 `#statusPanel` 的页面里，**只有 `ask.html` 写了 `hidden`**。

### 为什么没人发现

1. `hidden` 的 CSS 优先级（`[hidden]`，0-1-0）**高于** UA 样式表的
   `details { display: block }`（0-0-1）⇒ 实测计算样式确实是 `display: none`；
2. `warning.js` 只操作 `open` 属性、**从不碰 `hidden`** ⇒ 没有任何脚本会把它救回来；
3. 页面本身没有报错 —— 就是少了一行。

### 修法

去掉 `hidden`（与另外 11 页对齐）。

## 三、缺陷 3：`/ask` 的「本次会话不再展开」勾选框点了没反应

### 症状

勾上「本次会话不再展开」，下次进 `/ask` 还是自动展开。

### 根因

```html
<input type="checkbox" id="warnDismiss">     <!-- HTML：id -->
```

```js
var dismiss = panel.querySelector("[data-warn-dismiss]");   // warning.js：属性选择器
```

⇒ `querySelector` 返回 `null` ⇒ `warning.js` 里整段 dismiss 逻辑被**静默跳过**。
不是「功能不生效」，是**功能压根没被接上**。

### 修法

```html
<input type="checkbox" id="warnDismiss" data-warn-dismiss>
```

保留 `id`（不破坏既有选择器），补上 `warning.js` 真正查的那个属性。

> 参照：全站 **11 个**页面有 `data-warn-dismiss`（`report.html` 除外 ——
> 它的 `#statusPanel` 是**旧形态**（只有一个「数据时效」summary + 空 body），
> 压根没有警示内容可 dismiss。属另一件事，本轮不动）。

## 四、门禁加固：浏览器门禁 23 → 42 条断言

`scripts/_verify_i18n_keys.mjs` 扩展：

| 组 | 断言数 | 内容 |
|---|---|---|
| ① `/ask` 状态条 | 5 | `#statusPanel` 存在 / 无 `hidden` 属性 / 计算样式不是 `display:none` / summary 可见 / 面板内有 `[data-warn-dismiss]` |
| ② `admin/users.html` 三语译文 | 9 | zh-CN / en-US / zh-TW 各 3 条：**标题 / 无权提示 / 返回按钮**都是译文而不是键字面量 |
| ③ 泛化「无键字面量」 | 3 | 每个语言 1 条：任何 `data-i18n` 元素的正文若**恰好等于自己的键**就算失败 |
| ④ admin 页零噪音 | 2 | 零 console error / 零 pageerror |

合计 **19 条新增**（23 → 42）。

第 ③ 组是**泛化断言** —— 不只盯这 3 个键，而是「页面上任何一个 `data-i18n` 元素
都不许把自己的键字面量显示出来」。
这样下次再出现「漏引字典」或「某个 key 漏翻译」，不用改门禁就会红。

### 反向验证（每条新断言都必须真的能变红）

| 回退动作 | 变红的断言 | 实测 |
|---|---|---|
| ① 把 `hidden` 加回 `#statusPanel` | 3 条 | `无 hidden 属性` / `display:none` / `summary 可见` |
| ② 去掉 `data-warn-dismiss` | 1 条 | `面板内有 [data-warn-dismiss]` |
| ③ 去掉 `admin/users.html` 的字典行 | 4 条 | 3 条译文断言 + 残留 key 字面量计数实测 **10 个** |

反向验证用的是**真实回退实现**（改回旧代码），不是改断言的期望值。

## 五、已知问题（本轮**未**修 —— 要动生产数据库）

深挖时顺带查了生产库的 schema，发现**生产 SQLite 的 `users` 表缺 `role` 列**：

| 表 | 缺 | 多 |
|---|---|---|
| `users` | `role` | `username` / `is_default` |
| `telemetry_events` | — | `client_ts` |

（20 张模型表全部存在；`alembic_version = s1t2u3v4w5x` = 迁移链头，即 27 条 revision 全部「已应用」——
**记录的迁移状态与实际表结构对不上**。）

### 连带影响（实测）

| 端点 | 状态 | 原因 |
|---|---|---|
| `GET /api/v1/admin/users` | **500** | `no such column: users.role` |
| `POST /api/v1/admin/users/{id}/reset-password` | **500** | 同上 |
| `GET /api/v1/auth/me` | **500** | `DetachedInstanceError` |

`/auth/me` 的 500 被 `static/auth.js` **静默吞掉**（降级成「认证未启用」），
所以顶栏不会崩 —— 但**状态显示是错的**。

### 修法（本轮没做）

新增一条 alembic 迁移：`ALTER TABLE users ADD COLUMN role VARCHAR(...)` + 回填 `'owner'`。
做完之后，V0.97.0 那个 `require_user` 里的
`load_only` + `set_committed_value(legacy, "role", ROLE_OWNER)` workaround
**也可以一并撤掉**（它当初就是为了绕开这个缺列才写的）。

### 为什么本轮不做

它要**改生产 SQLite 库**（写文件、加列、回填数据），
属于「动生产数据」的动作 ⇒ 留给用户决定，本轮只报告不改。

### 另一处认证边界问题

单用户模式（`AUTH_ENABLED=false`）下，`require_owner` **接受匿名调用者** ——
认证边界不对。虽然当前请求会先因为缺列 500 而「什么都没发生」，
但一旦补了列，这条路径就会真的放行匿名写操作。
**补列时必须同时收紧这一条**，否则等于把一个 500 换成一个越权。

## 八、教训

1. **「页面显示成键字面量」这个症状，永远先怀疑 `<script>` 标签，而不是翻译。**
   本仓库的 i18n 加载是「默认语言读全局变量、其它语言动态插 script」的**分叉**结构，
   只有默认语言会因为漏引而炸 —— 这与直觉（「三语都不对 ⇒ 翻译问题」）正好相反。
2. **同一个脚本里两处扫描口径不一致，就是下一个漏扫的位置。**
   本轮修的 `check_dict_loaded()` 漏扫 `static/admin/`，
   与之前 `check_docs_claims.py` 漏扫 `docs/releases/` 是**同一个形状**。
   修法统一成递归 glob + 在注释里写明「为什么必须递归」。
3. **「静默跳过」比「报错」更危险。** `querySelector` 返回 `null` 不抛异常，
   `hidden` 也不抛异常 —— 两处的代价都是「功能看起来在，实际没接线」。
4. **门禁绿 ≠ 覆盖到了。** 本轮两个门禁缺陷（扫描口径洞 / 断言不存在）
   都是「门禁自己绿着，但绿的是错的范围」。
