## 〇 一页结论

**症状**：用户报告「首页今日要闻没有正确显示新闻标题，不需要分值显示在栏目」。
**根因**：home.html / home.js 在 `bfeb39f`（V0.102 今日要闻 readhub 财经流落地）已切到 readhub 端点，但 `static/sw.js` VERSION 仍卡在 `v0.100.0`；activate 阶段按 cache name（`gold-shell-v0.100.0` / `gold-runtime-v0.100.0`）无法识别旧版需清理，浏览器 SW 持续回放 `RUNTIME_CACHE` 旧 `/home` 307 + 旧 `/static/home.html`（含 `news-score` 旧字段，故用户看到「分值」）。
**修法**：4 处版本同步（`__version__` / `pyproject.toml` / `sw.js VERSION` / CHANGELOG）+ sw.js activate 阶段显式清 `RUNTIME_CACHE` 旧 `/home` + `/static/home.html`（套 V0.92.0 `/scoring` 同模式）。

**4 文件 / 1 commit / 20+/5-**，无 schema、无 i18n、无后端变动。

## 一、问题

### 现象

用户在 `http://192.168.0.204:8889/gold/home` 看到首页 今日要闻 section 仍走 `news-score` 旧版（每个 `<li>` 渲染出 0-100 的分值 badge），标题文字未正确显示（`news-score` 返回结构里 title 字段命名与 readhub 不同，模板里 `item.title` 命中 undefined 静默渲染）。

### 排查路径

1. **后端验证**：直接 `curl http://127.0.0.1:8888/api/v1/news-feed/items?days=2&limit=5` 返回完整 `[{external_id, title, url, site_name, publish_date, ...}]`，**数据层没问题**。
2. **静态资源**：`curl http://127.0.0.1:8888/static/home.html` 内容里 `id="homeHeadlinesChip"` + `.home-news-title` + `.home-news-site` + `.home-news-date` 类齐全，**HTML 本身没问题**。
3. **本地 puppeteer 实跑**（127.0.0.1:8888）：5 条 readhub 新闻完整渲染，标题、时间、来源站、URL 全对，`hasAnyScoreField: false`，**应用层没问题**。
4. **服务端 sw.js 实际 VERSION**：`grep VERSION static/sw.js` → `v0.100.0`，但 home.html / home.js 在 `bfeb39f` 已切到 readhub —— **SW 缓存版本与前端代码不同步**。
5. **激活机制**：`activate` 阶段清 cache 用的过滤条件是 `k !== SHELL_CACHE && k !== RUNTIME_CACHE`，两个常量分别是 `gold-shell-${VERSION}` / `gold-runtime-${VERSION}`。VERSION 没变 → 旧 cache 名 `gold-shell-v0.100.0` / `gold-runtime-v0.100.0` == 新 cache 名 → 旧 cache **永远不会被清**。

### 根因

参照 [sw-version-sync-gate.md](../../.claude/projects/-home-surui-gold-etf-analyzer/memory/sw-version-sync-gate.md) 教训：发版 4 处版本同步清单（`__version__` / `pyproject.toml` / `sw.js VERSION` / CHANGELOG）必须同步 bump，否则浏览器 SW 缓存永远无法感知新版本。

V0.102 落地 7 commit 时只 bump 了 V0.100.0 的功能代码（home.html / home.js），但没动 sw.js VERSION（因为当时"还不算 V0.102 正式发版"）。结果部署后用户浏览器持续回放 stale home.html。

### sw.js activate 阶段显式清 stale（RUNTIME_CACHE）

参照 V0.92.0 hotfix（V0.92.0 `/scoring` 同问题）模式：

```js
.then(async () => {
    const rt = await caches.open(RUNTIME_CACHE);
    const stale = [
        "/scoring", "/static/scoring.html",
        "/home", "/static/home.html",   // V0.100.1 新增
    ];
    for (const url of stale) {
        const hit = await rt.match(url);
        if (hit) await rt.delete(url);
    }
})
```

原因：`/static/*` 走 cache-first；若 RUNTIME_CACHE 里有 stale `/home` 307 入口或旧 `/static/home.html`，SHELL_CACHE 里的新版永远没机会被命中。一次性清理后新条目进 SHELL_CACHE 优先。

## 五、教训沉淀

参照 [sw-version-sync-gate.md](../../.claude/projects/-home-surui-gold-etf-analyzer/memory/sw-version-sync-gate.md) V0.88.0 教训：**前端改 static/*.html / static/*.js 时必须同步 bump sw.js VERSION**，否则浏览器 SW 缓存永远无法感知新版本。V0.100.1 这次的根因正是 V0.102 7 commit 改前端时漏了这一步。

新增护栏建议（待 V0.101 收口时做）：`check_pwa_assets.py` 增一项检查 —— 对比最近 7 天改动的 `static/*.html` / `static/*.js` 文件清单与 sw.js 的 `git log --since=VERSION` 时间戳，若有任何静态资源在 VERSION 之后改动则报红。这能从机制上避免再发生。
