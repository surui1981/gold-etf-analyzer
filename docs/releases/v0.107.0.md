# V0.107.0 · 今日要闻按天聚合 + 刷新 UX 改进

> 日期：2026-10-19
> 类型：数据层深化 + 体验改进（aggregate + UX）—— news_feed_daily 物化宽表 + 刷新 toast + alembic 双 head 合并

## 用户原话

> OK 当前今日要闻 页面新闻 客户刷新后可以实现新闻更新么， 新闻的存储也需要按照天进行保存。制定计划开始实施

## 问题与目标

**问题 1**：V0.102 起的 `news_feed_items` 是单条粒度表（每条新闻 1 行），「/headlines 顶部 daily 摘要」每次都靠 `GROUP BY` 实时算（~30 天 × 1 次查询 ~5-20ms），**没有持久化的按日快照**。

**问题 2**：刷新按钮是 emoji-only 🔄，success 路径**无 toast**（fail 才弹），用户点击不知道触发了 readhub 调用，且 fav 收藏 toast 因 `PMToast` 拼错**静默 dead**（F12 看不到错）。

**问题 3**：alembic 双 head `n0a1b2c3d4` (V0.103 收藏) + `n0o1p2q3r4` (V0.105 类目) 从 V0.102 `m9g0a1b2c3` 分叉后**未合并**，`alembic heads` 一直返回 2 个 head。

**目标**：
1. 新建 `news_feed_daily` 物化宽表（仿 `scoring_daily_wide` 的 date-as-PK 模式），1 日 1 行
2. UI 直接读聚合表（O(1) 行）替代实时 `GROUP BY`
3. 刷新按钮加 success toast + tooltip 改写「从 readhub 立即拉取最新」
4. 顺手修 `PMToast` → `PM_Toast` typo（fav toast 之前静默 dead）
5. 合并 alembic 双 head（V0.107 末单一 head）

## 关键设计

### 1. ORM `NewsFeedDaily`（C1，仿 `scoring_daily_wide`）

```python
class NewsFeedDaily(Base):
    __tablename__ = "news_feed_daily"
    date: Mapped[date_t] = mapped_column(Date, primary_key=True, comment="BJT 日期")
    total_count: Mapped[int]              # 当日总条数（含未分类）
    finance_count / tech_count / vc_count / biz_count / other_count  # 5 类目
    unique_sites_count: Mapped[int]       # 独立来源站数
    en_count / zh_count: Mapped[int]      # 语种计数
    first_publish_at / last_publish_at    # UTC，nullable 当日空
    last_refresh_at: Mapped[datetime]     # 最近 rebuild 时间
    created_at / updated_at
```

**不挂 user_id**（V0.80.0 #159 例外，news 是 shared context，与 `news_feed_items` 一致）。

### 2. 合并迁移 `n1o2p3q4r5`（C1）

`down_revision = (n0a1b2c3d4, n0o1p2q3r4)` tuple → alembic 自动合并 2 个 head。

### 4. service + 2 端点（C3）

### 5. scheduler 集成（C4）

```python
async def _refresh_news_feed() -> int:
    n = await service.refresh(force=True)  # 现有
    # V0.107：refresh 后**始终**重建 BJT today + BJT yesterday
    for d in (bjt_yesterday, bjt_today):
        await service.rebuild_daily(d)
    return n
```

**为何 2 天都重建**：覆盖「跨 BJT 午夜 refresh」场景（self-healing），2 次 rebuild ≈ 20ms 可接受。

启动 lifespan 阶段 `_backfill_news_feed_daily(start_date=today-30d, end_date=today)` spawn_background，仿 `_backfill_news_categories` 模式（失败仅日志，不阻塞 readiness）。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| `upsert_daily` BJT 时区转换错 | SQL 显式 `datetime(publish_date, '+8 hours')` 测过；test_sql 验证 + 实测 27/154/56 三天数据准确 |
| 启动 backfill 30 天 × scheduler 4h × forever → 每次重启 30 天重算 | 30 天 × 1 row × 1 SQL 聚合 ≈ 30ms，可接受；后续可加增量 backfill |
| 跨午夜 refresh 漏掉昨日 | `_refresh_news_feed` 重建 BJT today + BJT yesterday 2 行（self-healing） |
| daily 表与 items 表 count 不一致（用户查 items 但 daily 显示不同）| daily 是 BJT 日；items 是 UTC。文档里加 BJT 标注；UI 也写「今日摘要（按 BJT 日）」 |
| 5 类目计数需要 category 非 NULL | backfill_categories 已跑过（V0.106.2 hotfix），无需新加 backfill；新插入的由 fetcher 的 `_normalize` 即时分类 |
| `uv lock` 网络阻塞 | 手动 bump uv.lock 版本号（其他 lock 内容不变，pyproject.toml 也无 dependency 变更） |

## 排除（明确不做）

- ❌ 自动刷新（page load 时 > 2h 自动 refresh）—— 用户没要求
- ❌ home page daily summary 用实时 GROUP BY 算（要 1 次 SELECT 解决）
- ❌ 跨语言 daily 聚合（i18n 文案是显示层，不是数据层）
- ❌ 给 daily 表加 user_id 字段（news 是 shared context，V0.80.0 #159）
- ❌ 把 daily 做成 incremental update（每次只算 delta）—— 重算 30 天 = 30ms，复杂度不值
- ❌ 加 admin 守卫到 daily API（只读，无副作用）
- ❌ daily 周报 / 月报聚合
