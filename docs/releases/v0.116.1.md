# V0.116.1 · CI 修绿（ruff lint / ruff format / pytest）+ 版本状态整合

> 2026-10-24 · fix · 维护性发版 · CI 从「每次 push 都红」变成全绿

## 起因

用户：「开始修复」。

CI 从 **V0.108.0（2026-10-16）起每一次 push 都是 failure**，失败步骤始终是同 3 步：

| 步骤 | 状态 | 实测基线 |
|---|---|---|
| `ruff lint`（`uv run ruff check src tests`） | ✗ 预存红 | **290 errors**（257 可 `--fix`） |
| `ruff format check`（`uv run ruff format --check src tests`） | ✗ 预存红 | **79 files would be reformatted**（211 已合规） |
| `pytest (offline regression)` | ✗ 预存红 | **10 failed** / 1777 passed（16 分 30 秒） |
| 其余 11 步（JS 门禁 / docs claims / PWA / 死链 / 版本同步 / 依赖声明 / junit） | ✓ 全绿 | |

这 3 步**都不在「版本状态整合」那一轮的改动范围内**（用 `git worktree add /tmp/wt_pre HEAD~2`
对拍逐条确认全部预存）。但它们让 CI 长期红着，带来两个持续的坏后果：

1. **「CI 绿」在这仓库不能当质量信号** —— 得先看是哪个步骤红；
2. 每次发版都要重新花 25 分钟 + 一个 worktree 对拍，才能确定「不是我这次搞坏的」。

本轮把它们修绿。**修的过程里顺带挖出 4 处真 bug**（不是 lint 噪音），一并修掉。

## 一、ruff：290 → 0，79 个文件重排 → 0

### 怎么做的

```
.venv/bin/ruff check src tests --fix      # 254 条自动修
.venv/bin/ruff check src tests scripts     # 剩 24 条手工改
.venv/bin/ruff format src tests scripts    # 79 + 11 个文件重排
```

⚠️ **CI 只 lint `src tests`，不 lint `scripts/`** ⇒ 新写的脚本 CI 抓不到，本地必须自己守。
本轮把 `scripts/` 的 36 个错也一并修了。

### 语义零变化怎么证明的

**逐文件 AST 比对**（`ast.dump`，对 `HEAD` 与工作区各解析一次再比）：

- 99 个改动的 Python 文件里，**49 个 AST 完全等价** —— 纯格式，语义零变化；
- 其余 50 个的实质改动逐条列出并人工核对（下面第二节）。

这个手段当场抓到了**我自己改出的一个语义 bug**（见下），
也顺带证明了「批量重排」这件事本身是安全的。

### 手工改的 24 条（每条都判过语义）

### `# fmt: off` —— 保紧凑排版

`ruff format` 会把「一行 7 个关键词」的紧凑表炸成**一行一个**。
`news_classifier.py` 的 4 张关键词表（`_FINANCE_KW` / `_TECH_KW` / `_VC_KW` / `_BIZ_KW`）
正是这种形态 —— 里面的分组注释（`# ── 行情 ──` / `# ── 机构 ──`）**只在紧凑排版下读得懂**。

用 ruff 官方的 `# fmt: off` / `# fmt: on` 保住原有排版：该文件 **638 → 340 行**，
`ruff format --check` 依然全绿。（仓库此前没有 `# fmt: off` 用法，这是第一处。）

### ⚠️ 一度改出语义 bug —— AST 比对抓到的

`scripts/check_docs_claims.py` 的 SIM103 我第一次写成：

```python
if re.search(r"\.(py|js|…)$", tail):
    return True
segments = tail.split("/")
...
return False
```
→
```python
return bool(re.search(r"\.(py|js|…)$", tail))     # ← 把后面的判据变成死代码
```

改完局部看着没问题，但**函数后半段（`/api/v1/<segment>/…` 判为模块路径）再也不执行了**
⇒ `check_docs_claims.py` 会漏判一批文档声明。AST 比对时才发现，改回：

```python
if re.search(r"\.(py|js|…)$", tail):
    return True
segments = tail.split("/")
return len(segments) >= 4 and segments[3] in {...}
```

**教训**：`SIM103` 这类「把 if 压成 return」的自动改写，**必须**回头看被压掉的分支有没有后续逻辑。

## 三、pytest：10 failed → 0

10 条全部是**预存**。用干净 worktree（`git worktree add --detach /tmp/wt_head HEAD`）对拍 `HEAD` 逐条复现：
**9 条单跑即红 + 1 条必须整文件跑才红**（顺序污染那一条），与基线记录的 10 条吻合。

| 文件 / 用例 | 根因 | 修法 |
|---|---|---|
| `test_ai_chat_endpoints.py::test_send_message_stream_error_event_yields_error` | **同文件内测试顺序污染**（不是 flaky）：`sse_starlette` 的 `AppStatus.should_exit_event` 是**类级全局**且惰性创建，`anyio.Event` 首次 await 时把 `_loop` 绑死；pytest-asyncio 每个用例新建 loop ⇒ 后面的用例 await 了别的 loop 上的 Event | `tests/conftest.py` 加 autouse fixture，每个用例前重置 `should_exit_event` **与** `should_exit`（只重置前者不够，后者同样会短路关闭信号） |
| `test_news_feed.py::test_list_items_filter_days` | seed 用**写死的 2026-10-19**，而 cutoff 是**相对当下**的 `now - days` ⇒ 测试随日历腐烂 | seed 改**相对今天**（`_D0/_D1/_D2`），`days=2` 留 12 小时余量；实测 400 天 × 24 小时零失败 |
| `test_i18n_coverage.py::test_all_data_i18n_keys_resolve_in_zh_cn` | `ask.html` 用了 `data-i18n="status.warnings"`，**该键 3 语都没有** | 改用已有的 `status.warn_pill_label` |
| `test_i18n_dict.py::test_no_empty_values` / `test_no_duplicate_keys` | `weights.mo_loading` **重复定义**；`en-US.js` 的 `ai.msg_count_unit` 是**空串** | 删重复键 + 新增 `weights.mo_loading_short`；`ai.msg_count_unit` 填 `"msgs"` |
| `test_scripts_check_pwa_assets.py::test_shell_entry_referencing_const_is_expanded` | 夹具造的 HTML **没有 `<link rel="icon">`** ⇒ 门禁正确地判它不合格 | 夹具改成合法 HTML（含 icon link）+ 造出 `icon-192.png` |
| `test_scripts_check_routes.py` ×3 | 断言**写死的个数**（16 / 15 / 18），alias 数一路涨到 18 后**恒红** | 改成**集合相等**断言（alias ∪ 额外端点）+ 新增「无重复项」断言 |
| `test_admin_users.py::test_anonymous_returns_401_or_403` | 断言「匿名应被拒」，但 V0.97.0 起单用户模式（`auth_enabled=false`，本仓库默认）`require_user` 会**回退到 LEGACY_USER** ⇒ 实际 200 | 拆成**两条模式专属**用例：单用户模式断言回退身份 + `is_self`；多用户模式（monkeypatch `auth_enabled=true`）断言 401 |

### 顺带修掉 1 条「绿着但什么都没保护」的断言

`test_main_app.py::test_root_alias_count_matches` —— 这条**在 HEAD 上是绿的**，**不是** pytest 失败，
是 `ruff` 的 **F841（局部变量 `root_gets` 赋值后从未使用）** 顺带把它挖出来的：

```python
root_gets = [ ... ]                      # 辛苦算出来的
assert len(ROOT_ALIASES) == 18, "..."     # 却断言的是另一个常量
```

`ROOT_ALIASES` 是**测试文件里自己写的列表** ⇒ 「常量 == 常量」，两边都是人肉同步的 ⇒ 保护不了任何东西
（alias 悄悄增删时它不红；同时删一条又加一条时它也不红）。

改成两条**真断言**：

- `test_root_alias_paths_match_app` —— 与 `app.routes` **双向集合比对**（两边多出什么都红）
- `test_root_alias_targets_are_static_pages` —— 逐条查跳转目标文件**真实存在**
  （目标写错成 `/static/trend.htm` 线上表现是「点导航 → 404」）

### 断言本身的病根：写死的个数

这 10 条失败里有 **3 条**（`test_scripts_check_routes.py`）是同一个病：**断言「个数」而不是「集合相等」**。
再加上 ruff 顺带挖出的那 1 条绿着的（`test_root_alias_count_matches`），一共 **4 处**同源。

- 数目对不上 ⇒ **恒红**（人肉同步失败时它不是变红而是永远红着）
- 数目碰巧对上但内容错了 ⇒ **假绿**（比如同时删一条别名，总数不变）

改法统一成**集合相等**：`routes == set(EXPECTED_ALIAS_PATHS) | set(EXPECTED_REFLECTED_EXTRA)`。
两边多出什么都红。

### 「断言必须先剥注释」的老教训在这轮又应验了一次

`test_main_app.py` 的旧断言 `assert len(ROOT_ALIASES) == 18` 里，
它精心算出来的 `root_gets` 列表**从头到尾没被用过** ——
断言的是「常量 == 常量」，而两个常量都是人肉同步的 ⇒ **保护不了任何东西**。
新断言直接拿 `app.routes` 做比对，并**逐条查跳转目标文件真实存在**
（目标写错成 `/static/trend.htm` 线上表现是「点导航 → 404」）。

### 测试数对账：一个测试都没被静默丢掉

修 10 条失败时顺手把「5 删 7 增」也算清楚，避免「修着修着少了几条没人知道」：

```bash
git worktree add --detach /tmp/wt_head HEAD          # 干净 HEAD
pytest --collect-only -q | grep "::" | sort > head.txt   # 1831
pytest --collect-only -q | grep "::" | sort > work.txt   # 1833
comm -23 head.txt work.txt   # HEAD 有、工作区没有 → 5 条（全部有名字）
comm -13 head.txt work.txt   # 工作区新增          → 7 条（全部有名字）
```

**净 +2**（5 删 7 增），逐条对得上，没有一条「消失得莫名其妙」。

### 新增门禁：`scripts/_verify_i18n_keys.mjs`

本轮改了 3 处 i18n，pytest 的 `test_i18n_coverage` 只能证明「键存在」，
证不了「**文案真的被翻译到 DOM 上**」。补一条实跑门禁（23 条断言）：

- `/ask` 的 `placeholder` 在 **zh-CN / en-US / zh-TW** 三语下都是**对应语言的文案**
  （查 `getAttribute("placeholder")` 的值，**不是**查 `data-lang`）
- `data-i18n-attr` 死属性**零残留**
- 警示 chip / 关闭文案在三语下都被翻译
- 4 个改动过的键在 3 语下 `i18n.t()` 都能取到**非空**值

⚠️ **反向验证过**：把 `data-i18n-placeholder` 改回 `data-i18n-attr` 后，
门禁真的红 3 条（zh-CN 那条仍绿 —— 因为 HTML 字面量恰好就是中文文案，符合预期）。
「只绿一次」不算门禁。
