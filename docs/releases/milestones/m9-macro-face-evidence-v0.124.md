## 二、为什么必须先补历史深度

V0.122.0 曾给过一个数：「宏观面 composite 在 h=60 上前瞻偏相关 **−0.107**、回看 **+0.329**」。
V0.123.0 已经指出那个数**不能用**，但当时只能说到「样本太少」为止 —— 没有补测。

补测前，生产库 `daily_macro_factors` 的实测状态（2026-11-09）：

| 项 | 实测 | 后果 |
|---|---|---|
| 时间跨度 | **201 天**（2026-02-16 → 2026-11-09） | 20 年历史只覆盖 10% |
| 7 个日频因子 | 各 ~188~200 行 | 勉强够 252 日滚动窗口 |
| 4 个低频因子 | `cb_gold` 33 / `cn_gov_debt` 14 / `eu_gov_debt` 14 / `us_gov_debt` 14 行 | **几乎为空**；且 `cn_gov_debt` 14 行**全是 88.327**（一个常数） |
| h=60 非重叠采样后 | 整段只剩 **~3 个样本** | 任何统计都不可用 |

⇒ 宏观面 35% 的权重，其中 **34%**（4 个低频因子）在**一个常数**上骑了半年。
⇒ **结论不是「宏观面没前瞻力」，而是「宏观面还没被测过」。**

**本版把前置条件补齐了**：见 §三。

## 三、交付物 ①：历史深度（2 万行）与它带来的口径修正

### 3.1 回填口径 = 「把每日采集流水线重放一遍」

| 维度 | 口径 | 为什么 |
|---|---|---|
| 行粒度 | **日历日**（周末也写一行） | 线上 `daily_capture_loop` 每天 07:00 触发、**无星期过滤** ⇒ 库里天天有一行；滚动分位窗口是 252 **日历**日 ⇒ 只写交易日会让窗口样本数与线上不一致 ⇒ P10/P90 不同 ⇒ 「复算」就不是生产口径 |
| point-in-time | 每个日历日 D 取「**D 当时能拿到的最新真实读数**」 | 前视是这个题目的头号风险 ⇒ 必须能证伪（§五·X2） |
| 因子覆盖 | **11 个**（7 日频 + 4 低频） | 低频 4 个合计 **34% 面内权重**，不能缺席 |
| 窗口 | **5 年**（1825 自然日） | roadmap C6 要求 ≥3 年；5 年给 252 日滚动窗口留两次余量，也给「三段各 ~1.7 年」留空间 |
| 幂等 | upsert 按 `(target, snapshot_date, factor_key)` 覆盖 | 重跑不脏；重跑即订正 |

**实测写入量：20086 行**（dry-run 与实跑一致）：

```
cb_gold 1826 · cn_gov_debt 1826 · curve_10y2y 1826 · dxy 1826 · eu_gov_debt 1826
real10y 1826 · us10y 1826 · us2y 1826 · us30y 1826 · us_gov_debt 1826 · vix 1826
```

⚠ **上线的第一版是 20085 行、且整批回滚了两次** —— 见 §三·3.4 的两个真实缺陷。
最终这 20086 行与脚本重建**逐行相等**（X1 绿，§五·5.2）。

### 3.2 ⚠ 发布时滞模型（本轮最重要的口径发现）

回填要回答「**这个读数当天到底看得见吗**」。不建模就等于把未来的读数写进历史 ⇒ 整轮测量作废。
本轮的时滞**不是拍脑袋的常数**，而是从生产表**逐行反推**出来的
（读 `snapshot_date − data_date`，逐源逐段核对，**22 个采集日 × 3 个源逐行核对通过**）：

| 源 | 可得日规则 | 实测依据 |
|---|---|---|
| H.15（us2y/us10y/us30y/curve） | `next_business_day(观测日) + 1 天` | H.15 按 T+1 工作日 16:15 ET 发布；采集在 07:00 北京（= 前一天 23:00 UTC）⇒ 当天早上还拿不到 |
| FRED 日频（real10y/vix） | 同上 | 同 H.15 的发布节奏 |
| Yahoo（dxy） | `观测日 + 1 天` | Yahoo 收盘后才出当日线 |
| `us_gov_debt` | 期末 + **122** 自然日 | **切换点精确值**（2026-10-30 那一行的实测差） |
| `eu_gov_debt` | 期末 + **119** 自然日 | 首次出现 ⇒ **上界** |
| `cn_gov_debt` | 期末 + **665** 自然日 | 首次出现 ⇒ **上界**（年度序列 + FRED 发布滞后） |
| `cb_gold` | 期末 + **39** 自然日 | **切换点精确值**（2026-11-08 那一行的实测差） |

⚠ **误差方向是保守的**：低频三个是**上界**（真实发布只会更晚）⇒
「更晚可得」= 更少前视 ⇒ 若低频组仍不过三问，**结论只会更保守**、不会更宽松。

⚠ **一个真实的坑**：源字符串在库里是 `"Yahoo DX-Y.NYB"`，不是 `"yahoo"` ——
原先按 `source == "yahoo"` 判断的分支**永远不进**，Yahoo 会被错配成 H.15 的工作日规则。
修法是**小写子串匹配**（`"yahoo" in source.lower()`）。

### 3.3 单一真源：脚本与生产回填共用一份「源数据 → 观测」映射

原先的隐患：生产回填与证据脚本**各抄一份**映射 ⇒ 迟早漂。
本版把映射抽到 **`src/app/services/macro_history.py::build_observations`**，
**两侧都调它** ⇒ X1 交叉验证才有意义（§五）。

### 3.4 ⚠ 上线时撞到的两个真实缺陷（都是**写库那一刻**才暴露的）

dry-run 只打印行数，**不碰数据库** ⇒ 这两个缺陷在 dry-run 里**一个都看不出来**。

| # | 缺陷 | 症状 | 根因 | 修法 |
|---|---|---|---|---|
| **1** | **一条 SQL 写 2 万行 ⇒ 整批回滚、零行落库** | `sqlite3.OperationalError: too many SQL variables`（**退出码 1**，表里**一行都没多**） | SQLite 单语句绑定变量上限 `SQLITE_LIMIT_VARIABLE_NUMBER`（本机实测 **32766**），每行绑 **6** 个 ⇒ 2 万行 = **12 万**个变量 | `MacroFactorHistoryRepository.upsert_many` 改为**分块**（`UPSERT_CHUNK_SIZE = 1000` 行/块 ⇒ 6000 变量，离上限 5 倍余量）；语义不变（仍按同一唯一键幂等覆盖） |
| **2** | **窗口第一天的 DXY 整行缺失** | X1 报「只在脚本：1」⇒ `2021-11-10 dxy` 脚本有、生产表没有 | Yahoo 是**唯一按窗口取数**的源（H.15 / FRED / Eurostat 都是全量历史）⇒ 窗口第一天拿不到「窗口之前最后一次收盘」 | 取数起点前置 **`YAHOO_LOOKBACK_DAYS = 30`** 天；窗口前的观测本来就必须保留（`asof_rows` 自己挑「可得日 ≤ 该天的最后一条」） |

⚠ **缺陷 1 的教训**：**「dry-run 通过」≠「写库能成」**。
dry-run 走的是同一条重建函数，但**不执行那条 INSERT** ⇒
真正的失败点在**数据库的参数上限**上，只有真写才暴露。
⇒ 以后凡是「大批量写」类改动，dry-run 之后必须再跑一次**真写**（有备份兜底）。

⚠ **缺陷 2 的教训**：**回放型回填的第一行最容易丢**。
「窗口起点」是一个**人为的边界**，而真实流水线的第一天用的是**窗口之前**的读数
⇒ 凡是「按区间取数」的源，都必须留**回看余量**。

> ⚠ **这张表是「同一份行情快照」下的前后对照**（BEFORE 跑在回填前的备份库副本上，
> AFTER 跑在回填后的库上，**行情数据完全相同**）⇒ Δ 列只反映**宏观面**的影响。
> ⚠ **综合指数本身还会随行情动** —— 它含技术面 / 消息面 / 资金流面，
> 那三面跟着金价走 ⇒ **线上读到的综合指数不等于表里的 42.2**
> （实测本轮发版时线上读数已是 **38.9**，而**宏观面仍是 45.5** ⇒ 与本表一致）。

**怎么读这张表**：

- **只有 3 个因子动**（`us10y` / `us30y` / `real10y`，加上 `dxy` 在**截断边界**上的 −0.6）
  ⇒ 它们是**收益率类**因子 —— 旧窗口里混着**交易日行**（样本少、分布偏），
  换成 252 个日历日（周末重复值也进窗口）后分位带略动。
- **4 个低频因子一分没动**（它们恒用**静态带**，不受历史长度影响）⇒
  ⚠ 这也说明「补历史深度」**没有**改变低频组的表现 —— 它们的分数从来不是靠样本算出来的。
- **宏观面总分只动了 −0.3**（45.8 → 45.5）⇒ **回填不实质改变宏观面**。
- ⚠ **写库前的离线预判**（用 20 年重建缓存算的）预测的是
  `us10y −3.00 / us30y −2.12 / real10y +0.78 / macro 45.70 → 45.47` ——
  三个主要变动与实测**一致**（−3.0 / −2.1 / +0.8），
  差别在 `dxy`（预判 0.00、实测 −0.6：`dxy` 的分数被**截断在 0**，
  带稍动一点就跨界）⇒ 预判可用但**不等于线上**，最终以线上实测为准。

### 5.2 两层交叉验证（本轮最硬的两条断言）

| 断言 | 内容 | 实测状态 |
|---|---|---|
| **X1 · 脚本重建 ≡ 生产表** | 同一套重建函数产出的 (日期, 因子, 值, data_date, source) 与生产库**逐行相等**（容差 1e-9） | ✅ **绿**：重叠区间 2021-11-10 ~ 2026-11-09 ⇒ **逐行相同 20086 / 不同 0 / 只在一侧 0** |
| **X2 · 口径守卫** | 撤销重建里的 point-in-time（把可得日退回观测日）⇒ X1 **必须变红** | ✅ **守卫生效**：前视版**逐行不同 17540**（相同仅 2546）⇒ 守卫能判红 |

⚠ **X1 的比较区间 = 双方的重叠区间**（本轮实测后修的判据，见 §五·5.5）。
脚本窗口是 **20 年**，生产表只回填了 **5 年** ⇒ 脚本多出的那 5475 天
**不是不一致，只是生产表还没回填到** ⇒ 把它算进失败会让 X1 **永远红**
⇒ 判据失真 = 等于没有判据。

### 5.3 X1 在深回填之前是红的 —— 而且红得有道理

**在深回填之前跑 X1**（把 `DATABASE_URL` 指到回填前的备份库，同一份缓存、同一个脚本）：

```
逐行相同：148    逐行不同：1278    只在脚本：785    只在生产表：0
2026-02-17 dxy   脚本=(96.880, '2026-02-13', 'Yahoo DX-Y.NYB')   生产=(97.160, '2026-02-17', …)
2026-02-17 us10y 脚本=(4.04, '2026-02-13', '美联储 H.15')          生产=(4.05, '2026-02-17', …)
```

⇒ 旧采集口径把**当天才发布的读数**写成了当天可见 ⇒ **旧生产表本身带前视**。
这正是「为什么必须建模发布时滞」的实证，也是 X1 该有的样子 ——
**它不是装饰，是尺子**：尺子能把旧表量出问题，才说明这把尺子准。

⚠ **这就是 X1 的反向验证**：同一把尺子、同一个缓存，
**换一个（旧的）生产表 ⇒ 立刻变红（退出码 1）** ⇒ X1 不是恒真的装饰。

**同一把尺子量出来的另外两个真实缺陷**（都由本轮回填修掉）：

| 缺陷 | 实测 | 修法 |
|---|---|---|
| **静态兜底值被写进了历史表** | **15 行** `source='静态参考值'`（dxy 96.5 / vix 18.5 / us10y 4.4 / us30y 4.9，data_date 2026-08-28）躺在 2026-10-10 ~ 10-25 的窗口里 | 深回填按 point-in-time 重建覆盖 ⇒ 那 15 行变成真实读数（回填后 `source='静态参考值'` 的行数 = **0**） |
| **`cb_gold` 33 行是旧口径** | 842.6 吨（各国行求和 = **重复计数**） | 覆盖为 WGC **合计行**滚动 4 季（V0.121.4 的口径） |

### 5.4 离线测试（脚本口径 23 条 + 本轮新增 4 条回归，全不联网）

| 组 | 条数 | 守住什么 |
|---|---|---|
| **X1 离线版** | 1 | 脚本重建 ≡ 生产回填**逐行相等**（同一批桩数据） |
| **X2 离线版** | 1 | 撤销 point-in-time ⇒ **必须**与生产回填不同 |
| 行粒度 | 2 | 每个日历日一行（含周末）；第一条观测前**不写行**；低频因子按实测滞后才出现 |
| 打分口径 | 6 | 低频恒用静态带；日频走滚动带（改历史 ⇒ 分数变）；负号因子方向；分数 ∈ [0,100]；组内权重归一化；11 因子分组与权重合计 1.0 |
| 候选口径 | 2 | 尾随 z 分数**不用未来数据**；样本不足 60 不给值 |
| 三问判决 | 6 | 门槛 / 比值不足 / **分母趋零判不可判** / 三段不同向 / 缺段判不过 |
| **正/负对照** | 2 | **合成真信号必须判过**（pc_fwd 0.947、比值 4.37）；**白噪声必须判不过** |
| 不隐式联网 | 2 | 无 cache ⇒ 退出码 2；只给 cache ⇒ 不调取数函数 |
| **★ 分块写**（本轮新增） | 2 | 一次写入的行数**超过 SQLite 单语句变量上限** ⇒ 必须成功；分块后重跑仍幂等（`tests/test_repositories/test_macro_factor_history.py`） |
| **★ Yahoo 回看余量**（本轮新增） | 2 | 取数起点必须早于窗口起点；窗口第一天必须用**窗口之前**的观测播种（`tests/test_services/test_macro_backfill.py`） |

⚠ **正对照是本轮最有价值的一条新断言**：若机器对**真信号**也判不过，
那「宏观面全部未通过」就毫无意义（测不出 ≠ 没测）。现在机器在合成真信号上
`pc_fwd = +0.947 / 比值 4.37 / 三段全正 ⇒ 判过`，在白噪声上判不过。

⚠ **五条关键断言都做过反向验证**（撤销修复 ⇒ 必须变红）：

| 撤销了什么 | 结果 |
|---|---|
| 改脚本重建口径（X1） | X1 变红 |
| 把前视守卫改成恒等（X2） | X2 变红 |
| 去掉 `skip_rolling`（静态带） | 变红 |
| **关掉分块**（`UPSERT_CHUNK_SIZE = ∞`） | **重现** `sqlite3.OperationalError: too many SQL variables`（与生产报错逐字相同） |
| **去掉 Yahoo 回看余量** | **2 条**变红 |

### 5.5 ⚠ 一处判据的修正（X1 的比较区间）

X1 最初的写法是「脚本窗口内的行必须全部在生产表里逐行相等」。
**它在本轮会永远红** —— 因为脚本窗口是 **20 年**、生产表只回填 **5 年** ⇒
脚本多出的 **5475 天**（≈ 5.7 万行）根本不是「不一致」，只是**生产表还没回填到**。

修法：比较区间改成**双方的重叠区间**（`script_dates ∩ prod_dates`），
并把「脚本窗口更长、生产表未覆盖的那段」单独打印出来（不计入判据）。

⚠ **这个修正没有削弱判据**，两处证据：
① **X2 照样能判红**：撤销 point-in-time 后，重叠区间内 **17540** 行不一致 ⇒ 守卫生效；
② **X1 本身可判红**：把 `DATABASE_URL` 指到回填前的备份库 ⇒ **1278** 行不一致、退出码 1（§五·5.3）。

⚠ **教训**：**判据失真比没有判据更坏** ——
一个永远红的断言会让人养成「红是正常的」的 ⇒ 真红时反而看不见。
