## 一、测试基础设施：`database is locked`（任务 #164）

### 现象

`tests/test_api/test_async_backtest.py` 本地跑 **1 passed / 10 errors**，而
**CI 是绿的** —— 时序不同掩盖了问题，于是本地无法完整回归、只能靠 CI。

### 走了四轮才定位到真根因（前三轮都是错解）

| 轮次 | 做法 | 结果 |
|---|---|---|
| 1 | 清后台任务集合 | 仍锁 |
| 2 | `cancel() + gather()` | `RuntimeError: Event loop is closed` |
| 3 | 按 loop 归属过滤 + `loop_scope=session` | 仍锁 |
| 4 | `engine.dispose()` 前置 | **偶发通过**（11 passed ↔ 10 errors 随机） |

⚠ **第 4 轮的「成功」是误判** —— 复跑立刻又失败。当时据此做了负向验证
（移除 dispose ⇒ 复现 10 errors），看似因果已确认，其实是随机时序骗了我。

### 真正的根因：engine从未配置 SQLite 并发参数

`repositories/db.py` 的 `create_async_engine()` **没传任何 `connect_args`**：

- **WAL 模式只在 `main.py` 启动路径设置**（`ensure_sqlite_optimizations`），
  而**测试完全不经过 `main.py`** ⇒ 测试库从未开 WAL ⇒ 读写互相阻塞；
- **`busy_timeout` 未设** ⇒ SQLite 默认**立即抛锁错误**而非等待重试。

配套三环：① `engine` 是模块级单例（导入时创建）⇒ 连接池绑定**第一个**event loop；
② pytest-asyncio 默认**每个测试函数新建 loop**；③ 上一用例遗留的 pooled 连接
未 check-in ⇒ 本用例 `drop_all` 在旧连接上执行。

### 修法

- `connect_args={"timeout": 30.0}`（SQLite 场景）
- `@event.listens_for(engine.sync_engine, "connect")` 在**每条新连接**上执行
  `PRAGMA journal_mode=WAL` + `PRAGMA busy_timeout=30000`
  ⚠ 必须在 connect 事件里做 —— 连接池会新建连接，启动时对单条连接执行一次不够
- `:memory:` 库跳过 WAL（开 WAL 会报错）
- `tests/conftest.py`：`drop_all` 前 `await engine.dispose()`

⚠ 写在 engine 而非启动流程，是为了让**测试与生产共用同一套语义**。

### 验证

- **连跑 3 遍全绿**（11 passed / 23s / 23s / 23s）——
  ⚠ 耗时从 **63s 降到 23s** 是决定性证据：不再有 5 秒超时等待重试
- **本地全量回归 1101 例全绿**（8 分 28 秒）—— 这是本主题的**实际收益**

### 附带：`.gitignore` 补 WAL/SHM

`.gitignore` 此前只有 `*.db-journal`，**缺 `*.db-wal` / `*.db-shm`**
—— 而项目 V0.73.0 起就开了 WAL，这两个文件一直在被生成却未被忽略。
本版把 WAL 下沉到 engine 层后，它们**每次跑测试后都出现**（首次提交时被
`git add -A` 误带入）。

## 二、数据隔离第 2 批（任务 #159）

### 背景

第 1 批（2026-10-06）只做了 `positions` / `accounts`。
**这三张表当时连 `user_id` 列都没有**：

| 表 | 泄露面 |
|---|---|
| `news_scores` | A 用户的打分（含 `basis` 研判依据与 `review_note` 复盘批注）可被 B 读到 |
| `analysis_records` | 机会分析记录（含因子明细与评分）跨用户可见 |
| `push_subscriptions` | 按 `endpoint` 单列匹配 ⇒ 同设备换用户会覆盖密钥，推送到错的人 |

⚠ **最严重的一条**：B 用户提交打分会命中 A 用户的记录并**直接覆盖**，
而 `basis` 在 UPDATE 分支是**硬覆盖**（V0.77.2 已知）⇒ 不可逆丢失。

### ⚠ 施工中发现两个必须一并改的隐藏缺陷

**① `news_scores` 唯一键不含 user_id ⇒ 两用户根本无法共存**

加列后实测 Bob 在与 Alice 同日同槽位提交直接
`IntegrityError: UNIQUE constraint failed`。**这不只是测试问题** ——
它意味着「每个用户各自打分」在数据库层被禁止，多用户下第二个人用不了打分功能。
⇒ 唯一键 `(score_date, slot)` → `(user_id, score_date, slot)`。

⚠ 连带：`db_migrate` 的键声明 + 新增 `LEGACY_UNIQUE_INDEX_DROPS`
（**必须先删旧索引再建新的**，否则旧键仍在生效 ⇒ 数据隔离形同虚设）。

**② SQLite 改唯一键的两个坑**

- `op.create_unique_constraint` 在 SQLite的 alembic dialect **不支持**
  （`NotImplementedError: No support for ALTER of constraints`）
  ⇒ 改用 `CREATE UNIQUE INDEX`（语义等价，索引名与 ORM 对齐以利排查）；
- **重建表只复制数据，索引不会跟着走** ⇒ 两张表的 `user_id` 单列索引都要补建。

### 仓储层改造（「加列」不是重点，「有人读它」才是）

- `NewsScoreRepository`：**9 个方法**全部加 `user_id` 参数 + `resolve_user_id`
  ⚠ **`upsert` 的 `existing` 查找必须按 user_id 过滤** —— 否则 A 用户提交会命中
  B 用户同日同槽位的记录并覆盖它
- `AnalysisRepository`：`create` 落库带归属、`list_recent` 按用户过滤
- `PushSubscriptionRepository`：查找键 `(user_id, endpoint)`；
  `archive` / `delete` 跨用户一律 False

### `ALL_USERS` 显式哨兵值

⚠ `list_active` 的两个调用方是**服务级操作**：`notify.py` 告警广播、
`push.py` 管理员验证推送。若依赖「忘了传 ⇒ 不过滤」的默认行为实现全库查询，
等于把越权藏在默认值里 —— 后来者补上真实 user_id 时行为会**静默改变**。

⇒ 新增 `user_scope.ALL_USERS = 0`（真实 id 从 1 起，不冲突），两处显式传参。

### 测试（14 例）

`tests/test_services/test_user_isolation_batch2.py`，沿用第 1 批的 `acting_as`
上下文管理器（⚠ 不能用「同步夹具 set + teardown reset」——
`contextvars.Token` 只能在创建它的 Context 里 reset，pytest-asyncio 每用例独立
Context 会报错）。

覆盖：跨用户读不到 / **跨用户 upsert 不覆盖**（最严重）/ 跨用户撤销 False /
区间查询与「沿用上次」隔离 / analysis 落库与过滤 / push 同端点两用户共存 /
`ALL_USERS` 全库 / 单用户模式回归。
