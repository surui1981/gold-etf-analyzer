# V0.114.0 · 新闻多源容灾

> 日期：2026-10-22 ｜ 类型：数据源容灾 + 既存缺陷修复 ｜ 无 UI 布局变更
>
> 一句话：今日要闻从**单点**（readhub）改成 **4 源链式 failover**，任一源挂了仍有输出；
> 顺带修掉两个让「收藏」从头到尾**没有任何反馈**的既存缺陷。

## Context

用户给出三个新闻源，要求「互为冗余，单点挂了还有输出」。实测确认三源全通，但现状是
**只有 readhub 一个源**，而这轮实测中 readhub **直接超时了一次** —— 单点无冗余不是理论
风险，是已经发生过的事。

## 实测数据（本机，非文档推断）

| 源 | HTTP | 耗时 | raw | classify 后 | title | URL |
|---|---|---|---|---|---|---|
| 华尔街见闻 `api-one.wallstcn.com` | 200 | 0.28s | 30 | 20（科技 11 财经 9） | **22/30 为空**（快讯只有 `content_text`） | ✅ `uri` |
| 金十数据 `flash-api.jin10.com` | 200 | 0.39s | 21 | 20（科技 14 财经 6，0 其他） | 0/21 | ❌ 无 |
| 东方财富 `np-listapi.eastmoney.com` | 200 | 0.33s | 30 | 23（科技 10 财经 12 创投 1） | 30/30 | ❌ 无 |
| readhub（原有兜底） | 200 | — | 20 | — | 有 | ✅ |

关键事实：

- 华尔街见闻与 readhub 标题**仅 2 条重合** ⇒ readhub 是真正的第 4 个独立源，不是冗余重复
- **金十 / 东财实测 0/20 条有 url 字段** ⇒ url 必须可空，且无链接时卡片不可点
- 金十 `id` 是 **20 位数字串**（`20261022052115590800`）⇒ 超出 JS `Number.MAX_SAFE_INTEGER`
  **2249 倍**，也超出 SQLite INTEGER（int64）⇒ 列类型必须 `String(32)`
- 金十 / 东财的 `time` / `showTime` **不带时区** ⇒ 按 BJT 解释
- 东财成功码是**字符串** `"1"`：`payload.get("code") != 1` 会把成功当失败（踩过）

## 已确认的三个决定

1. **4 源链式 failover**：wallstcn ★ → jin10 → eastmoney → readhub（readhub 降为末位兜底）
2. **首个足量即止**：`len(items) >= MIN_ITEMS(=10)` 即返回，不做四源合并
3. **url 改可空，无链接时卡片不可点** —— 不合成假链接（V0.77.1 不给假 affordance）

## 改动

### C1 · migration + 模型

新 `migrations/versions/q3r4s5t6u7_news_feed_multi_source.py`（revision `q3r4s5t6u7`，
down_revision `p2q3r4s5t6`），`batch_alter_table`（SQLite 不能直接 ALTER）：

- `news_feed_items`：`external_id` **Integer → String(32)**；`url` → nullable；
  删 `uq_news_feed_external_id`，建 `uq_news_feed_source_external(source, external_id)`
- `user_news_favorites`：`news_external_id` → String(32)；`url` → nullable
- ⚠️ 计划里写的是 BigInteger，**实测推翻**：SQLite 的 `INTEGER` 是 **int64**（上限
  ≈9.22e18），而金十 id ≈2.02e19 —— `OverflowError: Python int too large to convert to
  SQLite INTEGER`。改成 `String(32)` 后又发现直接构造 ORM 传 int 仍溢出（绑定发生在
  Python 侧，早于 SQLite 的 affinity），因此加 `models/base.py::SourceId` TypeDecorator，
  `process_bind_param` **永远**以文本绑定
- ⚠️ `downgrade()` 自述**不可逆**：复合 UNIQUE 恢复不了，String 也退回不了 Integer
- `_table_exists()` 幂等守卫必须带 —— `main._migrate_db()` 在 alembic 失败时回退
  `Base.metadata.create_all`，两条路径都跑过时第二次启动会炸

### C2 · fetcher + failover 注册表

新 `src/app/repositories/news_sources_fetcher.py`：3 个源各一个 `_normalize_*`，输出与
`readhub_fetcher._normalize` **完全一致的 dict 形状**（含 `source`），共用 `classify()` +
弃入「其他」+ 共享 `SITE_BLOCKLIST`；`SOURCES` 注册表 + `fetch_news_feed()` 链式 failover，
首个足量即返回，全挂抛 `NewsSourceError` 并列出每源失败原因。

**readhub_fetcher 一行不动**（28 个现有测试依赖它），只作为注册表末位参与。

### C3 · service / scheduler 接线

`fetch_readhub_feed` → `fetch_news_feed`；refresh 返回值加 `source`（哪个源赢了 ——
让 failover 对外可见）；顺手修 `main.py` 日志写死 `every 6h: 00/06/12/18 UTC`（实际 4h）
与 `scheduler.py` 指向不存在的 `app.scripts.refresh_news_feed`。

### C4 · 收藏链路打通 source

多源后 `external_id` **不再全局唯一** —— 同一个数字可能同时是华尔街见闻的 `3182985` 和
金十的某条。原先前端两处硬编码 `source=readhub`、POST 不传 `news_source`，会收藏到
「另一条同号新闻」。`headlines.js` / `home.js` / `favorites.js` 三处全部改成按
`data-source` 定位与提交；`user_news_favorite.py` 两处 `missing` 去掉 `"url"`（否则金十 /
东财条目**永远收藏不了**，422）。

⚠️ 这里踩了一个自己造的回归：把 `url` 移出 `missing` 清单后，payload 兜底那次拷贝也
跟着没了，**外部 URL 直传的收藏静默丢掉链接**（不报错、收藏成功、点不开）。由
`test_external_url_still_works` 抓到，已补显式兜底。

### C5 · i18n ×3

新增 6 key（`headlines.source_*` 4 + `no_url_title` + `fav_add`）× 3 语。

⚠️ 我自己写的注释里含 `tr("headlines.source_" + key, ...)`，被 `check_i18n_keys` 的
`tr_call_re` 当成真调用，凭空造出 3 个「缺失 key」。注释要避开门禁的字面量形态。

## 顺手修的既存缺陷：收藏从头到尾没有任何反馈

puppeteer 实跑点收藏时冒出一条 `PM_Toast.show is not a function`。顺藤摸下去是**三层**：

| 层 | 现象 | 谁坏 |
|---|---|---|
| ① | `toast.js` 只导出 `info/success/warn/err`，**从未导出 `show`**，而全站 **14 处**在调 `PM_Toast.show(...)` | 自 V0.98 C3 起 |
| ② | `headlines.js` / `home.js` 的 guard 只查 `window.PM_Toast`（对象在）⇒ 抛 TypeError；`favorites.js` / `report-archive.js` guard 查到 `.show` 为 falsy ⇒ 静默不弹 | 同上 |
| ③ | `headlines.js` **模块作用域没有 `t()`**，却在处理器里裸调 `t("favorites.toast_archived", ...)` ⇒ `ReferenceError`，且抛在 **catch 块内**无人接管 ⇒ 未处理拒绝 | 同上 |

三层的**用户可见后果完全一样**：点了收藏，POST 成功了，屏幕毫无反应。

修法：`toast.js` 补 `show(msg, type)` 派发器（一次性修好全部 14 处，含 `error`→`err`
别名与「未知值退回 info 绝不抛错」）；`headlines.js` 两处改 `tr()`。

⚠️ `headlines.js` **故意**不叫 `t()`：本页 `fmtBjtDate()` 内部有 `const t = new Date(iso)`
（124 行），同名会把翻译函数在那个函数体内整个遮蔽，是留给下一个人的地雷。
⚠️ 我的教训：加翻译助手前先 grep 本文件有没有同名调用方，别默认「全站惯例是 `t()`」——
本轮就是我加了 `tr()` 却没发现旁边 2 处 `t()` 一直是坏的。

## 验证

### 端到端 failover（真重启 uvicorn，5 种场景）

| 场景 | 结果 |
|---|---|
| 基线（4 源都在） | `ok=True source=wallstcn upserted=21` |
| A wallstcn 不可达 | `ok=True source=jin10 upserted=16` |
| B wallstcn + jin10 不可达 | `ok=True source=eastmoney upserted=16` |
| C 三个新源全挂 | `ok=True source=readhub upserted=14` |
| D 四源全挂 | HTTP **200**、`ok=False`、error 列出全部 4 源；`/items` 仍供末次数据 |

⚠️ 场景 D 返回 200 是**刻意**的（V0.84：绝不 500，绝不在用户可见路径上显示红框）。

⚠️ 第一版 failover 验证是**无效的**：`sed` 改文件不影响已在跑的 uvicorn，5 个场景全返回
`wallstcn`。改成每场景重启服务（`run_in_background` + `TaskStop`，不用 `pkill` ——
它会把 shell 一起杀掉，exit 144）才拿到上面的真结果。

### puppeteer（1352×900，实跑 23 条断言全绿）

钉死的 5 件事，每条都对应一个「不跑浏览器就发现不了」的缺陷：

1. 4 源卡片都渲染出来（failover 换了源，UI 不能跟着瞎）
2. 无链接条目的标题**不是 `<a>`** —— 原先 `it.url || "#"` 是假 affordance；实测
   68 张有 `<a>` / 32 张是 `span.no-url` 纯文本
3. fav 按钮带 `data-source`，POST 带 `news_source`，且 `external_id` **全程字符串**
   （点金十 `20261022055128917800` → POST 原样透传；先前 `parseInt` 会静默舍入到
   …7000，收藏落到不存在的行）
4. 点收藏后**真的弹出 toast**
5. 3 语都无 i18n key 字面量泄漏

**脚本本身也修了两次**：① 只绿一次不算门禁 —— 第二轮点同一张卡必然 409 幂等分支，
改成点击前经 API 删掉上一轮收藏；② 只断言「请求发出去了」不够，服务端 4xx 时前端同样
会发请求，补了真实响应码断言（顺手发现 POST 返回 **201** 不是 200，写死 200 会自己把
自己判红）。

## 已知遗留

### `test_list_items_filter_days` 失败（既存，本轮未修）

已用 `git stash` 在**未改动的 main** 上复现同样失败 ⇒ 与本轮无关。

根因：种子数据把日期硬编码成 2026-10-19/18/17，而测试假设 10-19 ≈「今天」；今天 10-22，
`days=1`（cutoff 10-21）把全部行过滤掉。

**不修的理由**：修它要连带改 4 个测试的语义（tz-offset 用例的期望 id 会从 1002 翻成
1001、`has_newer` 翻成 False），会让发版 diff 里混进一堆与新闻源无关的改动，反而更难审。
建议单独一轮把「相对日期」改成从 fixture 的基准日推算。

### favicon 全站 404（既存，纯装饰）

20 个页面都没有 `rel="icon"`，服务端也没有 `/favicon.ico` 路由 ⇒ 浏览器每次访问都打一个
404。与本轮无关，验证脚本已豁免并**在输出里显式列出豁免项**（不静默吞）。

### ⚠ 行情侧的独立故障（比新闻更要紧，不在本轮范围）

实测用户给的第二个话题（行情双源交叉验证）时发现：

- `push2.eastmoney.com` 与 `push2his.eastmoney.com` 从本机均 **HTTP 000**（不可达）
- `akshare fund_etf_hist_em` 抛 `ConnectionError: Remote end closed connection`

意味着 `AkshareGoldHistoryProvider` 的**主**黄金 ETF 历史源正在静默失败，每次 518880
历史抓取都退化到内嵌 V8 引擎的 sina 子进程。**待用户决定**是否单开一轮处理。
