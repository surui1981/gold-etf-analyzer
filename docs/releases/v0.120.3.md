## 〇 一页结论

**症状**：用户报「对话给出的格式 不方便阅读」，贴出的原文长这样：

```
我先查询今天的黄金行情及金价相关指标。]<]minimax[>[<invoke
]<]minimax[>["name":"get_market_data","arguments":{"query":"今天黄金现货价格、COMEX黄金期货、上海金Au99.99，以及涨跌幅和更新时间"}}
```

**这不是「排版丑」，是上游把它的原生 tool-call 协议当成正文吐了出来。**
`]<]minimax[>[` 是 miniMax 的协议哨兵，`<invoke` / `{"name":…}` 是它的内部调用格式。

**根因链（4 层，逐层剥）**：

| # | 层 | 事实 |
|---|---|---|
| 1 | **请求侧** | 回传给上游的会话**缺 assistant 的 tool_use 回合** ⇒ 协议畸形 ⇒ 上游 400 / 退化成本地协议 |
| 2 | **读取侧** | 历史库里 10 条 assistant 消息**已被污染**（落的就是协议原文）⇒ 打开旧对话照样是垃圾 |
| 3 | **工具层** | `get_user_portfolio` 调错类、`get_scoring_summary` 强制要 from/to ⇒ 工具 100% 报错 ⇒ 模型反复重试 ⇒ **正文为空** |
| 4 | **兜底层** | 工具轮次耗尽时没有「强制作答」路径 ⇒ 用户看到的是**空白回复**（不是格式问题） |

**修法**：请求侧补回合 + 读取侧清洗残留 + 工具层修真缺陷 + 加安全网兜底。

## 一、第 1 层：请求侧缺 assistant(tool_use) 回合（**主因**）

### 现象

用户看到的不是「格式不便阅读」，而是**协议原文**。这说明模型侧根本没走到「正常作答」，
而是在把内部调用格式当正文吐。

### 根因

Anthropic 协议要求 `assistant(tool_use) → user(tool_result)` **配对**。
原实现（`src/app/services/ai_chat/service.py`）在拿到 tool_use 后**只** append 了
`user(tool_result)`，**assistant 的 tool_use 回合从未回传** ⇒ 上游收到的是
「连续两条 user 消息，且 tool_result 找不到配对的 tool_use」。

### 直连上游的 A/B 证据

| 请求形状 | 上游响应 |
|---|---|
| `[user, user(tool_result)]`（缺 assistant 回合） | **HTTP 400** |
| `[user, assistant(tool_use), user(tool_result)]` | **HTTP 200 + 完整 Markdown 答案** |

### 修法

`send_message`（同步）与 `send_message_stream`（SSE）**两处**都补上：

```python
assistant_blocks = [{"type": "text", "text": response.text}] if response.text else []
assistant_blocks += [
    {"type": "tool_use", "id": tc.id, "name": tc.name, "input": tc.input or {}}
    for tc in response.tool_calls
]
tool_result_blocks = [
    {"type": "tool_result", "tool_use_id": tc.id, "content": result.content}
    for tc in response.tool_calls
]
messages.append({"role": "assistant", "content": assistant_blocks})
messages.append({"role": "user", "content": tool_result_blocks})
```

⚠️ 多个 tool_result 必须放在**同一条** user 消息里 —— 拆成多条同样是畸形会话。

### 历史回放也要修

`serializers.py::_to_claude_messages` 原来**整条跳过 tool 消息**、且**从不重建 tool_use 块**
⇒ 从第 2 轮起模型看不到任何工具数据。现在按「回合」重建：

- 回合里**只有 1 个** tool 消息 ⇒ 原生 `tool_use` / `tool_result` 块，id 严格配对
- 回合里**多个** tool 消息 ⇒ DB 只留了第一个 tool_use，无法 1:1 配对 ⇒ **退化成纯文本描述**
  （宁可退化也不能发「1 个 tool_use 对 N 个 tool_result」的畸形配对）

## 二、第 2 层：读取侧清洗残留协议标记

新会话不再产生垃圾，但**库里已有的 10 条污染行**还在（生产库实测：含哨兵即计）。
⇒ 读时清洗（`src/app/schemas/ai_chat.py::AIMessageOut` 的 `model_validator`）：
新行旧行**同时生效**，**不写生产库、不用迁移**，原始数据保留在库里作为证据。

清洗器 `src/app/utils/protocol_strip.py`（新）：

| 规则 | 处理 |
|---|---|
| 哨兵 `]<]minimax[>`（含 U+200B/200C/200D/2060/FEFF 变体） | 触发清洗；**没有哨兵则原样返回**（保护正常答案） |
| `<tool_call>` `</tool_call>` `<invoke` `</invoke>` `<ut>` 等标签 | 整段删除 |
| 形如 `{"name":…,"arguments":{…}}` 的整行 JSON | 整行删除（是协议载荷，不是正文） |
| 裸标识符前缀（如 `invoke_market_data`） | 删除 |
| 3 个以上连续空行 | 折叠为 1 个 |

⚠️ **只清洗 assistant 正文**：tool 消息正文**本身就是** JSON（含 `name` 键），
清洗规则 3 会把工具数据整段毁掉。

流式路径同样清洗（`claude.py::_iter_sse`）：用一个 `ProtocolStripper`
在**字节流**上边喂边清，跨 delta 切断的哨兵也能识别（哨兵长度 ≤15，窗口 24）。

**验证**：生产库 **10 条**污染行逐条过一遍 —— **4 条清成空**（本来就只有协议）、
**6 条保留可读散文**（含 `## 数据支撑` / `### 结论` 小标题）、**残留标记 0 条**；
正常消息**字节级不变**。测试里内嵌 **8 条**典型样本（覆盖上述两类形态）。

## 三、第 3 层：工具层的**真缺陷**（线上 100% 报错）

> 这两条是**旧缺陷**，不是本次引入的 —— 是「协议修好后工具真的跑起来了」才暴露出来。

### 3.1 `get_user_portfolio` 调错了类

原实现调 `self._position.equity_curve(...)` / `self._position.performance(...)`，
但生产 wiring 注入的是 **`PositionService`** —— 它**根本没有这两个方法**
（`PositionService` 只有 `summary` / `list_positions`；`equity_curve` / `performance`
在 **`PortfolioAnalyticsService`** 上）。

⇒ 结果恒为 `{"error": "AttributeError: 'PositionService' object has no attribute 'equity_curve'"}`
⇒ 模型拿到错误就反复重试工具 ⇒ 工具轮次耗尽 ⇒ **最终正文为空**。

**修法**：`main.py` 构造 `PortfolioAnalyticsService(pos_repo, market_repo)` 并注入
`ToolDispatcher(portfolio_service=...)`；`_exec_portfolio` 改为
`summary()` + `list_positions()` + `performance()` + `equity_curve(days=90)`。

### 3.2 `get_scoring_summary` 强制要 from/to

模型经常**漏掉** from/to ⇒ 原实现直接返 `{"error": "from/to required"}`
⇒ 模型拿到错误就反复重试同一个工具 ⇒ 轮次耗尽 ⇒ **正文为空**。

**修法**：缺省取「近 30 天」（与本 tool 的 mini_card「最近 30 天」口径一致），
schema 去掉 `required`，并在返回体里报告**实际使用的区间** ⇒ 不产生假数据。

### 3.3 模型不知道「今天是几号」

`get_scoring_summary` 要日期区间，模型算不出来 ⇒ 只能漏参 ⇒ 回到 3.2 的死循环。

**修法**：system prompt 加规则 9「今天是 YYYY-MM-DD（北京时间）」。
`cn_today(now=None)` **可注入**（测试不能把「今天」写死 —— 跨周末就是永久红）。

### 3.4 ⚠️ 这正是「桩藏住被替换的调用方」

`tests/test_services/test_llm_client.py::_FakePosition` **自己实现了**
`equity_curve` / `performance` ⇒ 5 条 tool 测试**全绿**，线上 100% 坏。

**通用解法（不依赖桩）**：用 `ast` 扫 `tools.py` 里真实的 `self._<svc>.<method>(...)`
调用（注释 / docstring 不算），逐个与**真实类**的方法集对账
⇒ `test_tool_dispatcher_calls_only_real_service_methods`。

⚠️ 用 `ast` 而不是正则：正则会把 docstring 里那段「原实现调
`self._position.equity_curve(...)`」的历史说明也扫进来 ⇒ 假红。

## 四、第 4 层：安全网 —— 正文为空时强制作答

工具连续报错 / 模型只发 tool_use ⇒ 整轮**没有正文** ⇒ 用户看到**空白回复**。

**修法**：`send_message` / `send_message_stream` 在整轮无正文时，补一次
**不带工具**的调用，让模型基于已有工具数据必须给出结论。

⚠️ 为什么不复用 `messages` 列表：那里面是 `assistant(tool_use)` / `user(tool_result)` 块，
miniMax 代理对 tool_use_id 配对极敏感（2013）。**纯文本 = 零协议风险**
⇒ 把「用户问题 + 已有分析 + 工具返回」压成一段文本。

失败不抛 —— 宁可正文为空也不要整轮 500。

### ⚠️ 安全网自己的坑：**上游已经报错了，还去白等一轮**

实测（线上）：miniMax 返回 **HTTP 429「已达到 Token Plan 用量上限」** ⇒
安全网**又调了一次上游** ⇒ 多等 ~15 秒，还是同一个 429。

⇒ 加 `llm_failed` 标志：3 个上游错误分支置位 ⇒ `if not has_text and not llm_failed:`
⇒ **上游已报错时不再触发安全网**（反向验证：撤掉 `and not llm_failed` ⇒
`test_send_message_stream_error_event_yields_error` 变红）。

> 429 是**账号级配额耗尽**，不是代码缺陷；但代码不该在明知失败时再浪费一轮。

## 六、教训（通用）

1. **「协议畸形」的表现是「格式脏」，根因却在请求侧**。用户报的是「排版不便阅读」，
   实际是**上游协议对不上**。⇒ 看到协议原文外泄，先查请求形状，别先调 CSS。
2. **读时清洗优于改库**：污染行读时清洗对历史 + 新行同时生效，
   **不写生产库、不用迁移**，原始数据留作证据。
3. **「旧缺陷」常被「新修复」暴露**：协议修好后工具真跑起来，
   才看见工具层 100% 报错 —— **别把「暴露」当成「引入」**。
4. **桩藏住被替换的调用方**（第 3 次踩）：桩自己实现了被调方**没有**的方法。
   ⇒ 通用解法：**用 `ast` 把「代码调的方法」与「真实类的方法集」对账**，不依赖桩。
5. **正文为空 ≠ 格式问题**：工具连错会让模型无限重试 ⇒ 轮次耗尽 ⇒ 空白。
   ⇒ 任何多轮 agent 都要有「**强制作答**」的兜底路径。
6. **「今天」必须可注入**（第 2 次踩）：`cn_today(now=None)`。
   测试里写死「今天」⇒ 跨周末/跨月**永久红**，CI 当时绿只是跑得早。
